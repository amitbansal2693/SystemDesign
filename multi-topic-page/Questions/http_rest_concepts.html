🔌 REST Principles
1
Core REST Principles▼
  • Client-Server — separation of client (UI) and server (data/logic)
  • Stateless — server stores no session state; each request contains all info needed
  • Cacheable — clients & intermediaries (browser, CDN) can cache responses
  • Uniform Interface — standard way to access data (GET, POST, PUT, DELETE)
  • Layered System — client is unaware of multiple layers (LB, security, cache, DB)
2
Is HTTP mandatory for REST?▼

No. Any protocol that supports REST principles can be used, but HTTP is the most common.

3
How does REST improve scalability?▼
  • Statelessness — reduces server memory (no session storage)
  • Cacheability — decreases server load
  • Layered System — components scaled independently
4
REST Pros & Cons▼

Pros

  • Simple — follows standard HTTP conventions
  • Cache-friendly — relies on HTTP caching mechanisms
  • Widely supported

Cons

  • Over-fetching / under-fetching — can't control response shape from client
  • Complex to fetch nested data (multiple API calls)
  • Versioning issues — schema changes require versioned endpoints

When to use

Simple, well-structured resources. Content-heavy APIs where caching matters.

CodeMeaning

💾 HTTP Caching in APIs
1
What is HTTP Caching?▼

Store responses temporarily so the client doesn't make repeated requests. Improves performance, reduces server load, saves bandwidth.

Types

  • Client-Side Cache — browser/API client stores responses
  • Proxy Cache — CDN stores responses
  • Server Cache — backend stores in Redis, database
2
Cache-Control Directives▼
DirectiveMeaning
publicAnyone can cache (browser, proxy, CDN)
privateOnly browser can cache
max-age=86400Fresh for 1 day
no-cacheAlways validate with origin before serving
must-revalidateOnce stale, re-check with server

Putting It Together

Client request: no-cache → "validate before use."

Server response: public, max-age=86400, must-revalidate → cacheable for 1 day, must revalidate after expiry.

📄 Pagination & Filtering
1
Pagination▼

Problem

10,000 recipes → GET /recipes returning all is slow, memory-heavy, network-heavy.

Solution

GET /recipes?page=1&size=20 Response: { "content": [...20 recipes...], "page": 1, "size": 20, "totalPages": 500 }
2
Filtering▼

Problem

Client wants only vegetarian recipes. Without filtering, client has to filter itself.

Solution

GET /recipes?category=Vegetarian GET /recipes?difficulty=Easy GET /recipes?caloriesLessThan=500

Server returns only matching records.

🏷️ API Versioning
1
Why API Versioning?▼

Problem

v1 returns {"name":"Pizza"}, then you change to {"recipeName":"Pizza"}. Existing mobile apps using "name" break.

Solution — Keep multiple versions

URL Versioning:

/api/v1/recipes /api/v2/recipes

Header Versioning:

Accept: application/vnd.company.v2+json

Old clients use v1, new clients use v2.

♻️ REST API Connection Pooling
1
Why Pooling in REST?▼

Creating a TCP connection is expensive (handshake + TLS + OS resources). Without pooling: 100 requests → 100 connections ❌. With pooling: 100 requests → reuse ~10 connections ✅.

Pooling reuses TCP connections, NOT requests, NOT threads.
2
How the Pool Works▼
Pool = [Conn1, Conn2, Conn3, Conn4, Conn5] 1. Request comes 2. Ask pool → get existing connection (or create new) 3. Execute request 4. Return connection to pool Pool full? Next request WAITs (connectionRequestTimeout)

Configuration

.setMaxConnTotal(20) // total connections across all hosts .setMaxConnPerRoute(10) // max connections per single host
3
HTTP Versions & Keep-Alive▼
VersionBehavior
HTTP/1.0Open → Close after each request ❌ Slow
HTTP/1.1Connection: keep-alive → reuse connection ✅ Needs pooling
HTTP/2Multiplexing — multiple requests on same connection ✅ Reduces need for pooling

gRPC uses HTTP/2 — that's why it's faster ⚡

4
Spring Boot Implementation▼
// Step 1: Create HttpClient with pool CloseableHttpClient httpClient = HttpClients.custom() .setMaxConnTotal(10) .setMaxConnPerRoute(5) .build(); // Step 2: Use with RestTemplate HttpComponentsClientHttpRequestFactory factory = new HttpComponentsClientHttpRequestFactory(httpClient); RestTemplate restTemplate = new RestTemplate(factory);

Full System View

Client → HTTP Connection Pool → REST API → DB Connection Pool → Database
5
Interview Answer▼
"REST APIs typically use HTTP/1.1 with keep-alive connections, allowing reuse of TCP connections. On the client side, connection pooling is used to efficiently manage multiple requests, while HTTP/2 further improves performance by multiplexing multiple requests over a single connection."
