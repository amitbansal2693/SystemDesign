🧮 Back-of-Envelope Estimation
1
What is Back-of-Envelope Estimation?▼

Quick calculations to estimate scale, capacity, and performance without exact numbers. Think: "Rough idea is enough — not exact precision."

Before building a system, ask

  • How many users?
  • How much data?
  • How many requests per second?
2
Cheat Sheet — Powers & Units▼

Memory Units

1 KB = 10³ 1 MB = 10⁶ 1 GB = 10⁹ 1 TB = 10¹² 1 PB = 10¹⁵

Time

1 day = 86 400 seconds

RPS = Total Requests / 86 400

Trick

Every +10 power ≈ ×1000

1M × 1MB ≈ 1TB (useful shortcut)

3

Worked Example — Instagram▼

Step 1 — Users

100M users, 10% active → 10M DAU

Step 2 — RPS

10 requests/user → 100M requests/day → 100M / 86 400 ≈ 1K RPS

Step 3 — Storage

2M uploads/day × 1MB = 2TB/day

2TB × 365 ≈ 730TB/year

6
Worked Example — Twitter▼

Given

300M monthly users, 50% DAU → 150M. Each user → 2 tweets/day (1KB). 10% tweets have media (1MB).

Write Storage/day

Text: 300M × 1KB ≈ 300GB/day

Media: 30M × 1MB ≈ 30TB/day (media dominates)

Storage over time

30TB × 365 ≈ 11PB/year → 55PB over 5 years

Read RPS

100 views/tweet → 300M × 100 = 30B reads/day → ~350K RPS

7
Worked Example — URL Shortener▼

Given

100M new URLs/day, each 500 bytes, 10 accesses/URL/day.

Storage

100M × 500B = 50GB/day → 18TB/year

Read RPS

100M × 10 = 1B reads/day → 10⁹ / 86 400 ≈ 10–12K RPS

8
Worked Example — YouTube Bandwidth▼

100M users × 5 videos × 10MB = 50MB/user → 5PB/day

Bandwidth: 5PB / 86 400 ≈ ~50–60 GB/s

🔗 Consistent Hashing
1
What is Consistent Hashing and why do we need it?▼

Consistent Hashing is a technique that minimizes data redistribution when nodes are added or removed. In regular hash-based partitioning (key % N), changing N requires moving almost all data. Consistent Hashing arranges nodes on a virtual ring so that only a small fraction of keys need to be reassigned.

Use Cases

  • Distributed caching (Memcached, Redis Cluster)
  • Database sharding
  • Load balancing across servers
  • Content Delivery Networks (CDN)
🚦 Rate Limiting
1
What is Rate Limiting?▼

Rate limiting prevents overuse or abuse of a system by limiting the number of requests over a period of time. It protects APIs, controls load, and improves security.

We Track

  • Who is making the request (user / IP / API key)
  • How many requests they've made
  • In what time window (per second / minute / hour)

Implementation

Store a counter per user/IP with a timestamp. On each request, check the limit for the current window. Use Redis or Memcached for performance.

2
Fixed Window Counter▼

Count requests within a fixed time window (e.g., per minute). Deny any more once the limit is hit.

Problem

Burst traffic at the window boundary can bypass the limit — a user can send max requests at the end of one window and at the start of the next.

3
Sliding Window Log▼

Log timestamps of each request. On each new request, check how many requests were made in the last T seconds.

Advantage

Blocks bursts regardless of minute boundaries — more accurate.

Disadvantage

Needs to store a list of timestamps per user — memory heavy at scale.

4
Sliding Window Counter▼

A hybrid approach. Uses Map<TimeBucket, Count> to track request counts. For each request, calculate which time bucket it belongs to and increase the count. Before processing, remove expired buckets and check the total.

Better accuracy than fixed window, less memory than sliding window log.

5
Token Bucket▼

Each user gets a bucket with tokens (e.g., 10). Tokens refill over time (e.g., 1/sec). Each request consumes 1 token. No tokens = wait or reject.

Advantage

Allows short bursts while enforcing a sustained average rate.

6
Leaky Bucket▼

Requests go into a queue (bucket). They "leak" out at a constant rate. If the bucket is full → reject new requests.

Result

Smooth, consistent request processing. No bursts allowed. Ideal for background jobs, message queues.

🔁 Idempotency
1
What is Idempotency?▼

An HTTP method is idempotent if making the same request multiple times produces the same final result as making it once. Repeating the request does not cause additional changes to the resource.

MethodIdempotent?
GET✅ Yes
PUT✅ Yes
DELETE✅ Yes
POST❌ No (can create multiple resources)
PATCH✅ Usually (if it sets values), but not always (e.g., incrementing a counter)
2
POST, PUT & PATCH — Examples▼

POST — Create

POST /users { "name": "John", "email": "john@example.com" } → 201 Created, Location: /users/101 Sending twice → two users created → NOT idempotent

PUT — Replace entire resource

PUT /users/101 { "name": "Johnny", "email": "johnny@example.com", "age": 31 } Sending 10 times → same final state → idempotent

PATCH — Partial update

PATCH /users/101 { "email": "johnny@example.com" } Only specified field changes; rest unchanged
📝 PUT vs PATCH & Idempotency Keys
1
Where do we need Idempotency?▼

Use idempotency when repeating an operation can create an unwanted business side effect.

  • Payment creation
  • Order creation
  • Money transfer
  • Booking / reservation
  • Subscription creation
  • Inventory updates
  • Message processing
  • Creating customer / account
2
HTTP Idempotency vs Idempotency Key▼

HTTP-level idempotency

HTTP defines GET, PUT, DELETE, HEAD, OPTIONS as idempotent. Idempotency is about the intended effect of repeating the request.

Idempotency Key

For operations like POST /payments which create new resources, we add:

Idempotency-Key: abc-123

The server recognizes: "This is the same logical operation I've already seen."

3
How to determine & use the Idempotency Key?▼

The client generates a unique key for each logical business operation. The same key must be reused on retries.

✅ Correct: Attempt 1 → key=A, Attempt 2 → key=A ❌ Wrong: Attempt 1 → key=A, Attempt 2 → key=B

Request Fingerprint

Additionally calculate hash(method + endpoint + body) and store alongside the key to detect misuse.

Same Key + Different Request → 409 Conflict

4
What does the server store?▼
FieldExample
Idempotency Keyabc-123
Request HashXYZ789
StatusCOMPLETED
HTTP Status201
Response Body{"paymentId":"P1001","status":"SUCCESS"}
TTL24 hours

Redis for fast tracking; database when stronger durability is needed.

5
Interview Summary — Key Rules▼
  • 1 Idempotency-Key = 1 logical operation
  • Same key + same request → return existing result
  • Same key + different request → reject (409)
  • Concurrent same key → atomic lock, only one executes
  • Payment timeout → don't assume failure → reconcile before retrying

Idempotency vs Retry vs Circuit Breaker

  • Retry — try the request again
  • Idempotency — make sure retry doesn't create duplicate business effect
  • Circuit Breaker — stop calls when a dependency is repeatedly failing
🔀 Forward & Reverse Proxy
1
What is a Proxy?▼

A proxy is an intermediate server that sits between a client and another server, forwarding requests and responses.

2
Forward Proxy▼

Used by the client to communicate with the internet while hiding the client's identity.

[Client] → [Forward Proxy] → [Internet Server]

Purpose

  • Hide client IP (anonymity)
  • Control internet access
  • Bypass geo-restrictions
  • Content filtering & monitoring

Tools

Squid Proxy, Privoxy, commercial VPNs, Bright Data, Smartproxy

3
Reverse Proxy▼

Used by the server to control and route traffic to backend systems while hiding them from the client.

[Client] → [Reverse Proxy] → [Internal Servers]

Purpose

  • Load balancing
  • SSL termination (handle HTTPS encryption)
  • Caching static content
  • Security / firewall
  • Routing to microservices
  • DDoS protection

Tools

NGINX, HAProxy, Apache HTTP Server, Cloudflare, AWS ALB

♻️ Connection Pooling
1
Why does pooling exist?▼

Creating a new resource (DB connection, TCP connection) for every request is expensive. With 1000 req/sec, that means 1000 new connections — the system crashes.

Core Idea: Don't create new resources → reuse existing ones.
2
How does a connection pool work?▼
Request comes ↓ Ask pool: "Give me connection" ↓ Use connection ↓ Return connection to pool

Pool Empty?

  • Wait ⏳
  • Fail ❌
  • Create new (rare)

Spring Boot

Uses HikariCP (default DB pool): spring.datasource.hikari.maximum-pool-size=10

3
System Design View▼
Client ↓ Rate Limiter 🚫 ← controls traffic ↓ Service ↓ Connection Pool 🔄 ← controls resources ↓ Database

Quick Test

10 requests, pool size = 5 → First 5 get connections, next 5 wait or fail.

One-Line: Pooling = reuse expensive resources instead of recreating them.
🛑 Single Point of Failure
1
What is a SPOF?▼

Any one component that, if it fails, can bring down the entire system. "If this one thing goes down, everything breaks."

Common Examples

  • Single Database Server
  • Single Cache Server (Redis)
  • Single Application Node
  • Single Load Balancer
  • Single Power Supply
2
Why is SPOF a problem & how to solve it?▼

Problems

  • Downtime — system unavailable
  • Data loss
  • Revenue loss & frustrated users
  • Scalability bottlenecks

Solutions — Design for Redundancy

  • Replication — replicas for DBs, caches
  • Clustering — group nodes together
  • Failover — auto switch to backup on failure
  • LB Redundancy — active-passive or active-active
  • Distributed Architecture — spread across zones/regions

Example: Redis SPOF

One Redis server → if it crashes, app slows or fails. Solution: Redis Sentinel or Redis Cluster for automatic failover.

⚖️ Trade-offs in System Design
1
How to explain a trade-off in an interview?▼
Requirement → Possible Options → Chosen Solution → Benefits → Trade-offs → Why Acceptable

Example

Requirement: Read-heavy app (millions of reads). Solution: Redis Cache.

Benefits: Faster response, reduced DB load.

Trade-off: Stale data, cache invalidation complexity.

Why OK: Product info changes infrequently.

2
Performance vs Consistency▼

Use Redis Cache → faster API response, reduced DB load. Trade-off: cached data may become stale, invalidation is complex.

Real examples: Amazon product pages, news websites, e-commerce catalogs.

3
Availability vs Consistency (CAP)▼

Prioritize Consistency

Every user sees latest data. Trade-off: system may reject requests during failures. Use for: Banking, payments.

Prioritize Availability

System stays online. Trade-off: some users may see outdated data. Use for: Facebook, Instagram, Twitter.

4
Read vs Write Performance▼

Create DB indexes → faster SELECT. Trade-off: INSERT, UPDATE, DELETE become slower, extra storage needed.

5
Simplicity vs Flexibility (Monolith vs Microservices)▼

Monolith

Easy to develop, test, debug, deploy. Trade-off: hard to scale individual modules, full redeploy needed.

Microservices

Independent deployment & scaling, fault isolation. Trade-off: distributed system complexity, network latency, service discovery.

"For a small startup → monolith. As the app grows → microservices."
6
Sync vs Async Communication▼

Synchronous

Immediate response, easier to debug. Trade-off: higher latency, tighter coupling.

Asynchronous (Kafka, RabbitMQ)

Faster API response, better scalability, loose coupling. Trade-off: eventual consistency, complex error handling.

Sync: Create Order → Send Email → Generate Invoice → Return Async: Create Order → Publish Event → Return 200 OK Background: Email, Inventory, Invoice services
7
Other Common Trade-offs▼
  • Scalability vs Cost — horizontal scaling = more infra cost but better scalability
  • Security vs UX — MFA = better protection but extra login step
  • Normalization vs Performance — normalized = less duplication; denormalized = faster reads
  • Storage vs Speed — caching = faster access but more memory, stale data risk
  • Strong vs Eventual Consistency — strong = latest data, higher latency; eventual = high availability, lower latency
⚡ Concurrency vs Parallelism
1
What is the difference?▼

Concurrency

Dealing with multiple tasks at the same time by interleaving execution. Tasks may not run simultaneously — they take turns on a single core.

Parallelism

Actually executing multiple tasks at the same instant on multiple CPU cores.

Concurrency = structure (managing many tasks). Parallelism = execution (running many tasks simultaneously).
📈 Parallel Data Fetching & Early Permission Filtering
1
Architecture Concept▼

Key Ideas

  • Early permission filtering + distributed authorization — permissions evaluated early in the pipeline
  • Unauthorized data filtered before ranking & aggregation → reduces unnecessary processing
  • Parallel data pollination — fetching data concurrently

Result

  • More reliable search
  • Fewer authorization failures
  • Better consistency under load

Interview Statement

"We redesigned the search pipeline to use parallel data pollination and early permission evaluation. By distributing permission checks across the search flow and fetching data concurrently, we reduced unnecessary processing and improved both latency and reliability."

Resume Bullets

  • Improved search performance by ~500ms by introducing parallel data fetching and early permission filtering
  • Reduced search latency through parallelized data aggregation and optimized permission evaluation
