💼 Current Project Challenges

Real-world system design problems and solutions

Q.1: What was the problem as Samsung's business grew? ▶
"As Samsung expanded its product portfolio beyond traditional consumer electronics into products such as wearables, home appliances, accessories and other connected products, the traffic and size of the e-commerce platform increased significantly across multiple countries."
Challenges Created by Growth ▶

As Samsung expanded globally, several challenges emerged:

  • Increasing traffic and concurrent users
  • Increasing product catalog size
  • Increasing search volume
  • Larger Solr indexes
  • Longer indexing times
  • Higher database load
  • Increasing response latency
  • More frequent batch/cron processing
  • Difficulty maintaining consistent performance during peak traffic
Why Scaling Was Difficult ▶

The existing architecture was becoming difficult to scale:

"We were reaching the limits of scaling a single application/search/database setup."

Architect's Observation: The important point was that adding CPU or memory to a single node was no longer sufficient. We needed horizontal scalability and better distribution of workload.
Q.2: How did you solve the scalability problem? ▶
Presented as five architectural decisions for horizontal scaling and workload distribution.
Solution 1: Multi-Region / Multi-Cluster Architecture ▶

Introduce multiple clusters across regions so that traffic could be distributed geographically instead of sending all requests to a single cluster.

Customer → Global Routing → Regional Cluster → Application Nodes → Solr

This helped with:

  • Geographic latency reduction
  • Improved availability
  • Traffic distribution
  • Regional scalability
Solution 2: Full Product Catalog Per Cluster ▶

Each regional cluster maintained the product catalog required for that market, so search requests could be served locally.

Each cluster maintained the complete catalog required for the markets it served, allowing local query serving without depending on another region for every search.
Solution 3: Replication / Synchronization ▶

Because each cluster was independently deployed, product data, configuration and indexing activities had to remain synchronized across clusters.

Product Update → Source System
    → Cluster A
    → Cluster B
    → Cluster C

We replicated the required indexing and data-processing processes across clusters so each could independently build and maintain its search index.

Solution 4: Routing ▶

Introduced routing so that customers were directed to the appropriate regional cluster based on factors such as geography, domain or market.

Customer → DNS/Global Routing → Region → Cluster → Application

This reduced unnecessary cross-region traffic.

Solution 5: Search Optimization ▶

Optimized the search layer by distributing the search workload and reducing the size of individual indexes where possible.

This resulted in:

  • Faster search
  • Faster indexing
  • Better resource utilization
  • Reduced search latency
Trade-Offs and Key Decision ▶

The architecture increased infrastructure and Solr costs because multiple clusters and indexes had to be maintained. However, this cost was justified by:

  • Improvement in performance
  • Improved availability
  • Better scalability
Strong Closing Statement: The main architectural decision was to trade some infrastructure cost and operational complexity for horizontal scalability, lower latency and better availability.
Q.3: How did you migrate existing orders when introducing sharding? ▶
This is one of the strongest interview questions because it demonstrates understanding of distributed database migration challenges.
The Problem with Sharding Migration ▶

The challenge was that the existing database contained historical and active orders for multiple countries in a single database. We could not simply split the database because:

  • Customers still needed access to their historical orders
  • Some orders were still active (installment-based orders)
  • Live business processes depended on order state
Before Sharding:
Existing DB
├── India Orders
├── Germany Orders
├── UK Orders
├── Latvia Orders
└── USA Orders

After Sharding:
India → DB 1
Germany → DB 2
UK → DB 3
etc.
Phase 1: Define Shard Key ▶

First, we defined the shard key (for example: country/market) based on how the application accessed the data.

Important: The shard key should align with the application's most common access pattern.
Phase 2: Historical Data Migration ▶

Migrated existing records based on the shard key:

Existing DB → Extract → Transform/Validate → Target Shard
Example: Country = Germany → Germany DB
         Country = India → India DB
Phase 3: Active Orders Handling ▶

Active orders required special handling because they had ongoing business processes.

We used controlled migration, validation and reconciliation rather than moving everything in a single operation. This ensured that:

  • Payment processing was not interrupted
  • Fulfillment workflows continued
  • Installment processes were maintained
  • Customer history remained accessible
Phase 4: Shard Routing ▶

The application needed to know: "Which database contains this order?"

Customer → Order ID/Customer/Market → Shard Resolver → Correct DB
Critical Interview Point: Sharding isn't just a database change. The application also needs a deterministic way to identify the correct shard for every request.
Phase 5: Validation and Gradual Cutover ▶

After migration, we performed comprehensive validation:

  • Source Count = Target Count
  • Checksums / Data Validation
  • Order Status Validation
  • Payment Status Validation
  • Customer History Validation

Then we gradually moved traffic to the new sharded database.

Important Challenge: Cross-Shard Queries ▶

Cross-shard queries became difficult. For example:

"Give me all orders for this customer across all countries."

Request → Shard 1 + Shard 2 + Shard 3 → Aggregate Results

Therefore, we tried to keep operations shard-local wherever possible and avoided unnecessary cross-shard transactions.

Q.4: What problem did Spartacus solve? ▶
Framed as a decoupling problem between frontend and backend, not just a technology choice.
The Problem: Tight Coupling ▶

The existing storefront was tightly coupled with the SAP Commerce backend. This meant:

  • Frontend development was highly dependent on backend changes
  • Changes in one layer could affect the other
  • Release dependencies existed between teams
  • Longer development cycles
  • Difficult independent testing
  • Higher coordination between teams required
Backend Change → Storefront Impact
Storefront Change → Backend Dependency
Solution: Headless Architecture with Spartacus ▶

We moved towards a headless storefront using Spartacus, where the frontend was separated from the commerce backend and interacted through APIs.

Spartacus → OCC REST APIs → SAP Commerce

Now both teams could:

  • Develop independently
  • Test independently
  • Deploy independently
  • Scale independently
Key Benefit: The key benefit wasn't simply introducing Spartacus. It was reducing coupling between the presentation layer and the commerce backend.
Q.5: How did frontend and backend communicate and deploy independently? ▶
Once decoupled architecturally, the implementation required clear communication contracts and independent deployment pipelines.
Communication: REST APIs as Contract ▶

We used REST APIs as the contract between Spartacus and SAP Commerce.

Spartacus → HTTP/REST → OCC → SAP Commerce

The API contract became the boundary between the teams. As long as both sides adhered to the contract, development could proceed independently.

CORS (Cross-Origin Resource Sharing) ▶

Because the frontend and backend could be hosted on different origins:

Frontend Origin ≠ Backend Origin

The browser enforced CORS. We configured the backend to allow:

  • Required frontend origins
  • Allowed HTTP methods
  • Required headers

Browser flow:

Browser → OPTIONS → Backend
Backend → CORS Headers → Browser
Browser → GET/POST → Backend

Note: Tools like Postman don't enforce browser CORS, so testing without CORS errors is possible in tools but required in browsers.

Independent Deployment ▶

Because the frontend and backend were independently deployable, they had separate CI/CD pipelines and infrastructure.

Spartacus → Pipeline → Frontend Infrastructure

SAP Commerce → Pipeline → Backend Infrastructure

Both could be deployed independently, even across different cloud environments if required.

Architectural Point: The key advantage is independent deployment and scaling capabilities, not merely using different cloud providers.
Q.6: What deployment strategies did you use? ▶
Different deployment scenarios require different strategies. Blue-Green and Canary are often confused—here's the distinction.
Blue-Green Deployment ▶

Blue-Green means:

  • Blue = Current Production
  • Green = New Version

Process:

Test Green → Switch Traffic → Green serves requests
Rollback: Switch back to Blue if needed

Use case: For major features such as new trade-in capability, we could deploy the new version alongside the existing version, validate it and then switch traffic.

Advantage: Controlled, quick switch and easy rollback.

Canary Deployment ▶

Canary deployment means exposing new functionality to a small percentage or selected group of customers first, monitoring the system and gradually expanding the rollout.

New Version → Small User Group → Monitor → Increase Traffic → 100%

Example: We exposed the new rewards functionality to a small percentage of customers first, monitored the system and gradually expanded the rollout.

Advantage: Reduces risk by testing with real traffic before full rollout.

Feature Flag / Progressive Rollout ▶

Different from Blue-Green and Canary, feature flags allow functionality-based control.

Feature OFF → B2C
Feature ON → B2B
Then gradually:
B2B → 10% Users → 50% → 100%

This allows fine-grained control over feature availability without full deployment changes.

Key Distinctions ▶
  • Blue-Green: Environment-based switching
  • Canary: Traffic/user-based gradual rollout
  • Feature Flag: Functionality-based enable/disable
Q.7: Payment Problems ▶
This is a strong production problem demonstrating integration, asynchronous processing and state management. Three separate stories are involved.
Problem 1: 3DS Authentication Issue ▶

Problem: We had an issue in the 3DS authentication flow with Mercado Pago where customers did not receive the expected authentication challenge, causing the issuing bank to reject the payment.

Investigation: We traced the payment flow:

Customer → Samsung → Payment Provider → 3DS → Issuing Bank

We checked:

  • Payment request
  • 3DS configuration
  • Redirect/challenge flow
  • Payment provider response
  • Callback/notification
  • Final transaction state

Solution: We corrected the authentication flow and ensured that the customer was correctly redirected into the 3DS challenge and that the resulting authentication status was correctly propagated through the payment flow.

Problem 2: Misinterpreting Adyen Status ▶

Problem: Our application treated Adyen "Received" or "Pending" responses as payment failures, while these statuses actually meant that Adyen had accepted the request but was still processing it.

This is a state-machine problem:

Incorrect:
Received → FAILED

Correct:
Received → PROCESSING/PENDING
    ↓
SUCCESS / FAILED (eventually)

Solution: We corrected the payment state mapping and made the business process asynchronous where the payment provider's response indicated that processing was still in progress.

Payment Request → Adyen → Pending → Notification → Final Status
Key Insight: We separated the payment-request state from the final payment state instead of assuming that the initial provider response represented the final outcome.
Problem 3: PTE Update Race Condition ▶

Problem: During payment capture notification processing, there was a 2–3 second delay before the Payment Transaction Entry was updated. The downstream business process did not wait for that state transition and interpreted the payment as unsuccessful.

This is a race condition / timing problem:

Payment Notification → PTE Update (2-3 sec delay)

But:
Business Process → Checks PTE too early → Payment Failed

Solution: We changed the processing flow so that downstream business logic was triggered only after the required payment state was persisted. We improved:

  • Asynchronous notification handling
  • State validation
  • Event-driven processing
  • Retry mechanisms
  • Idempotency checks
Strong Interview Line: The core issue was not simply latency. It was that the system assumed a state transition had completed when it was still in progress.
Q.8: Duplicate Serial Numbers ▶
An excellent concurrency/distributed-system story demonstrating state coordination challenges.
The Problem ▶

Serial number ranges were maintained in each node's in-memory cache. Each node could hold its own sub-range, but under certain circumstances two nodes could end up with overlapping ranges, resulting in duplicate serial numbers.

Architecture:
Node 1 → numberCacheMap → Range A
Node 2 → numberCacheMap → Range B
Node 3 → numberCacheMap → Range C

Problem:
Node 1 → Range 1000–1999
Node 2 → Range 1000–1999

Result:
Node 1 → Serial 1001
Node 2 → Serial 1001
= DUPLICATE
Root Cause: The allocation state was distributed across node-local memory, while the serial number itself needed global uniqueness. That is a state coordination problem.
Solution: Atomic Central Allocation ▶

The best architectural approach was to make range allocation atomic and centrally coordinated:

Central DB/Sequence → Atomically Allocate Range → Node 1
Central DB/Sequence → Atomically Allocate Different Range → Node 2

Then:
Node 1 → Local Range 1–1000
Node 2 → Local Range 1001–2000

This gives the performance benefit of local caching while keeping allocation globally safe.

Strong Architect Statement: We separated range allocation from serial-number consumption. Allocation required global coordination, while consumption could happen locally.
Q.9: Configuration Property Update ▶
Configuration changes needed to be propagated reliably across a distributed cluster of nodes.
The Problem: Stale Configuration ▶

Configuration properties were cached in application memory. When a configuration value changed, every node could continue using its stale local value until the cache was manually refreshed or the application was restarted.

Initial State:
Node 1 → Config = A
Node 2 → Config = A
Node 3 → Config = A

Admin changes Config to B:

But:
Node 1 → Still uses A
Node 2 → Still uses A
Node 3 → Still uses A

Result: Inconsistent behavior across cluster
Initial Solution: Manual Refresh ▶

Manual refresh or restart wasn't ideal because:

  • Requires manual intervention
  • Causes downtime
  • Doesn't scale for frequent changes
  • Error-prone
Improved Solution: Event-Based Cache Invalidation ▶

We introduced event-based cache invalidation so that when configuration changed, an event was published and the affected nodes invalidated or refreshed their local cache.

Config Updated → Event → Nodes → Invalidate Local Cache → Read New Value

Benefits:

  • No manual intervention required
  • Faster propagation
  • Consistent configuration across cluster
  • Better operational reliability
Key Change: We moved from manual synchronization to event-driven cache invalidation.
Q.10: Obsolete Data Cleansing ▶
Removing old data efficiently without impacting production workload requires careful design and controlled parallelism.
The Problem ▶

Over time, the system accumulated obsolete data such as old records that were no longer required for active business processing. Running a large cleanup synchronously created significant database load and could affect production workload.

Millions of obsolete records → DELETE → DB Load

A single huge delete creates:

  • Long transactions
  • Table/index contention
  • High CPU/I/O
  • Locking issues
  • Transaction log growth
  • Application performance degradation
Solution: Batch Processing with Controlled Parallelism ▶

Instead of deleting everything in one large transaction, we processed the cleanup in smaller batches using controlled parallelism.

Obsolete Records → Batch → Worker Threads → Delete → Next Batch

Example:
10 million records → Batch 1 → Batch 2 → Batch 3 → ...

We used a bounded thread pool:

  • Cleanup could run concurrently
  • Remained within controlled resource limits
  • Did not compete aggressively with customer-facing traffic
This directly applies to Concurrency, Thread Pool and Bulkhead pattern concepts.
Additional Improvements ▶

We made the cleanup incremental and throttled it:

  • Batch processing: Delete smaller chunks
  • Bounded thread pool: Control parallelism
  • Scheduled execution: Run during off-peak hours
  • Database indexes: On cleanup criteria for faster identification
  • Commit after each batch: Reduce transaction size
  • Retry failed batches: Handle transient failures
  • Monitoring: Track progress and issues
  • Backpressure/throttling: Adjust based on system load
Strong Architect Statement ▶

"The goal wasn't simply to delete data faster; it was to remove obsolete data without impacting the production workload."

That is the important distinction.
