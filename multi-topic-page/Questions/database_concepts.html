📇 Indexing

What is a Database Index?▼

An index is a separate data structure (usually a B+ Tree) that stores indexed column values along with pointers to the corresponding table rows, allowing the database to find data quickly without scanning the entire table.

Trade-off

FasterSlower
SELECT, WHERE, JOIN, ORDER BYINSERT, UPDATE, DELETE

Extra storage is required to store the index data structure.

2
How does an index work internally?▼

Without Index

SELECT * FROM Users WHERE UserId = 205; → checks every row → O(n)

After creating index

CREATE INDEX idx_userid ON Users(UserId); 205 / \ 150 300 / 101 Each value stores a pointer to the actual row.
Search Tree → Find 205 → Follow Pointer → Read Row #2

Time complexity: O(log n)

The index does NOT store the complete row — only indexed values + pointers.
3
B+ Tree vs Inverted Index▼

B+ Tree — for structured data (IDs, dates, salaries). Used by relational databases.

Inverted Index — maps each word (token) to documents containing that word. Used by search engines (Solr, Elasticsearch) for full-text search.

4
Interview Answer (30 seconds)▼
"An index is a separate data structure, usually a B+ Tree, created on one or more columns. It stores the indexed values and pointers to the actual table rows. Instead of scanning the entire table, the database searches the index first and then directly accesses the matching row. This improves read performance from roughly O(n) to O(log n), at the cost of additional storage and slower insert, update, and delete operations."
🍰 Sharding
1
What is Sharding?▼

Sharding splits large datasets into smaller chunks — called shards — stored across multiple databases/servers. Each shard holds a subset of data and is usually independent.

Analogy

Dividing 1000 students into rooms by name: Room 1 (A–F), Room 2 (G–L), Room 3 (M–Z). Each room manages a portion.

2
How does sharding work?▼

Define a shard key — a field used to decide which shard each record belongs to (e.g., user_id, region, tenant).

Types

  • Horizontal Sharding — each shard contains rows. Most common. E.g., Users 1–1000 in one shard, 1001–2000 in another.
  • Vertical Sharding — split by columns/features. E.g., one shard for profile info, another for transactions.
3
Benefits & Challenges▼

Benefits

  • Scalability — spread the load
  • Performance — queries faster on smaller datasets
  • Availability — one shard down doesn't take everything down

Challenges

  • Complex queries — joins across shards are hard
  • Rebalancing — hot shards need splitting
  • Shard key design — bad key = uneven distribution
  • Cross-shard transactions — tricky
  • Operational complexity — backups, migrations

When to Use

✅ DB too big for one server, queries slowing down, hit I/O limits.

❌ Don't shard too early — start with vertical scaling or replication first.

📦 Partitioning
1
Partitioning Criteria▼

1. Key / Hash-Based

Apply a hash function to a key attribute (e.g., ID % 100). Ensures uniform allocation. Problem: adding servers requires redistribution → use Consistent Hashing as a workaround.

2. List Partitioning

Each partition assigned a list of values. E.g., Nordic countries (Iceland, Norway, Sweden, Finland, Denmark) in one partition.

3. Round-Robin

Tuple i assigned to partition i mod n. Simple, ensures uniform distribution.

4. Composite

Combine schemes — e.g., first list partitioning then hash-based. Consistent hashing is a composite of hash + list.

2
Common Problems of Data Partitioning▼

Joins & Denormalization

Joins across partitions on different machines are not performance efficient. Workaround: denormalize so queries can run from a single table (at the cost of data inconsistency).

Referential Integrity

Most RDBMS don't support foreign keys across different database servers. Applications must enforce integrity in code and run cleanup jobs for dangling references.

Rebalancing

Reasons: uneven data distribution, too much load on a partition. Rebalancing without downtime is extremely difficult. Directory-based partitioning helps but creates a new SPOF (the lookup service).
