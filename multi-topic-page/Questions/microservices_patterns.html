🛡️ Resilience Patterns
1
What are Resilience Patterns?▼

Design patterns that help microservices continue functioning even when services are slow, unavailable, or fail.

PatternPurpose
TimeoutDon't wait forever — stop after threshold
RetryRetry temporary failures
Circuit BreakerStop calling a failing service
FallbackReturn alternative response
BulkheadIsolate resources to contain failures
Rate LimiterProtect from excessive requests
IdempotencyEnsure retries don't create duplicates
2
Retry Pattern▼

Automatically retry a failed request when the failure is temporary (network glitch, service starting up, short DB lock).

Attempt 1 → Failed Attempt 2 → Failed Attempt 3 → Success ✅

Trade-offs

  • ✅ Handles transient failures, improves success rate
  • ❌ Can increase latency, may overload a failing service

Tools: Resilience4j Retry, Spring Retry

3
Timeout Pattern▼

Set a maximum waiting time. If no response → cancel and return error/fallback.

Trade-offs

  • ✅ Prevents thread exhaustion, faster failure detection
  • ❌ Too short → rejects valid requests; too long → poor performance

Tools: WebClient, RestTemplate, OpenFeign, Resilience4j TimeLimiter

4
Fallback Pattern▼

When primary service is unavailable, return: cached data, default value, friendly message, or alternative service.

Trade-offs

  • ✅ Better UX, improved availability, graceful degradation
  • ❌ Users may see stale/incomplete data, added complexity
⚡ Circuit Breaker
1
What is a Circuit Breaker?▼

Stops sending requests to a failing service for a period, preventing repeated failures and allowing recovery.

Problem without it

Order Service calls Payment Service (down) → all requests wait until timeout → threads blocked → entire Order Service becomes slow/unavailable.

2
Three States▼
CLOSED ──→ OPEN ──→ HALF-OPEN ──→ CLOSED │ │ │ │ Failure Timeout Success ✅ threshold period threshold

1. Closed (Normal)

All requests pass through. Failures monitored. If failure rate exceeds threshold (e.g., 50% of last 10) → transition to Open.

2. Open (Blocking)

Rejects all requests immediately — returns fallback or exception. Remains open for configured timeout (e.g., 10s). Then → Half-Open.

3. Half-Open (Testing)

Limited test requests allowed. If successful → back to Closed. If they fail → back to Open.

3
Trade-offs & Tools▼

Advantages

  • Prevents cascading failures
  • Faster failure response
  • Reduces unnecessary network calls
  • Gives failing services time to recover

Disadvantages

  • Additional configuration
  • Wrong thresholds may block healthy services

Tools: Resilience4j, Spring Cloud Circuit Breaker

🚢 Bulkhead Pattern
1
What is the Bulkhead Pattern?▼

Isolates resources (thread pools, connection pools) into separate compartments so that failure in one part doesn't affect others.

Named after watertight compartments in ships — if one floods, the rest stay dry.

Problem

All services share one thread pool → Notification Service slow → occupies all threads → Payment & Order also fail.

Solution

Order Thread Pool — 50 threads Payment Thread Pool — 20 threads Notification Thread Pool — 10 threads Notification slow? Only its 10 threads affected. Orders & Payments continue normally.
2
Types & Implementation▼

1. Thread Pool Bulkhead (Most Common)

Each service gets its own thread pool. Used heavily in Spring Boot.

2. Semaphore Bulkhead

Limit concurrent requests (e.g., max 10). 11th request → rejected immediately.

Spring Boot

@Bulkhead(name = "paymentService", type = Bulkhead.Type.THREADPOOL)

Trade-offs

  • ✅ Prevents cascading failures, protects critical services
  • ❌ Resources may be underutilized, pool size needs tuning
🔄 Saga Pattern
1
What is the Saga Pattern?▼

A distributed transaction pattern that maintains business consistency across multiple microservices without a global database transaction. The business transaction is divided into a sequence of local transactions, each with a compensating transaction.

Problem

In microservices, each service owns its DB — can't use one ACID transaction across all.

2
How it works — Success & Failure▼

Success Flow

Create Order ✅ → Reserve Inventory ✅ → Process Payment ✅ → Confirm Order ✅

Failure → Compensating Transactions

Create Order ✅ → Reserve Inventory ✅ → Payment ❌ ↓ Release Inventory ↓ Cancel Order
Important: Compensation ≠ DB rollback. It's another business transaction (e.g., Refund Payment, Release Inventory).
3
Choreography vs Orchestration▼

Choreography — No central coordinator

Services communicate through events. Each listens and decides what to do next.

OrderCreated → Kafka → Inventory → InventoryReserved → Kafka → Payment
  • ✅ Decentralized, no SPOF, good for simple workflows
  • ❌ Hard to understand in complex systems, difficult debugging

Orchestration — Central Saga Orchestrator

Orchestrator controls the workflow, telling each service what to do.

Saga Orchestrator / | \ Order Inventory Payment
  • ✅ Easy to understand, centralized control, easier monitoring
  • ❌ Orchestrator = additional component, can become bottleneck
4
Saga + Idempotency + Transactional Outbox▼

Saga + Idempotency

Messages can be delivered more than once. Consumers must be idempotent — check event/message ID, ignore if already processed.

Saga + Transactional Outbox

DB Transaction: ├── Update Order └── Insert Outbox Event ↓ COMMIT Outbox Publisher → Kafka

Ensures if DB commits, the event is not lost (even if Kafka is temporarily unavailable).

Saga + Eventual Consistency

For a short period, different services may show different states. Eventually all converge.

5
Interview Answer▼
"Saga is a pattern for managing distributed business transactions across microservices where each service has its own local transaction and database. Instead of using a global transaction, the Saga coordinates a sequence of local transactions. If a later step fails, compensating transactions are executed for the previously completed steps. It can be implemented using choreography (events) or orchestration (central coordinator). The main challenges are eventual consistency, compensation logic, duplicate events, and workflow visibility. I would combine Saga with idempotent consumers, transactional outbox, retries, and observability."

When NOT to use

If the operation can be contained within a single service and database → prefer a normal local transaction. Introduce Saga only when the distributed workflow actually requires it.

📊 CQRS
1
What is CQRS?▼

Command Query Responsibility Segregation — separates write operations (Commands) from read operations (Queries), allowing each to be optimized and scaled independently.

Application ┌──────┴──────┐ Command Query ↓ ↓ Write Model Read Model ↓ ↓ Write DB Read DB
2
Problem it Solves▼

Read and write requirements are often very different:

Write SideRead Side
Complex validation, transactions, business rulesFast queries, aggregated data, search/filtering

Using the same model for both makes the system unnecessarily complicated.

3
CQRS with Event-Driven Architecture▼
Command → Write Service → Write DB ↓ Event Kafka / RabbitMQ ↓ Read Model Updater → Read DB → Query

Important

CQRS does NOT necessarily mean two databases. You can use the same DB with separate models.

4
Advantages & Drawbacks▼

Advantages

  • Independent optimization of read/write
  • Independent scaling (10K reads + 100 writes → scale reads)
  • Pre-computed/aggregated read models
  • Different tech per side (PostgreSQL for writes, Elasticsearch for reads)

Drawbacks

  • Increased complexity (two models + sync)
  • Eventual consistency — small delay between write and read update
  • More infrastructure (message broker, event processing, retry/error handling)
  • Must handle duplicate/out-of-order events
5
CQRS vs Event Sourcing vs CRUD▼
ConceptWhat it does
CQRSSeparates commands and queries
Event SourcingStores state changes as events
CRUDSame model for read and write

CQRS and Event Sourcing are often used together but are independent concepts.

When to use CQRS

  • Read/write workloads significantly different
  • Read performance is critical
  • Complex business/write logic
  • Independent scaling needed

When NOT to use

Simple CRUD — don't introduce CQRS just because you're building microservices.

🗄️ Data Management Patterns
1
Database per Service ⭐⭐⭐⭐⭐▼

Each microservice owns its own database. Other services access data through APIs or events — not by querying the DB directly.

Advantages

  • Loose coupling, independent deployment & scaling
  • Technology flexibility (MySQL for one, MongoDB for another)
  • Clear data ownership, better security

Disadvantages

  • No cross-service joins
  • Distributed transactions are difficult
  • Data duplication may be needed
2
Shared Database (Anti-Pattern)▼

Multiple services share one database. Initially convenient (easy joins, ACID) but creates tight coupling, no clear ownership, schema changes affect all, hard to scale independently.

Generally considered an anti-pattern in true microservices architecture.
3
Event Sourcing ⭐⭐⭐⭐▼

Instead of storing latest state, store every business event. Current state rebuilt by replaying events.

Account Created → Deposit $500 → Deposit $700 → Withdraw $300 Current Balance = $900 (rebuilt from events)

Advantages

  • Complete audit history
  • Supports temporal queries ("balance yesterday?")
  • Easy event replay, better debugging

Disadvantages

  • Complex implementation
  • Schema evolution must be managed
  • Rebuilding state slower without snapshots

Tools: Axon Framework, EventStoreDB, Spring Kafka

4
Transactional Outbox ⭐⭐⭐⭐⭐▼

Problem

Order Service saves to DB ✅ then publishes to Kafka ❌ (Kafka down) → order exists but no event published → data inconsistency.

Solution

DB Transaction: ├── Save business data └── Save event to Outbox table ↓ COMMIT Background process → Read Outbox → Publish to Kafka → Mark processed

If DB commits, the event is guaranteed not to be lost.

Trade-off

Duplicate events possible → consumers should be idempotent.

Tools: Debezium (CDC), Kafka Connect

🔍 Service Discovery
1
Why Service Discovery?▼

In microservices, services are deployed dynamically — IPs change due to K8s, Docker, auto-scaling. Hardcoding addresses is not practical.

Solution: A Service Registry. When a service starts, it registers. Others query the registry to find current locations.

Examples: Eureka, Consul, Zookeeper, Kubernetes DNS

2
Client-side vs Server-side Discovery▼

Client-side Discovery

Client queries the registry, gets instances, selects one using load-balancing algorithm, sends request directly.

  • ✅ No extra proxy, lower latency, intelligent client-side LB
  • ❌ Discovery logic in every client, more complex clients

Tools: Netflix Eureka Client, Spring Cloud LoadBalancer

Server-side Discovery

Client sends to API Gateway / LB, which queries registry and forwards to an instance.

  • ✅ Simpler clients, centralized discovery & LB
  • ❌ Additional infrastructure, extra hop latency

Tools: Spring Cloud Gateway, NGINX, K8s Service/Ingress

🕸️ Service Mesh
1
What is a Service Mesh?▼

An infrastructure layer that manages service-to-service communication using sidecar proxies, providing traffic management, security, observability, and resiliency without changing application code.

Service Mesh is a design pattern; Istio is its implementation.

Problem it solves

In large architectures, every service needs secure communication, retries, timeouts, LB, monitoring, circuit breaking → implementing in every service = duplicate code, inconsistent implementations.

2
Architecture — Sidecar + Control Plane▼

Sidecar Proxy (Data Plane)

Runs alongside every service, intercepts all traffic. Handles: routing, LB, retry, circuit breaker, timeout, mTLS, metrics.

Examples: Envoy, Linkerd Proxy

Control Plane

Manages & configures all sidecars. Handles: traffic policies, security policies, certificate management, service discovery.

Examples: Istio, Linkerd

3
Features & Use Cases▼
CategoryFeatures
Traffic ManagementRouting, LB, canary releases, blue-green, traffic splitting
SecuritymTLS, authentication, authorization, certificate mgmt
ObservabilityDistributed tracing, metrics, logging, monitoring
ResilienceRetry, circuit breaker, timeout, fault injection

When to use

  • Large, complex microservice architectures
  • Security is a priority (mTLS)
  • Need advanced traffic management

Trade-offs

  • ✅ No code changes, centralized management, built-in observability
  • ❌ Additional infrastructure, higher resource usage, learning curve, slight latency increase
🏎️ Sidecar Proxy
1
What is a Sidecar Proxy?▼

A small service that runs alongside your main application, handling all networking tasks. Called "sidecar" like a motorcycle sidecar — works alongside the primary service.

Each microservice in a Service Mesh has its own sidecar proxy. Instead of handling network communication directly, the sidecar takes over.

2
How it Works▼
Service A → A's Sidecar Proxy → B's Sidecar Proxy → Service B ↑ mTLS encryption ↑

Responsibilities

  • Traffic Management — load balancing, retries, timeouts
  • Security (mTLS) — both services verify identity & encrypt traffic
  • Observability — collects latency, success/failure metrics → monitoring tools
  • Routing — uses rules from Control Plane (e.g., 90% stable, 10% canary)

Internal Working

  • Injected into K8s pod, intercepts traffic via iptables
  • Service discovery via Control Plane
  • Metrics sent to Prometheus/Grafana without code changes

Popular Proxies: Envoy (most common, used in Istio), Linkerd-proxy, HAProxy
