🚀 How To Scale

System Design Scaling Strategy Interview Guide

How would you scale a system from 1 user to 1M+ users?
▼
Opening Answer: "I would scale the system incrementally rather than introducing a complex distributed architecture from day one. At every stage, I would first identify the bottleneck and then introduce the architecture needed to solve that specific problem."
📱 Stage 1: 1 → 1K Users
▼
Focus
Simple Monolith + Database
Problem
At this stage, the primary focus is building and validating the product. The traffic is still small, so a distributed architecture would add unnecessary complexity.
Solution
I would start with a simple monolithic application and a relational database. I would focus on clean code, proper database design, indexing, and query optimization.
Why?
A monolith is easier to develop, deploy, debug and operate at this stage.
Future Challenge
As traffic grows, a single application instance becomes a scalability and availability bottleneck.
⚖️ Stage 2: 1K → 10K Users
▼
Focus
Horizontal Scaling + Load Balancer
Problem
A single application instance may no longer handle the increasing traffic, and if that instance fails, the entire system becomes unavailable.
Solution
I would make the application stateless, deploy multiple instances, and put a load balancer in front of them.
Load Balancer → Instance 1 / Instance 2 / Instance 3
Benefits
  • Horizontal scalability
  • Higher availability
  • Traffic distribution
  • Easy replacement of failed instances
New Challenge
Since we now have multiple instances, I cannot depend on local application memory for shared state or sessions.
Solution: Use stateless authentication or a shared state store such as Redis where required.
Future Challenge
The application layer can now scale, but the database may become the next bottleneck.
💾 Stage 3: 10K → 100K Users
▼
Focus
Cache + Read Replicas + CDN
Problem
The database starts receiving a large number of repeated read requests, increasing database load and response latency.
Solution 1: Cache
I would introduce Redis for frequently accessed data.
Application → Redis → Database
This reduces database load and improves latency.
Solution 2: Read Replicas
If the workload is read-heavy, I would introduce read replicas so that read traffic can be distributed across multiple database nodes.
Solution 3: CDN
For static or cacheable content such as images, JavaScript, CSS and videos, I would use a CDN to serve content closer to users.
New Challenges
Now I have to deal with cache invalidation, stale data and replication lag.
Key Question: Which data requires strong consistency and which data can tolerate eventual consistency?
Future Challenge
Read scalability is improved, but eventually database writes or total data volume may become the bottleneck.
🔀 Stage 4: 100K → 1M Users
▼
Focus
Asynchronous Processing + Queue + Database Scaling + Rate Limiting
Problem 1: Database Write Bottleneck
Read replicas primarily help with reads. If write traffic becomes too high for a single database, I need to scale the write side.
Solution: Depending on the workload:
  • Partitioning
  • Sharding
  • Database optimization
Problem 2: Synchronous Processing
Suppose an order request synchronously calls payment, inventory, notification, analytics and shipping. The user has to wait for all these operations, and one slow dependency can increase the overall latency.
Solution: I would move non-critical operations to asynchronous processing using queues or event streaming.
Order Created → Queue/Event → Notification / Analytics / Email
This provides:
  • Decoupling
  • Better scalability
  • Failure isolation
Problem 3: Traffic Spikes
A sudden traffic spike can overwhelm the application or database.
Solution: Rate limiting, throttling, backpressure, and queue buffering protect the system from overload.
Problem 4: Regional Failure
If the business requires very high availability, a single geographical region can become a single point of failure.
Solution: Introduce multi-region architecture with appropriate data replication and traffic routing.
New Challenge
Now the system becomes distributed, so I have to deal with eventual consistency, distributed transactions, network failures and more operational complexity.
🌐 Stage 5: 1M+ Users
▼
Focus
Independently Scalable Distributed Architecture
Problem
At this scale, different parts of the system have completely different traffic and scaling requirements.
Product → 1M reads/sec Payment → 10K requests/sec Notification → 500K events/sec
Scaling the entire system together would be inefficient.
Solution
I would decompose the system into independently scalable business services where there is a clear business and scaling boundary.
Product Service Order Service Payment Service Inventory Service Notification Service
Each Service Can Have
  • Independent scaling
  • Independent deployment
  • Appropriate database/storage
  • Appropriate caching
  • Appropriate communication pattern
For Extremely Large Datasets or Throughput
Use partitioning/sharding and distribute workloads appropriately.
For High Availability
Use multi-region architecture where justified by business requirements.
What is Sharding and why would you use it?
▼
Opening Answer: "I would consider sharding when a single database has reached its scalability limits, either because of data volume, read/write throughput, storage capacity, or hardware limitations. Instead of keeping the entire dataset on one database node, I divide the data into smaller partitions and distribute them across multiple nodes."
1️⃣ First Problem — Database Becomes Too Large
▼
Scenario
Imagine we have 1 billion users and all users are stored in one database.
Over Time Problems
  • Storage becomes huge
  • Indexes become large
  • Queries become slower
  • Backup/restore becomes expensive
  • Hardware has a physical limit
Solution
Split the data across multiple shards.
Shard 1 → Users 1–250M Shard 2 → Users 250M–500M Shard 3 → Users 500M–750M Shard 4 → Users 750M–1B
Now each database handles only a portion of the data.
2️⃣ Second Problem — Database Throughput
▼
The Issue
This is actually one of the most important reasons for sharding.
One database can handle: 20K writes/sec Application needs: 80K writes/sec
Why Adding More App Servers Doesn't Help
Application 1 Application 2 Application 3 Application 4 ↓ Same Database
The database remains the bottleneck.
Solution
Distribute writes across multiple shards.
Application ↓ Shard Router ↙ ↓ ↓ ↘ Shard 1, 2, 3, 4
Now the workload can be distributed.
3️⃣ How Does the System Decide Where Data Goes?
▼
Shard Key
We need a Shard Key to determine where the record belongs.
Example
user_id → Shard User 101 → Shard 1 User 250,001 → Shard 2 User 500,001 → Shard 3
Other Possible Shard Keys
  • User ID
  • Tenant ID
  • Region
  • Customer ID
⚠️ Very Important
Shard-key selection is one of the most important decisions in sharding.
4️⃣ Real-World Example — Banking 🏦
▼
Scenario
A bank has 500 million customers. Instead of keeping all customer data on one database cluster, distribute customers across multiple database partitions.
Shard Strategy
Based on Customer ID or region:
Shard 1 → Customers A–F Shard 2 → Customers G–L Shard 3 → Customers M–R Shard 4 → Customers S–Z
Benefit
A query for a customer can go directly to the relevant shard.
5️⃣ Real-World Example — E-commerce 🛒
▼
Scenario
An e-commerce platform with 1 billion orders.
Distribution Strategy
You could distribute orders by:
  • customer_id
  • order_id
  • Another business-appropriate key
Example
Shard 1 → Customers 1–10M Shard 2 → Customers 10M–20M ... and so on
Result
The order database doesn't have to handle the entire billion-order dataset on one node.
6️⃣ What Problems Does Sharding Solve?
▼
Problem → Solution Mapping
Database too large → Split data across nodes Database write bottleneck → Distribute writes Database storage limit → Distribute storage Database CPU/I/O bottleneck → Distribute workload Large dataset causing query/maintenance problems → Smaller datasets per shard
Main Goal
Horizontal scalability of the data layer.
7️⃣ But Sharding Creates New Problems
▼
Important Note
This is where an architect-level answer becomes important. You don't just say "I'll use sharding." You need to explain the trade-offs.
Challenge 1 — Bad Shard Key
▼
The Problem
Suppose you shard based on Country. If 70% of customers are from India:
India → 70% of data Other countries → 30%
Now one shard becomes overloaded. This is called a Hot shard.
Solution
Choose a shard key that distributes workload more evenly:
  • User ID
  • Hash-based distribution
  • Composite key
Challenge 2 — Cross-Shard Queries
▼
The Problem
Data exists across multiple shards. User asks: "Give me all customers whose spending is greater than ₹1M."
Query Shard 1 Query Shard 2 Query Shard 3 ↓ Merge results
Impact
  • Increased latency
  • More network traffic
  • Increased application complexity
Best Practice
Design queries around the shard key whenever possible.
Challenge 3 — Cross-Shard Transactions
▼
The Problem (One of the Biggest)
Account A is on Shard 1, Account B is on Shard 2. You want to transfer ₹10,000 from A to B.
Debit A (Shard 1) AND Credit B (Shard 2)
But they're on different shards. A normal local database transaction doesn't easily cover both.
This Can Lead To
  • Distributed transaction / consistency problems
Solution Approaches
  • Saga pattern
  • Distributed transaction coordination
  • Careful transaction design
Challenge 4 — Rebalancing
▼
The Problem
Initially data is balanced, but over time it becomes unbalanced:
Initially: Shard 1 → 250M records Shard 2 → 250M Shard 3 → 250M Shard 4 → 250M Later: Shard 1 → 600M others → remain smaller
Result
Shard 1 becomes a bottleneck.
Solution Required
Rebalance / redistribute the data. But moving huge amounts of data is operationally expensive.
Challenge 5 — Operational Complexity
▼
Complexity Increases
With 1 database: - Backup → relatively straightforward With 50 shards: - Backup 50 databases
You Also Need to Think About
  • Monitoring
  • Failover
  • Schema changes
  • Backups
  • Data migration
  • Rebalancing
  • Disaster recovery
Bottom Line
Sharding increases operational complexity significantly.
8️⃣ Sharding vs Replication
▼
Important Interview Question
Understanding the difference is crucial.
Replication
Copies the same data to multiple nodes.
Primary → Replica 1 → Replica 2 → Replica 3
Purpose: Availability + read scalability
Sharding
Splits different data across nodes.
Shard 1 → Users A–F Shard 2 → Users G–L Shard 3 → Users M–R
Purpose: Data/storage + write/read scalability
Easy Way to Remember
Replication = same data, multiple copies Sharding = different data, multiple pieces
Combined Approach
They can be used together for both scalability and availability:
Shard 1 → Primary → Replica → Replica Shard 2 → Primary → Replica → Replica
9️⃣ When Would I Introduce Sharding?
▼
Important Principle
Don't shard just because you expect high traffic. Consider other approaches first.
Consider First
  • Query optimization
  • Proper indexing
  • Vertical scaling
  • Connection pooling
  • Caching
  • Read replicas
  • Partitioning
Consider Sharding Only If Database Reaches
  • CPU limits
  • Storage limits
  • I/O limits
  • Write throughput limits
🔟 Your Interview Answer
▼
If Asked: "How would you scale your database?"
"I would first optimize queries and indexes and consider vertical scaling. If the workload is read-heavy, I would introduce read replicas and caching. If the dataset or write workload becomes too large for a single database node, I would consider sharding. With sharding, I would partition the data based on an appropriate shard key so that storage and workload are distributed across multiple nodes. However, I would carefully design the shard key to avoid hot shards and consider the impact on cross-shard queries, transactions and rebalancing. I would avoid sharding prematurely because it significantly increases operational and application complexity."
Why This is Strong
You demonstrate understanding of:
  • Progressive scaling approach
  • Multiple scaling techniques
  • Sharding trade-offs
  • Architect-level thinking
  • Pragmatic decision-making
What is Sharding and when would you use it?
▼
Opening Statement: "Sharding is a database scaling technique where we split a large dataset into smaller parts and distribute those parts across multiple database nodes. I would consider it when a single database can no longer handle the required data volume or read/write workload."
1️⃣ Problem — Single Database Becomes a Bottleneck
▼
Problem Statement
As the application grows, the database may become the bottleneck because of increasing data volume, CPU, I/O, storage or read/write throughput.
Example
Application → Single Database As traffic increases: Database → CPU/IO/Storage limit
Solution
Instead of putting all the data on one database node, distribute the data across multiple database nodes using sharding.
Application → Shard Router → Shard 1 / Shard 2 / Shard 3
Benefits
  • Distribute storage
  • Distribute workload
  • Scale horizontally
  • Reduce pressure on a single database
Future Challenge
Once you distribute the data, the system now needs to know which shard contains a particular record.
2️⃣ Problem — Where Should Data Go?
▼
Problem Statement
The system needs a consistent way to decide which shard should store each record.
Solution
Select an appropriate shard key, such as user_id, tenant_id or region, and use it to determine the target shard.
User ID → Shard
Challenge
A poor shard key can create uneven distribution and produce a hot shard. For example, one shard receives 70% of the traffic while others remain underutilized.
Solution for Hot Shard
Choose a high-cardinality and well-distributed shard key, and depending on the workload, use techniques such as hashing.
3️⃣ Problem — Cross-Shard Queries
▼
Problem Statement
Once data is distributed, some queries may require data from multiple shards.
Example: "Find all customers whose spending is greater than ₹1M." Customers exist across: Shard 1 + Shard 2 + Shard 3
Solution
Design important queries around the shard key whenever possible. For queries that genuinely require multiple shards, query multiple shards and aggregate the results.
Challenge
Cross-shard queries increase network calls, latency and application complexity.
4️⃣ Problem — Cross-Shard Transactions
▼
Problem Statement
A business transaction may sometimes involve data stored on different shards.
Account A → Shard 1 Account B → Shard 2 Transfer money: Debit A + Credit B
Solution
Avoid cross-shard transactions where possible by designing the data model appropriately. If a distributed business transaction is unavoidable, use patterns such as Saga and compensating transactions.
Challenge
Maintaining strong consistency across multiple shards becomes much more complex.
5️⃣ Problem — Shard Growth / Rebalancing
▼
Problem Statement
Over time, some shards may become much larger or busier than others.
Shard 1 → 500 GB Shard 2 → 100 GB Shard 3 → 100 GB
Solution
Rebalance or redistribute data across shards.
Challenge
Moving large amounts of data can be expensive and may require careful migration planning.
6️⃣ Problem — Operational Complexity
▼
Problem Statement
With one database, backup, monitoring, failover and schema management are relatively simple. With many shards, all these operations become more complex.
Solution
Automate shard management, monitoring, backup, failover and data migration as much as possible.
Challenge
The operational overhead increases significantly as the number of shards grows.
7️⃣ When Would I Actually Use Sharding?
▼
Decision Statement
I would not introduce sharding just because the application has high traffic.
I would first consider:
  • Query optimization
  • Indexing
  • Vertical scaling
  • Caching
  • Read replicas
Only if database reaches:
  • Storage limits
  • CPU/I/O limits
  • Write throughput limits
  • Data volume limits
Then:
Consider sharding.
Caching
▼
Opening Statement: "Caching is a technique where frequently accessed data is stored in a faster storage layer so that we don't repeatedly access the slower underlying system such as a database or external service."
1️⃣ Problem — Repeated Database Reads
▼
Problem Statement
When the same data is requested frequently, sending every request to the database increases database load and latency.
Users → Application → Database
Solution
Introduce a cache such as Redis between the application and database.
Users → Application → Cache → Database
Cache Flow
Request → Cache Hit → Return Data Request → Cache Miss → Database → Store in Cache → Return Data
Benefits
  • Lower latency
  • Lower database load
  • Higher throughput
Challenge
Now we have to deal with stale data and cache invalidation.
2️⃣ Problem — Stale Data
▼
Problem Statement
The database can change while the cache still contains the old value.
Database = ₹1,000 → Cache = ₹900
Solution: TTL — Time To Live
Cache entry automatically expires after a specified period.
Store Data → TTL = 5 min → Entry expires → Next request gets fresh data
Good when: Slightly stale data is acceptable.
Solution: Cache Eviction on Update
When data changes, explicitly remove the corresponding cache entry.
Update DB → Invalidate Cache → Next request → DB → Cache
Solution: Write-Through
Application writes to the cache, and the cache synchronously updates the underlying database.
Application → Cache → Database
Useful when: You want cache and database updates to happen together.
Solution: Write-Behind
Application updates the cache first, while the database is updated asynchronously later.
Application → Cache → Queue/Async → Database
Useful when: Write performance is more important and some delay in persistence is acceptable.
3️⃣ Problem — Cache Stampede
▼
Important Interview Topic
A very popular product is cached. When it expires, millions of requests miss simultaneously.
1M requests → Cache key expires → 1M cache misses → 1M requests hit DB
Your cache has actually created a database overload problem. This is called: Cache Stampede / Thundering Herd
Solution 1 — Request Coalescing
Multiple requests for the same missing data are combined so that only one request fetches the data.
Instead of: 1M requests → Cache Miss → 1M DB requests We want: 1M requests → Cache Miss → 1 DB request → Cache → 1M requests receive result
Other requests wait for the first request to populate the cache.
Solution 2 — Locking
Only one thread/process is allowed to rebuild a particular cache entry while others wait.
1M requests → Cache Miss → Acquire Lock → 1 request → DB → Cache → Release Lock Other requests: Cache Miss → Wait for Lock → Read newly cached value
This prevents hundreds/thousands of requests from simultaneously hitting the DB.
Solution 3 — Staggered TTLs
Give different cache entries slightly different expiration times so many entries don't expire at exactly the same moment.
Instead of: 1M keys → TTL = exactly 10 min → All expire together Use: Key A → 9m 53s Key B → 10m 07s Key C → 9m 48s
This spreads cache misses over time. ⚠️ Note: This helps reduce mass expiration, but doesn't by itself solve a single extremely hot key expiring.
Solution 4 — Pre-warming
Load important/popular data into the cache before users request it.
Sale starts → Pre-load popular products → Cache is already populated → Users request products
This avoids: Sale starts → Millions of requests → Cache Miss → Database overload
This is especially useful for predictable traffic spikes.
4️⃣ Problem — Cache Failure
▼
Problem Statement
If the cache becomes unavailable, requests may suddenly fall back to the database and overload it.
Cache Failure → Cache Misses → Database Traffic Spikes → Database Overload
Solution
Design the cache as a performance layer rather than the only source of truth.
Possible Protections
  • Cache replication
  • Distributed cache
  • Circuit breaker
  • Rate limiting
  • Database protection
Important Principle
The system should ideally remain functionally correct even if the cache is unavailable, although performance may degrade.
5️⃣ Problem — Limited Cache Memory
▼
Problem Statement
Cache memory is limited, so we cannot keep every piece of data forever.
Solution — Eviction Policies
LRU — Least Recently Used
Removes data that hasn't been accessed recently.
LFU — Least Frequently Used
Removes data that is accessed least frequently.
TTL-based
Removes data after its expiration time.
Example
Cache full → Eviction policy selects old/unpopular entry → Remove → Store new entry
Challenge
Poor eviction decisions can reduce the cache hit ratio and increase database traffic.
6️⃣ Problem — Multiple Application Instances
▼
Problem Scenario
Pod 1 → Local Cache Pod 2 → Local Cache Pod 3 → Local Cache
Each pod may have a different version of the data.
Solution
Use a shared distributed cache:
Pod 1 ─┐ Pod 2 ─┼→ Redis Pod 3 ─┘
Challenge
Now the cache itself becomes a distributed component that needs availability, replication, monitoring and capacity planning.
7️⃣ Cache-Aside — Common Pattern
▼
Pattern Overview
This is the caching pattern you should remember first.
Read Flow
Application → Cache Cache Hit → Return Cache Miss → Database → Store in Cache → Return
Write Flow
Application → Database → Invalidate Cache
Why This Pattern?
The application controls when data is loaded into and removed from the cache.
8️⃣ Final Interview Answer
▼
"I would introduce caching when repeated or expensive reads are causing database load or high latency. I would typically use Redis with a cache-aside strategy, where the application first checks the cache and falls back to the database on a cache miss. I would then consider cache invalidation and TTL for stale data. For high-traffic systems, I would protect against cache stampede using techniques such as request coalescing, locking, staggered TTLs and pre-warming. I would also consider cache eviction policies and design for cache failure so that the database remains the source of truth where required. In a distributed application, I would use a shared cache when data needs to be available consistently across instances."
9️⃣ Revision Bullets
▼
  • Problem: Repeated/expensive reads → DB load + latency
  • Solution: Faster storage layer → Redis
  • Flow: Cache Hit → return; Cache Miss → DB → Cache → return
  • Benefits: Lower latency + lower DB load
  • Stale Data: TTL / invalidation / write-through / write-behind
  • Cache Stampede: Many requests miss simultaneously → DB overload
  • Request Coalescing: Combine same requests → only one DB call
  • Locking: One request rebuilds cache → others wait
  • Staggered TTL: Spread expiration times → avoid mass expiration
  • Pre-warming: Populate cache before expected traffic
  • Eviction: LRU / LFU / TTL → manage limited memory
  • Failure: Cache down → DB fallback → protect DB
  • Distributed Apps: Shared cache → Redis
  • Common Pattern: Cache-Aside
How consistency solves?
▼
1️⃣ What is Consistency?
▼
Definition
Consistency defines how and when changes to data become visible to users and different components of a distributed system.
The Main Architectural Question
"After data is updated, when should other users, services, replicas, caches, or databases see the latest value?"
Why It Matters
Consistency becomes especially important when the same data exists in multiple places.
Application → Primary DB → Read Replica → Cache → Search Index All these components may temporarily have different versions of the same data.
2️⃣ Why Do We Need to Think About Consistency?
▼
Problem Statement
In a distributed system, data is often replicated or maintained by multiple components. When one copy is updated, the other copies may not immediately reflect the change.
Example
A user changes their address:
Primary DB → Mumbai But immediately afterward: Read Replica → Delhi
The system is temporarily inconsistent.
Challenge
We need to decide whether the business requires the latest value immediately or whether temporary stale data is acceptable.
3️⃣ Strong Consistency
▼
Problem Statement
Some business operations cannot tolerate stale data because using an old value can result in an incorrect or dangerous business outcome.
Example: Bank Account
Balance = ₹10,000 User withdraws: ₹8,000 After withdrawal succeeds, next read should return: ₹2,000 NOT the old balance of ₹10,000
Solution
Strong consistency ensures that after a successful write, subsequent reads see the latest committed value.
Write ₹8,000 → Write completes → Read → ₹2,000
Where Would I Use It?
  • Payment transactions
  • Bank account balances
  • Financial transactions
  • Critical inventory operations (prevent overselling)
  • Operations involving important business invariants
Challenge
Strong consistency usually requires more coordination between components, which can increase latency and may reduce availability during certain failures.
4️⃣ Eventual Consistency
▼
Problem Statement
Not every business operation requires all copies of data to be updated immediately. Requiring strong consistency everywhere can introduce unnecessary coordination and reduce scalability.
Example: Social Media
A user uploads a post. It may take a short time to appear in:
  • Followers' feeds
  • Search results
  • Recommendation systems
  • Analytics
A small delay is usually acceptable.
Solution
Eventual consistency allows different copies of data to temporarily contain different values, with the expectation that they will eventually converge if no new updates occur.
Write → Primary DB → Event/Replication → Read Model → Eventually Updated
Where Would I Use It?
  • Social media feeds
  • Product catalogues
  • Recommendations
  • Analytics
  • Search indexes
  • Likes/views
  • Notifications
  • Non-critical reporting
Benefit
Eventual consistency allows systems to reduce coordination between components and can improve scalability, latency and availability.
Challenge
Users or services may temporarily see stale data.
5️⃣ Consistency Between Database and Cache
▼
Important Example
This is important because we discussed caching earlier. When data exists in both database and cache, an update to the database can temporarily leave the cache with an outdated value.
Problem Statement
Database → Price = ₹1,000 Redis → Price = ₹900
The user reads from Redis and receives ₹900 even though the actual database value is ₹1,000.
Solution
Depending on the consistency requirement, we can use:
Update DB → Invalidate Cache → Next read → DB → Cache
Or use strategies such as: Write-through, Write-behind, TTL, Explicit cache invalidation
Challenge
Cache invalidation becomes difficult when data changes frequently or multiple services can modify the same data.
6️⃣ Consistency in Microservices
▼
Problem Statement
In microservices, different services often own different databases. One business operation can change data across multiple independent systems.
Example: Order Processing
Order Service → Order DB Payment Service → Payment DB Inventory Service → Inventory DB Customer places order: Order → Created Payment → Pending Inventory → Pending Then: Payment → Success Inventory → Reserved Order → Confirmed
There can be a period where different services have different states.
Solution
For workflows where immediate global consistency is not required, services can communicate through events and eventually synchronize their state.
Order Created → Event → Payment Payment Success → Event → Inventory Inventory Reserved → Event → Order
Challenge
This introduces distributed-system problems:
  • Duplicate events
  • Out-of-order events
  • Failed message delivery
  • Retries
  • Partial failures
  • Temporary inconsistent states
Supporting Patterns
  • Idempotency → safely handle duplicate messages
  • Transactional Outbox → reliably publish events
  • Saga → manage distributed business transactions
  • Retry → handle temporary failures
7️⃣ Strong vs Eventual Consistency
▼
Comparison Table
Strong Consistency Eventual Consistency Data visibility: Latest immediately May be temporarily stale Coordination: Higher Lower Latency: Can be higher Usually lower Scalability: More difficult Generally easier Availability in failure: Affected by coordination Often easier to maintain Typical use: Payments, balances Feeds, analytics, recommendations
8️⃣ How Do I Decide Which One to Use?
▼
Architectural Principle
I would not decide based on technology first. Instead, I would ask:
"What happens if the user temporarily sees stale data?"
If Stale Data Can Cause:
  • Financial loss
  • Duplicate payment
  • Incorrect balance
  • Overselling
  • Violation of critical business rule
→ Prefer strong consistency
If Stale Data Only Causes:
  • Slightly outdated feed
  • Delayed search result
  • Delayed recommendation
  • Slightly outdated analytics
→ Eventual consistency may be acceptable
9️⃣ Consistency Is a Business Decision
▼
Important Architectural Principle
Consistency is not simply a database decision; it is a business requirement.
Example: E-Commerce System
Payment: Should be strongly consistent → Payment status must be accurate Product description: Few seconds of stale data acceptable → Description doesn't change often Product price: Depending on business rules, stronger consistency may be required → During checkout especially important Recommendation: Eventual consistency normally acceptable → Users expect some staleness
Key Insight
The same system can use different consistency requirements for different types of data.
🔟 Challenges with Eventual Consistency
▼
When Using Eventual Consistency, Design For:
Stale Data
A user may temporarily see an older value. This is expected behavior.
Duplicate Events
The same event may be delivered more than once, so consumers should be idempotent.
Out-of-Order Events
Events may arrive in a different order from when they were generated.
Partial Failure
One service may successfully process an update while another service fails.
Reconciliation
The system may need background processes to detect and correct inconsistent data.
Slowness and how to detect?
▼
1️⃣ What is Slowness?
▼
Opening Statement: "Slowness means the system is taking longer than the expected response time to process a request. As an architect, I would first identify where the latency is coming from before deciding on a solution."
Example
User → API → Application → Database → Response If response takes 5 seconds instead of expected 200 ms, identify which layer is responsible.
2️⃣ Problem — Application Is Taking Too Long
▼
Problem Statement
Application is receiving requests successfully, but processing time is high, resulting in poor user experience.
Request → Application → 5 sec → Response
Solution
Break down the request path and measure latency at each layer instead of assuming application itself is slow.
Investigate
  • Network latency
  • Application processing
  • Thread pool
  • Connection pool
  • Database
  • Cache
  • External services
  • Synchronous service calls
Challenge
Overall response time is often the result of multiple components, so identifying the actual bottleneck is the first challenge.
3️⃣ Problem — Slow Database Queries
▼
Problem Statement
Application may be waiting for the database to complete a slow query.
Request → Application → DB Query → 3 sec → Response
Investigate
  • Query execution time
  • Missing indexes
  • Full table scans
  • Expensive joins
  • Large result sets
  • Database CPU/I/O
  • Lock wait time
Solution
Optimize the query and indexing strategy.
Challenge
Optimizing one query may not be enough if the database itself is overloaded or there is contention between many queries.
Then may consider: Read replicas, Caching, Database scaling, Partitioning
4️⃣ Problem — Cache Misses
▼
Problem Statement
If frequently accessed data is not available in cache, application has to access the slower underlying database or service.
Request → Cache Miss → Database → Response
Solution
Analyze cache hit ratio and determine whether frequently accessed data should be cached.
Request → Cache Hit → Response
Challenge
Caching can introduce stale data and cache invalidation problems, so only cache data where consistency requirements allow it.
5️⃣ Problem — Thread Pool Exhaustion
▼
Problem Statement
Application may have enough CPU capacity, but all available threads may be busy waiting for slow operations.
100 requests → Thread Pool → Threads waiting for DB Eventually: New Request → No Available Thread → Wait → High Latency
Investigate
  • Thread pool size
  • Thread utilization
  • Thread waiting time
  • Blocking operations
  • Slow database calls
  • Slow external API calls
Consider
  • Optimizing blocking operations
  • Async processing where appropriate
  • Separating workloads using different thread pools
Challenge
Simply increasing thread pool is not always a solution because too many threads can increase context switching and resource consumption.
6️⃣ Problem — Connection Pool Exhaustion
▼
Problem Statement
Application may be waiting because all available database or external-service connections are already being used.
Request → Connection Pool → No Available Connection → Wait
Investigate
  • Active connections
  • Idle connections
  • Connection pool size
  • Connection acquisition time
  • Connection leaks
  • Slow queries holding connections
Challenge
Increasing connection pool blindly can overload the downstream database or service.
Connection-pool size should be designed based on: Application concurrency + downstream capacity
7️⃣ Problem — Slow External Service
▼
Problem Statement
Application may be waiting for another service or external API to respond.
Order Service → Payment Service → 4 sec
Even if Order Service is fast, overall request becomes slow.
Consider
  • Timeout
  • Retry where appropriate
  • Circuit breaker
  • Caching
  • Asynchronous processing
  • Parallel calls where dependencies are independent
Parallel Execution Example
Instead of: A → B → C Execute: A → B + C in parallel
Challenge
Retries can make the problem worse if downstream service is already overloaded.
Retries should be controlled using: Timeout, Backoff, Retry limits, Circuit breaker
8️⃣ Problem — Too Many Synchronous Service Calls
▼
Problem Statement
Request may need to call many downstream services synchronously, causing latency of overall request to increase.
API → Order → Payment → Inventory → Shipping → Notification The user waits for entire chain.
Solution
Identify which operations are actually required before responding to user and move non-critical operations to asynchronous processing.
Synchronous: Order → Payment → Response Asynchronous: Order Created → Event → Notification / Analytics / Email
Benefit
User receives response without waiting for non-critical operations.
Challenge
System now becomes eventually consistent and requires reliable event processing.
9️⃣ Problem — Network Latency
▼
Problem Statement
Application may be fast, but communication between geographically distant or multiple services can add significant network latency.
Service A → Region 1 ↓ Service B → Region 2 Every network call adds latency.
Consider
  • Keeping frequently communicating services geographically close
  • Reducing unnecessary network calls
  • Batching requests
  • Caching
  • CDN where applicable
  • Parallel calls where possible
Challenge
Reducing network calls can sometimes increase payload size or application complexity, so trade-offs need to be evaluated.
🔟 Problem — Queue Backlog
▼
Problem Statement
In asynchronous system, consumers may process messages slower than producers are generating them.
Producer → Queue → Consumer If: Producer = 10K messages/sec but: Consumer = 5K messages/sec Then: Queue → Growing backlog → Increasing processing delay
Investigate
  • Consumer throughput
  • Number of consumers
  • Consumer processing time
  • Partitioning
  • Consumer concurrency
Solution
Scale consumers where possible.
Challenge
Adding consumers does not always help if downstream database or service is already the bottleneck.
1️⃣1️⃣ How I Would Diagnose Slowness
▼
Architectural Principle
I would NOT immediately say: "Increase CPU."
I would FIRST identify where the latency is coming from.
Application Layer
  • Response time
  • p50, p95, p99
Thread Pool
  • CPU usage
Database
  • Query execution time
  • Connection pool
  • Lock wait time
  • CPU/I/O
Cache
  • Hit ratio
  • Cache latency
  • Eviction rate
External Services
  • Response time
  • Timeout rate
  • Error rate
Infrastructure
  • Network latency
  • Packet loss
  • CPU
  • Memory
Distributed System
  • Queue backlog
  • Consumer lag
  • Service-to-service latency
1️⃣2️⃣ Important Metrics
▼
p50 — Median Response Time
p50 represents the median response time. 50% of requests are faster than this value.
Example: p50 = 100 ms means half of requests complete within approximately 100 ms.
p95 — 95th Percentile
p95 represents response time below which 95% of requests complete.
Example: p95 = 500 ms means 95% of requests complete within 500 ms, while slowest 5% take longer.
p99 — 99th Percentile (Tail Latency)
p99 represents response time below which 99% of requests complete. It helps identify tail latency.
Example: p50 = 100 ms p95 = 300 ms p99 = 2 sec Most users are fast, but a small percentage are experiencing severe slowness.
Why These Percentiles Matter
Understanding percentiles helps identify: Normal performance, User experience variance, Outlier behavior, System degradation patterns
What Are Microservices?
▼
Opening Statement: "Microservices is an architectural approach where a large application is divided into smaller, independently deployable services, with each service responsible for a specific business capability."
Example: An e-commerce system could have:
Product Service | Order Service | Payment Service | Inventory Service | Notification Service
Each service can potentially have its own: Codebase, Database, Deployment, Scaling, Team ownership
1️⃣ Why Do We Need Microservices?
▼
Problem — Monolith Becomes Too Large
Initially good starting point:
Client → Monolithic Application → Database
But as business grows, application contains: Product, Order, Payment, Inventory, Customer, Notification, Reporting all in same application.
Challenge
As monolith grows, development, deployment, scaling and maintenance become increasingly difficult.
Payment team changes payment code → entire application needs to be deployed.
Solution
Split application around business capabilities so individual parts can evolve independently.
Client → API → Product Service → Order Service → Payment Service → Inventory Service
2️⃣ Problem — Independent Scaling
▼
Scenario
Product Service → 1M requests/sec Payment Service → 10K requests/sec
With Monolith
Entire Application → Scale everything This is inefficient.
Solution: Microservices
Product Service → 20 instances Payment Service → 3 instances Notification Service → 5 instances
Each service scales independently according to its workload.
Challenge
Multiple services communicate over network instead of simple in-process calls. This introduces network failures and latency.
3️⃣ Problem — Independent Deployment
▼
Problem Statement
In large monolith, small change in one module may require deploying entire application.
Notification team changes email logic → entire monolith deployed.
Solution: Microservices
Notification Service → Deploy independently Payment Service → Deploy independently Order Service → Deploy independently
Benefit
Teams can release services independently without waiting for entire application.
Challenge
Need deployment automation, service versioning and backward compatibility between services.
4️⃣ Problem — Team Scalability
▼
Problem Statement
As organization grows, many teams working on same codebase create coordination and ownership problems.
Solution
Align services with business capabilities and give teams clear ownership.
Payment Team → Payment Service Order Team → Order Service Inventory Team → Inventory Service
Benefits
  • Develop independently
  • Deploy independently
  • Own their services
Challenge
Distributed ownership can create inconsistent standards and duplicated functionality if governance is poor.
5️⃣ Problem — Database Coupling
▼
In Monolith
Order → Database Payment → Same Database Inventory → Same Database Any module can potentially access another module's tables.
Problem
This creates tight coupling because changes to one part of database can affect multiple modules.
Solution: Database per Service
Order Service → Order DB Payment Service → Payment DB Inventory Service → Inventory DB
Benefit
Each service owns its data.
Challenge
We lose simple database joins and local ACID transactions across entire application.
Now need to deal with: Distributed transactions, Data consistency, Eventual consistency
Patterns: Saga, CQRS, Transactional Outbox
6️⃣ Problem — Service-to-Service Communication
▼
Overview
Services need to communicate.
Order → Payment Order → Inventory
Synchronous Communication
Order → REST/gRPC → Payment
Order Service waits for response. Good when: Immediate response is required.
Asynchronous Communication
Order → Event → Kafka/RabbitMQ → Payment
Order Service doesn't need to wait for consumer. Good when: Processing can happen asynchronously.
Challenge
Must handle: Network failures, Timeout, Retries, Duplicate messages, Message ordering, Eventual consistency
Patterns: Retry, Circuit Breaker, Timeout, Idempotency, Saga
7️⃣ Problem — Too Many Services
▼
Scale Problem
Once we introduce microservices, we may end up with 100+ services. System becomes difficult to manage.
Problem
"How does one service find another service?"
Solution: Service Discovery
Order Service → Service Discovery → Payment Service
Instead of hardcoding: payment-service-ip = 10.x.x.x
Challenge
Service discovery itself becomes part of distributed system and requires availability and monitoring.
8️⃣ Problem — Clients Need to Call Many Services
▼
Scenario
Frontend needs: Product, Price, Inventory, Reviews Calling every service directly can become complicated.
Solution — API Gateway
Client → API Gateway → Services
Gateway Can Provide
  • Routing
  • Authentication
  • Rate limiting
  • Request aggregation
  • API policies
Challenge
Gateway can become bottleneck or single point of failure if poorly designed.
9️⃣ Problem — Different Clients Need Different APIs
▼
Scenario
We have: Web Application, Mobile Application, Smart TV Each requires different data.
Solution — BFF (Backend for Frontend)
Web → Web BFF → Services Mobile → Mobile BFF → Services
Benefit
Each client gets API designed for its requirements.
🔟 Problem — Service Failures & Resilience
▼
Problem
If one service becomes slow or fails, it can cascade failures.
Order → Recommendation Service Recommendation Slow → Order Slow → Client Slow
Resilience Patterns
  • Timeout: Stop waiting after defined period
  • Retry: Try operation again for temporary failures
  • Circuit Breaker: Stop sending requests to failing service
  • Bulkhead: Isolate resources so one dependency doesn't consume all
  • Fallback: Return alternative response on failure
1️⃣1️⃣ Problem — Distributed Transactions
▼
Challenge
Order succeeds → Payment succeeds → Inventory fails. Now what?
Solution — Saga Pattern
Breaks distributed transaction into sequence of local transactions with compensating actions on failure.
Create Order → Payment → Reserve Inventory If inventory fails: Cancel Payment → Cancel Order
Implementation
  • Orchestration
  • Choreography
1️⃣2️⃣ Problem — Data Consistency in Microservices
▼
Issue
Because each service owns its database, they may temporarily contain different states.
Order DB ≠ Payment DB ≠ Inventory DB
Solution
  • Eventual Consistency
  • Events
  • Transactional Outbox
  • Saga pattern
  • Idempotency
Challenge
System becomes more complex because data is no longer immediately consistent everywhere.
1️⃣3️⃣ Problem — Synchronous Call Chains
▼
Issue
Client → Order → Payment → Inventory → Shipping → Notification Every service waiting for another service. Latency increases, one slow dependency slows entire chain.
Solution: Async Processing
Order Created → Event → Notification Order Created → Event → Analytics User doesn't need to wait for these operations.
1️⃣4️⃣ Problem — Monitoring & Observability
▼
In Monolith
Request → Application → DB Relatively easy to trace.
In Microservices
Client → Gateway → Order → Payment → Inventory → Kafka → Notification Request crosses many services.
Solution
  • Distributed Tracing + Centralized Logging + Metrics
  • Know where request went
  • Which service was slow
  • Where did it fail
  • Which service generated error
Challenge
Observability becomes essential—failures occur across multiple independent components.
1️⃣5️⃣ Problem — Deployment Complexity
▼
Scale
Single Application: Deploy one application 50 Services: Deploy 50 services
Solution
  • CI/CD
  • Containers
  • Orchestration
  • Automated deployment
  • Health checks
  • Auto-scaling
Tool
At larger scale, platform like Kubernetes helps manage workloads.

▼

1️⃣7️⃣ The Overall Evolution
▼
Most Important: Progressive Problem-Solving
Simple Monolith → Growing Monolith → Scaling Problem → Decompose by Business Capability → Multiple Services Then new problems appear: Multiple Services → Communication → REST/Messaging Multiple Databases → Consistency → Saga/CQRS/Outbox Network Failures → Resilience → Timeout/Retry/Circuit Breaker Many Services → Discovery → Service Discovery Many Client Calls → API → Gateway/BFF Many Services → Observability → Metrics/Logs/Tracing Many Deployments → Operations → CI/CD/Containers/Orchestration
1️⃣8️⃣ Final Interview Answer
▼
"I would not introduce microservices simply because the application is growing. I would first identify the problems that the monolith is creating. As the system grows, we may face problems such as independent scaling, deployment coupling, team ownership and database coupling. At that point, I would consider decomposing the system around business capabilities into independently deployable services. However, microservices solve some problems while creating new distributed-system problems. Services communicate over network, databases are distributed, and failures occur independently. Therefore, I would introduce appropriate patterns such as API Gateway and service discovery for communication, database-per-service and Saga for data management, and timeout, retry, circuit breaker and bulkhead for resilience. At larger scale, I would also need asynchronous messaging, observability, CI/CD and appropriate deployment strategies. So I see microservices not as a technology decision, but as a response to specific scaling, organizational and deployment problems."

▼
  • Problem: Growing monolith → scaling, deployment, ownership, coupling
  • Solution: Decompose around business capabilities
  • New Problem: Network communication → REST/gRPC/Messaging
  • New Problem: Distributed data → Database per Service + Eventual Consistency
  • New Problem: Distributed transactions → Saga
  • New Problem: Reliability → Timeout + Retry + Circuit Breaker + Bulkhead
  • New Problem: Service discovery → Service Discovery
  • New Problem: Client complexity → API Gateway/BFF
  • New Problem: Async consistency → Events + Outbox + Idempotency
  • New Problem: Observability → Metrics + Logs + Tracing
  • New Problem: Deployment → CI/CD + Containers + Orchestration
  • Principle: Don't introduce microservices because popular; introduce when problems justify complexity
Concurrency
▼
Opening Statement: "Concurrency means that a system is handling multiple operations during the same period of time. In a real-world system, thousands of users may send requests at almost the same time. The challenge is not simply to process all requests concurrently. The real challenge is: How do we allow concurrent operations while making sure they do not interfere with each other, corrupt data, or overload the system?"
Example Problem:
Product Stock = 1 Two users request the product at almost the same time: User A → Buy Product User B → Buy Product Both requests may read: Stock = 1 If concurrency not handled correctly, both could succeed even though only one product exists.
1️⃣ Race Condition
▼
Definition
Race condition occurs when multiple operations access or modify same resource concurrently, and final result depends on timing or ordering of those operations.
Example
Balance = ₹1,000 Two requests arrive: Request A → Withdraw ₹800 Request B → Withdraw ₹800 Both read: Balance = ₹1,000 Both may approve the withdrawal → Incorrect balance
Solution Approaches
  • Database locking
  • Optimistic locking
  • Atomic operations
  • Distributed locking
  • Queue-based serialization
2️⃣ Atomic Operations
▼
Problem
Simple operations are implemented as multiple steps: read, modify and write.
Read Counter = 100 → Add 1 → Write 101
If executed simultaneously, some updates can be lost.
Solution
Make entire state change an atomic operation—happens as one indivisible action.
Instead of: Read → Modify → Write Use: INCREMENT → Done Counter = 100 → Request A INCREMENT + Request B INCREMENT → Counter = 102
Example: Inventory
Instead of: Read Stock → Check Stock → Reduce Stock → Write Stock Perform atomic conditional update: Check Stock > 0 + Reduce Stock → One Atomic Operation
When to Use
Atomic operations ideal for: counters, increments, decrements, conditional state changes
Challenge
Excellent for small state changes but insufficient for complex multi-step business transactions.
3️⃣ Optimistic Locking
▼
Principle
Conflicts are relatively rare, so locking every request reduces performance unnecessarily.
Solution
Allow multiple requests to work concurrently. Check whether another request modified data before committing.
Usually maintain a version number.
Example Flow
Initial: Stock = 10, Version = 5 Request A and B both read: Version 5 A updates: Stock = 9, Version = 6 B tries update using: Version = 5 Database detects: Current Version = 6 Result: B → Update Failed
When to Use
Use when conflicts are rare and we want higher concurrency without holding database locks.
Challenge
Application must handle failed update, usually through retry or returning conflict to user.
4️⃣ Database Locking
▼
When Needed
When multiple transactions frequently modify same database record, need to prevent simultaneous modification.
Solution
One transaction locks required data during operation. Other transactions wait until lock released.
Request A → Lock Row → Read → Update → Commit → Release Lock Request B → Wait for Lock → Read Latest Value → Update
Example: Inventory
Stock = 1 Request A → Lock → Reduce Stock to 0 → Commit → Release Request B → Wait → Read Stock = 0 → Reject
When to Use
Use when conflicts are frequent and correctness is more important than maximum concurrency.
Challenge
Excessive locking creates lock contention, increases latency and potentially causes deadlocks.
5️⃣ Distributed Locking
▼
Problem
Local application lock only works inside one instance. In distributed system, multiple pods/servers may access same resource.
Pod 1 → Request A Pod 2 → Request B Java synchronized lock in Pod 1 cannot prevent Pod 2 from accessing resource.
Solution
Distributed lock coordinates access across multiple instances, ensuring only one owns resource at a time.
Pod 1 → Acquire Distributed Lock → Process → Release Lock Pod 2 → Try Lock → Lock Unavailable → Wait/Fail
Example: Scheduled Job
Without distributed locking (10 instances): Instance 1/2/3 → Execute Job Same job may execute multiple times With distributed locking: Instance 1 → Acquire Lock → Execute Job Instance 2/3 → Lock Unavailable → Skip
Technologies
  • Redis
  • Database
  • ZooKeeper
  • etcd
Challenge
Introduces problems: lock expiry, network failures, stale locks, ownership management
6️⃣ Queue-Based Serialization
▼
Approach
Instead of multiple requests modifying resource simultaneously, queue requests and process controlled manner.
Scenario
1,000 Requests → Inventory If all directly access database, create heavy contention.
Solution
1,000 Requests → Queue → Consumer Pool → Inventory DB Consumer pool controls concurrent inventory operations.
Example
Stock = 1 Customer A + Customer B → Queue → Inventory Consumer → Stock Update Consumer processes safely: Customer A → Stock = 0 Customer B → Out of Stock
When to Use
Use when operation can be async and controlled processing more important than immediate response.
Benefit
Queue absorbs traffic spikes and prevents requests from overwhelming downstream system.
Challenge
Processing becomes async, system becomes eventually consistent, user may not get immediate response.
7️⃣ Thread Pool & Connection Pool
▼
Thread Pool Problem
10,000 Requests → Application But application has only: 200 Worker Threads Remaining requests must wait.
Thread Pool Solution
Use bounded thread pool to control concurrent task execution.
10,000 Requests → Thread Pool → 200 Concurrent Tasks
Thread Pool Challenge
Too many threads cause: memory consumption, context switching overhead, CPU overhead
Connection Pool Problem
5,000 Requests → Application → Database But database can safely handle: 200 Connections
Connection Pool Solution
5,000 Requests → Connection Pool → 200 DB Connections Requests wait for available connection.
Connection Pool Challenge
Increasing pool without database capacity consideration simply moves bottleneck to database.
8️⃣ Bulkhead — Isolating Concurrent Workloads
▼
Problem
Different workloads share same resources. One workload can exhaust resources and prevent other important operations.
Payment Requests, Report Generation, Image Processing All use same thread pool: Report Generation → Consumes All Threads Payment Requests → Waiting
Solution
Use Bulkhead Pattern to isolate resources between workloads.
Payment → Payment Thread Pool Reports → Report Thread Pool Notifications → Notification Thread Pool
Benefit
If reports become slow, Report Thread Pool exhausted, but Payment Thread Pool still available.
When to Use
Use when different workloads have different priorities and one shouldn't exhaust resources needed by another.
Challenge
Resource isolation requires careful capacity planning because resources divided between workloads.
9️⃣ Problem — Concurrent Operations Need Ordering
▼
Problem
Concurrency creates problems when certain operations for same business entity must happen in specific order.
Payment Successful must happen BEFORE Order Confirmed Wrong order: Order Confirmed → Payment Successful System enters invalid state.
Solution
Preserve ordering where business requires it.
Order ID → Same Queue Partition → Events Processed in Order
Important Principle
Only enforce ordering where business requires it. Global ordering reduces scalability.
🔟 Concurrency in Distributed Systems
▼
Problem
Application runs on multiple instances. Local synchronization cannot coordinate operations across instances.
Pod 1 → Request A Pod 2 → Request B Pod 3 → Request C Each pod has its own JVM and memory. Java synchronized block in Pod 1 cannot protect resource from Pod 2.
Solutions by Problem Type
  • Database: Database Lock / Atomic Operation
  • Distributed: Distributed Lock
  • Async Work: Queue
  • Multiple Updates: Optimistic Locking
1️⃣1️⃣ Concurrency vs Parallelism
▼
Concurrency
Multiple tasks in progress during same period. Single CPU manages multiple tasks by switching between them.
Parallelism
Multiple tasks execute at same time, usually using multiple CPU cores.
CPU Core 1 → Task A CPU Core 2 → Task B CPU Core 3 → Task C
Easy Memory Trick
Concurrency = managing multiple tasks Parallelism = executing multiple tasks simultaneously
1️⃣2️⃣ How Do I Choose the Right Approach?
▼
First Question
"What exactly is the concurrency problem I am trying to solve?"
Decision Tree
  • Simple state update: Atomic Operation
  • Conflicts rare: Optimistic Locking
  • Conflicts frequent: Database Locking
  • Multiple instances need exclusive access: Distributed Locking
  • Operations can be async: Queue-Based Serialization
  • Too many requests in app: Thread Pool
  • Too many connections to downstream: Connection Pool
  • One workload consumes all resources: Bulkhead
1️⃣3️⃣ The Three Levels of Concurrency
▼
Level 1 — Data Concurrency
Question: "Multiple requests modifying same data. Maintain correctness?"
Use: Atomic Ops → Optimistic Locking → Database Locking → Distributed Locking
Level 2 — Application Concurrency
Question: "Too many requests executing in app. Control workload?"
Use: Thread Pool → Bounded Queue → Backpressure → Bulkhead
Level 3 — Distributed Concurrency
Question: "Multiple instances accessing same resource or process same work?"
Use: Distributed Lock → Queue → Partitioning → Idempotency → DB Concurrency
1️⃣4️⃣ Final Interview Answer
▼
"Concurrency means handling multiple operations during same period while maintaining correctness and controlling resource usage. The first problem I look for is race condition, where multiple requests modify same resource concurrently. Depending on use case, I can use atomic operations, optimistic locking, database locking, distributed locking or queue-based serialization. Concurrency is also resource-management problem. Too many concurrent requests can exhaust application threads or database connections, so I use bounded thread pools, connection pools, queues and bulkheads to control concurrency. In distributed system, local JVM locks insufficient because multiple instances may access same resource. In that case, consider distributed locks, atomic database operations or queue-based serialization. My goal is not to maximize concurrency. My goal is to allow as much safe concurrency as system and its dependencies can handle without compromising data correctness or system stability."
1️⃣5️⃣ Revision Notes
▼
  • Concurrency: Handling multiple operations during same period
  • Main Problem: Multiple operations can interfere with each other
  • Race Condition: Result depends on timing/ordering of concurrent operations
  • Atomic Operation: Make small state change indivisible
  • Optimistic Locking: Allow concurrency, detect conflict before saving
  • Database Locking: Lock shared data while transaction executes
  • Distributed Locking: Coordinate access across multiple instances
  • Queue Serialization: Put operations into controlled processing flow
  • Thread Pool: Controls concurrent work inside application
  • Connection Pool: Controls concurrent connections to external resources
  • Bulkhead: Separates resources so one workload cannot exhaust everything
  • Ordering: Preserve ordering only where business requirements need it
  • Distributed Systems: Local JVM locks cannot coordinate across instances
  • Concurrency ≠ Parallelism: Managing vs executing multiple tasks simultaneously
  • Goal: Controlled concurrency, not maximum concurrency

💡 Remember: Choose concurrency mechanism based on the specific problem you're solving, not based on maximizing throughput.

Controlled concurrency is better than maximum concurrent chaos!
