🧱 SOLID Principles
1
Overview▼

5 OOP design principles intended to make software more understandable, flexible, and maintainable.

S — Single Responsibility → one class, one role O — Open/Closed → extend, don't modify L — Liskov Substitution → child replaces parent safely I — Interface Segregation → smaller, specific interfaces D — Dependency Inversion → depend on abstractions
2
S — Single Responsibility Principle (SRP)▼

One class should have only one reason to change — one responsibility or job.

Example: A User class handles user data storage, but NOT email notifications. Email logic belongs in a separate NotificationService.

3
O — Open/Closed Principle (OCP)▼

Classes should be open for extension but closed for modification. Reuse existing code by extending behavior.

Example: Instead of modifying PaymentProcessor, create a new CreditCardPaymentProcessor class that extends it.

4
L — Liskov Substitution Principle (LSP)▼

A subclass should be able to replace its parent class without changing the correctness or expected behavior of the application.

If B IS-A A, then object of B should replace object of A without changing program behavior.

Example: A Rectangle should be substitutable for a Square. If replacing parent with child causes unexpected behavior, inheritance is incorrect and LSP is violated.

5
I — Interface Segregation Principle (ISP)▼

Create smaller, more specific interfaces rather than large, general-purpose ones. Clients should not be forced to implement methods they don't use.

Example: Separate AuthenticationInterface from UserManagementInterface.

6
D — Dependency Inversion Principle (DIP)▼

High-level modules should not depend on low-level modules — both should depend on abstractions.

Example: Inject a DatabaseConnection interface into a service class instead of directly instantiating a database connection object.

📏 DRY, KISS, YAGNI
1
DRY — Don't Repeat Yourself▼

Every piece of logic should have a single, unambiguous representation in your codebase.

❌ Bad

double calculateTaxForInvoice(double amount) { return amount * 0.18; } double calculateTaxForProduct(double amount) { return amount * 0.18; }

✅ Good

private static final double TAX_RATE = 0.18; double calculateTax(double amount) { return amount * TAX_RATE; }

In Spring: reuse services instead of duplicating logic in controllers.

2
KISS — Keep It Simple, Stupid▼

The simplest working solution is usually the best. Don't build generic frameworks for problems that don't exist yet. Avoid excessive abstraction layers. Simplicity reduces bugs and onboarding time.

❌ Overengineered

return Optional.ofNullable("Hello") .map(String::toUpperCase) .filter(s -> s.length() > 0) .orElseThrow(() -> new RuntimeException("Empty!"));

✅ Simple

return "HELLO";
3
YAGNI — You Aren't Gonna Need It▼

Don't add functionality until it's actually required by the business. Every line of code has a maintenance cost. Build iteratively — add when justified by a user story or metric.

Avoid speculative "future-proofing."

🔺 CAP Theorem
1
What is the CAP Theorem?▼

In a distributed system, you can only guarantee two out of three properties:

  • Consistency (C) — every read receives the most recent write
  • Availability (A) — every request receives a response (not guaranteed to be the latest)
  • Partition Tolerance (P) — the system continues to operate despite network partitions
Since network partitions are inevitable in distributed systems, the real choice is between CP (consistency + partition tolerance) and AP (availability + partition tolerance).

CP Systems

Banking, payment systems, stock trading — correctness over availability.

AP Systems

Social media (Facebook, Instagram, Twitter), DNS, Amazon product reviews — availability over strict consistency.
