01Virtualization Fundamentals
Virtualization → hypervisors → VM isolation → VM vs containers → advantages/disadvantages → HA → cloud → microservices.
1. What is Virtualization?

Virtualization is the abstraction of physical computing resources into logical/virtual resources. Instead of giving one physical server to one application, a hypervisor can divide the physical resources into multiple isolated Virtual Machines (VMs).

Physical Server → Hypervisor → VM1 | VM2 | VM3

Each VM behaves like an independent machine and can have its own: Operating System CPU allocation Memory Storage Network configuration Runtime Application

2. What Problem Does Virtualization Solve?

The fundamental problem is: Applications depend on their environment, not just their source code. For example, your application may require: Java 21 + Ubuntu + specific libraries + specific configuration But another server may have: Java 17 + different OS + different libraries This creates: "It works on my machine." Virtualization provides a consistent and isolated execution environment.

3. Main Problems Solved by Virtualization
  • 1. Environment inconsistency

Different machines may have different: OS versions Runtime versions Libraries Drivers Configurations VMs allow us to standardize the environment.

  • 2. Poor hardware utilization

Without virtualization, one application might use only 15–20% of a physical server.

Instead:
Server → VM1 + VM2 + VM3 + VM4

Multiple workloads can share the same physical resources. This improves resource utilization.

  • 3. Server consolidation
Previously:
Server1 → Application A
Server2 → Application B
Server3 → Application C
With virtualization:
Physical Server → Hypervisor → VM-A | VM-B | VM-C

Fewer physical servers may be required.

Benefits include:

Lower infrastructure cost Lower power consumption Less hardware Easier management

  • 4. Isolation

Applications can be isolated from each other.

VM-A → Application A
VM-B → Application B

If Application A crashes, it generally doesn't crash Application B. This provides fault isolation. Virtualization also provides an important security boundary, although additional security controls are still required.

  • 5. Faster provisioning

Physical server provisioning can involve:

Hardware → OS → Network → Libraries → Application
With virtualization:
VM Template/Image → New VM → Application

This makes creating new environments much faster.

  • 6. Portability

A VM can be represented by an image containing the OS and configured environment. That image can potentially be deployed to another compatible virtualization platform. This makes workloads more portable than applications tightly coupled to one physical server.

4. What is a Hypervisor?

A hypervisor is the software layer responsible for creating and managing VMs. It controls access to: CPU Memory Storage Network Other hardware resources

Conceptually:
Hardware → Hypervisor → Virtual Machines

The hypervisor makes the physical resources appear as virtual hardware to each VM.

5. Types of Hypervisors
Type 1 — Bare-Metal Hypervisor

Runs directly on physical hardware.

Hardware → Hypervisor → VMs

Examples include: VMware ESXi Microsoft Hyper-V Xen Characteristics Better performance Common in data centers Designed for server virtualization Less dependency on a host operating system

Type 2 — Hosted Hypervisor

Runs on top of an existing operating system.

Hardware → Host OS → Hypervisor → VM

Examples: VirtualBox VMware Workstation Parallels Desktop

Commonly used for:

Development Testing Learning Running another OS on a personal machine

6. VM Isolation

Each VM gets virtualized resources.

For example:
Physical Server → Hypervisor → VM1: 4 CPU / 8 GB | VM2: 2 CPU / 4 GB

The hypervisor manages these resources. This means applications don't directly control the physical hardware.

7. Does a VM contain a complete Operating System?

Yes. This is one of the major differences between VMs and containers. A VM normally contains:

VM → Guest OS → Runtime → Application
For example:
VM → Ubuntu → Java 21 → Spring Boot Application

Therefore VMs consume more resources than containers because each VM typically requires its own guest OS.

8. Virtualization vs Containerization

This is a very common interview question. Virtual Machine

Hardware → Hypervisor → VM → Guest OS → Application

Container

Hardware → Host OS → Container Runtime → Container → Application

Containers share the host OS kernel. Therefore: VM Heavier More resource consumption Slower startup Stronger machine-level isolation Can run different operating systems Container Lightweight Fast startup Higher workload density Shares host kernel Excellent for microservices

9. Advantages of Virtualization
1. Better resource utilization

Multiple applications can share one physical server.

2. Isolation

Failure of one VM generally doesn't directly affect another VM.

3. Server consolidation

Fewer physical servers may be required.

4. Faster provisioning

VMs can be created from templates/images.

5. Scalability

New VM instances can be provisioned when required.

6. Portability

VM images can be moved between compatible environments.

7. Disaster recovery

VM images and snapshots can simplify backup/recovery strategies.

8. Support for different OS environments

The same physical host can run: Linux VM | Windows VM | Linux VM

10. Disadvantages of Virtualization
1. Resource overhead

Every VM generally needs its own guest OS.

For example:
VM1 → OS
VM2 → OS
VM3 → OS

This consumes memory, CPU and storage.

2. Performance overhead

Modern hypervisors are highly optimized, so overhead can be relatively small, but virtualization still introduces an additional abstraction layer. For extremely latency-sensitive workloads, this can matter.

3. Operational complexity

You now need to manage: Hypervisor VMs Guest OS OS patches VM images Networking Storage Monitoring

4. VM Sprawl

Because VMs are easy to create, organizations can end up with hundreds or thousands of VMs. This creates: Patch-management problems Security risks Unused resources Higher costs Operational complexity

5. Host failure can affect multiple VMs

Suppose:

Physical Host → VM1 | VM2 | VM3

If the physical host fails, all those VMs may become unavailable. Therefore production environments need: Multiple physical hosts Clustering Replication Failover Live migration where appropriate

11. Virtualization and High Availability

Virtualization alone does not provide high availability. You need multiple physical hosts.

Host-1 → VM1 | VM2
Host-2 → VM3 | VM4
Host-3 → VM5 | VM6

If Host-1 fails, workloads can potentially be restarted or migrated to another host. This is an important distinction: Virtualization provides abstraction and isolation. High availability requires additional infrastructure and orchestration.

12. Virtualization and Cloud Computing

Virtualization is one of the foundational technologies behind cloud computing. A cloud provider can have:

Physical Infrastructure → Virtualization → Customer VMs

Instead of dedicating an entire physical server to one customer, the provider can allocate virtual resources. This enables: Multi-tenancy Elastic provisioning Resource allocation Infrastructure sharing Rapid scaling This is one reason cloud providers can offer infrastructure on demand.

13. Virtualization and Microservices

Virtualization isn't the same thing as microservices. You could have:

VM → Monolithic Application

or:

VM → Multiple Containers → Microservices

Modern platforms often use both:

Physical Server → VM → Kubernetes Node → Containers → Microservices

Here: VM provides infrastructure isolation. Container packages the application. Kubernetes orchestrates containers.

Distributed System — Use Cases & Interview Q&A
1. Why deploy an application in multiple regions?
Question
Why would you deploy the same application in multiple continents?
Answer

To reduce latency for geographically distributed users, improve availability, provide disaster recovery, and potentially meet data-residency requirements.

Users ──► Global Routing ──► US / EU / Asia Regions
2. Multiple instances in ONE region
Question
I have one application and 5 instances. What do I use?
Client ──► ALB ──► App1 / App2 / App3 / App4 / App5
Answer

Use a load balancer to distribute traffic across healthy instances.

This provides:

Horizontal scalability High availability Health checks Traffic distribution

3. Multiple services in ONE region
Question
I have Order, Product and Payment services. What should I use?
Client ──► Gateway ──► Order / Product / Payment
Answer

Use an API Gateway as a single entry point for client-facing APIs. The Gateway can provide: Authentication Authorization Rate limiting Routing API versioning

4. Multiple services + multiple instances
Question
I have multiple microservices, and each service has multiple instances. What architecture would you use?
Client ──► Gateway ──► Order LB ──► O1 / O2 / O3
├─► Product LB ─► P1 / P2 / P3
└─► Payment LB ─► Pay1 / Pay2
Answer

Gateway handles service/API-level routing. Load balancing handles instance-level traffic distribution.

Gateway → Which service?
Load Balancer → Which instance?
5. Gateway + Service Discovery
Question
If Gateway already has service discovery, do I still need a Load Balancer?
Client ──► Gateway ──► Discovery ──► O1 / O2 / O3
Answer

Not necessarily. The Gateway can discover service instances and perform instance selection/load balancing. A separate load balancer can still be introduced when infrastructure-level traffic management, health checks, cloud-managed scaling, or other requirements justify it.

Global / Multi-Region Architecture

This is where your Distributed Systems topic really starts.

6. Application deployed in different continents
Question
Users are worldwide. How do I reduce latency?
Users ──► Global DNS ──► US / EU / Asia
Answer

Deploy application instances in multiple regions and use global traffic routing to direct users to an appropriate healthy region.

7. Does every region need a Gateway?
Question
If I deploy in US, Europe and Asia, do I need a Gateway in each region?

A common architecture is:

Users ──► Global DNS ──► US Gateway / EU Gateway / Asia Gateway

Each region can have its own complete stack:

US:   Gateway ──► ALB ──► US Instances
EU:   Gateway ──► ALB ──► EU Instances
Asia: Gateway ──► ALB ──► Asia Instances
Answer

If the Gateway is part of the regional application entry architecture, having a regional Gateway allows traffic to stay within the selected region and avoids unnecessary cross-region hops.

8. Who decides which region receives the request?
Question
Who decides whether the request goes to US, Europe or Asia?
Client ──► Global DNS / Traffic Manager ──► Region
Answer

A global DNS/traffic-management layer makes the regional routing decision. It can use policies such as: Latency Geography Health Failover Weighted routing Don't simply say "nearest region." Better interview wording: "The global traffic-management layer routes the client to the optimal healthy region based on latency, geography, or configured failover policies."

9. Does DNS route directly to the ALB?
Question
If I have Gateway + ALB, what does DNS point to?
Architecture:
Client ──► DNS ──► Gateway ──► ALB ──► Instances
Answer

DNS normally exposes the public entry point of the architecture. If Gateway is the public entry point:

DNS ──► Gateway

If ALB is the public entry point:

DNS ──► ALB

The exact architecture depends on which component is intended to be client-facing.

Regional Failure
10. What if one region goes down?
Question
Europe is completely unavailable. What happens?
Normal:
EU User ──► Global DNS ──► EU ──► Application
EU fails:
EU User ──► Global DNS ──► US ──► Application
Answer

Global traffic management detects the unhealthy region and routes traffic to another healthy region according to the configured failover policy. This gives global high availability.

11. What if only one server goes down?
Question
App-2 dies but the region is healthy?
Client ──► ALB ──► App1 / App2 ❌ / App3
Answer

The regional load balancer detects the unhealthy instance and stops sending traffic to it. This is regional high availability.

12. Regional HA vs Global HA
Question
What's the difference?

Regional HA:

EU ──► ALB ──► EU1 / EU2 / EU3

Protects against instance failure. Global HA:

Global DNS ──► US / EU / Asia

Protects against regional failure. Interview answer: "Regional load balancing provides availability within a region, while multi-region routing provides resilience against regional or data-center-level failures."

ALB / NLB
13. When do I use ALB?
Question
When would you choose ALB?
Client ──► ALB ──► HTTP Services
Answer

When traffic is HTTP/HTTPS and I need Layer-7 capabilities such as: Path-based routing Host-based routing HTTP-aware routing HTTP health checks

14. When do I use NLB?
Question
When would you choose NLB?
Client ──► NLB ──► TCP/UDP Instances
Answer

When I need Layer-4 network load balancing, particularly for TCP/UDP traffic, high throughput, low latency, or network-level requirements.

15. ALB vs NLB
Question
What's the difference?
ALB ──► L7 ──► HTTP / HTTPS
NLB ──► L4 ──► TCP / UDP
Answer

"ALB understands application-level HTTP traffic, while NLB operates at the network/transport level."

Gateway vs Load Balancer
16. Why not just use ALB instead of Gateway?
Question
Client ──► ALB ──► Services

Why do I need Gateway?

Answer

ALB can perform HTTP routing, but API Gateway provides broader API-management capabilities such as: Authentication Authorization Rate limiting API policies API versioning Request transformation

So:
ALB      → Traffic / Target balancing
Gateway  → API management
17. Can ALB route to multiple services?
Question
Can I do this?
Client ──► ALB ──► /orders → Order
└─► /products → Product
Answer

Yes. ALB supports Layer-7 HTTP routing. Therefore: API Gateway is not simply "a better ALB." They solve different architectural problems.

Internal Communication
18. Should every service call go through Gateway?
Question
Order ──► Gateway ──► Payment

Is this mandatory? No. Internal services can communicate using:

Order ──► Discovery ──► Payment

or:

Order ──► Internal LB ──► Payment Instances

or asynchronously:

Order ──► Kafka/RabbitMQ ──► Payment

Interview answer: "I would generally keep the API Gateway as the client-facing entry point rather than forcing all internal service-to-service traffic through it."

Global Database Problem

This is the next level of distributed systems.

19. What if every region needs the same database?
Question
US App ──┐
EU App ──┼──► Database
Asia App ─┘

What problem do we have?

Answer

Now database latency, consistency, replication, and availability become distributed-system concerns. A common approach is regional data replication:

US DB ◄────► EU DB ◄────► Asia DB

But now you must decide between: Strong consistency Eventual consistency Replication strategy Conflict resolution Read/write strategy

20. What if users write data in different regions?
Question
US User ──► US Region ──► US DB
EU User ──► EU Region ──► EU DB

What happens when the same customer's data is modified from both regions?

Answer

This becomes a distributed data consistency problem. You need to define: Data ownership Replication Conflict resolution Consistency model Write routing This is where CAP theorem, replication and distributed transactions become relevant.

21. What if the requirement is "very fast reads"?
Question
User ──► Region ──► Database

How can we improve latency?

Answer

Use caching and regional replicas/CDN where appropriate.

User ──► Region ──► Cache ──► DB

For static content:

User ──► CDN ──► Static Content

Client ───────────► App Instance
Question
Do I need a Load Balancer?

No. There is only one instance, so there is nothing to balance.

2. Single application, multiple instances
Client ──► ALB ──► App-1
├─► App-2
└─► App-3
Question
Why use ALB?

Because we have multiple instances of the same application/service and want: Load distribution High availability Health checks Horizontal scaling

Question
Is ALB mandatory?

No. You need load balancing, but the actual technology could be ALB, NLB, or another load-balancing mechanism depending on traffic requirements.

Question
Why ALB here?

Because the application uses HTTP/HTTPS and we may want Layer-7 routing.

3. Multiple services, but each has one instance
Client ──► Gateway ──► Order
├─► Product
└─► Payment
Question
Why Gateway?

Because we have multiple APIs/services and want a single entry point. Gateway can provide: Authentication Authorization Rate limiting Routing API versioning Request transformation

Question
Do I need a Load Balancer?

Not necessarily. If each service has only one instance, there is nothing to balance.

This is the classic microservices architecture. Client

Gateway

├──► Order LB ──► O1 / O2 / O3
├──► Product LB ─► P1 / P2 / P3

Service/API-level routing.

/api/orders   → Order Service
/api/products → Product Service
/api/payments → Payment Service

Instance-level distribution.

Order Service → O1 / O2 / O3

The important interview answer: Gateway decides which service should handle the request; the load balancer decides which instance of that service should handle it.

5. Gateway + Service Discovery

Now things become interesting.

Client ──► Gateway ──► Service Discovery ──► O1/O2/O3
Question
Do I still need an ALB?

Not necessarily. The Gateway can discover service instances and perform client-side load balancing/instance selection.

├── O1

Interview question: "If API Gateway has service discovery, why do you need a load balancer?" Good answer: "We don't necessarily need a separate load balancer. It depends on the architecture. The gateway can perform service discovery and instance selection itself. A separate load balancer can still be useful when we want infrastructure-level load balancing, centralized health checks, or cloud-managed traffic distribution."

6. ALB — HTTP/HTTPS traffic
Client ──► ALB ──► App-1
├─► App-2
└─► App-3

ALB operates at Layer 7. It understands HTTP concepts.

For example:
Client ──► ALB
├── /orders/*   → Order targets
└── /products/* → Product targets
Question
When would you choose ALB?

When: Traffic is HTTP/HTTPS You need path-based routing You need host-based routing You want application-aware routing

Question
Can ALB route to multiple services?

Yes.

Client ──► ALB ──► /orders    ──► Order
└─► /products  ──► Product

This is important: ALB itself can perform some routing that people often associate with API Gateway. But ALB is primarily a load balancer, whereas Gateway is an API management/entry-point component.

7. NLB — TCP/UDP traffic
Client ──► NLB ──► Server-1
├─► Server-2
└─► Server-3

NLB operates at Layer 4. Think: IP + Port + TCP/UDP rather than: HTTP method URL path HTTP headers

Question
When would you use NLB?

When you need: TCP UDP Very high throughput Very low latency Network-level load balancing Static IP / network-level requirements

8. ALB vs NLB
Question
Are ALB and NLB the same service?

No. They are different load-balancer types within AWS Elastic Load Balancing. AWS ELB

├── ALB → L7 → HTTP/HTTPS
└── NLB → L4 → TCP/UDP
9. Gateway + ALB

Yes, you can have:

Client ──► Gateway ──► ALB ──► App-1/App-2/App-3
Question
Why both?

Because they have different responsibilities. Gateway: Authentication Rate limiting API policies API routing Versioning ALB: Health checks Load distribution Target selection HTTP-level routing

So:

Gateway manages the API, ALB manages the traffic distribution to targets.

10. Gateway + NLB

Also possible:

Client ──► Gateway ──► NLB ──► Service instances

But this isn't the default pattern you should memorize. NLB makes sense when the underlying traffic/requirements are Layer 4/network-oriented.

How an Architect Approaches a New Project
How an Architect Approaches a New Project
Step 1: Understand Business Goals

First, understand what the client wants to achieve. Examples: Build an e-commerce platform Modernize a legacy application Support 1 million users Reduce operational costs Improve customer experience Questions: What problem are we solving? Who are the users? What is the expected scale?

Step 2: Define Architecture Principles -system design

These are the decision-making rules. Questions: Is Availability more important than Consistency? Is Security the top priority? Is Cloud First required? Is SaaS preferred over custom development? Must there be no single point of failure? Examples: Principles

├── Cloud First
├── Security First
├── High Availability
├── API First
└── Buy Before Build

Example: If the business is Netflix-like streaming: Availability > Consistency If the business is Banking: Consistency > Availability

Step 3: Identify Capabilities - system design

Determine what the system must do. Functional Capabilities Business features: Customer Registration Product Search Place Order Generate Invoice Technical Capabilities Supporting features: Authentication Authorization Caching Monitoring Logging Development Capabilities Version Control CI/CD Automated Testing Operations Capabilities Monitoring Backup Disaster Recovery Auto Scaling

Step 4: Select Architecture Patterns - Application design

Choose patterns that satisfy the principles and capabilities. Examples: Principle: Independent Deployment Pattern: Microservices Principle: Separation of Concerns Pattern: MVC Principle: Automated Infrastructure Pattern: Infrastructure as Code

Step 5: Choose Technology Components

Now decide what technologies implement the capabilities. Application Components Spring Boot Salesforce SAP Data Components PostgreSQL MongoDB Redis Platform Components Java 21 Linux Docker Kubernetes Infrastructure Components AWS Azure Load Balancer Firewall Storage

Easy Interview Answer

When a new project starts, I would: Understand business goals and constraints. Define architecture principles with stakeholders. Identify functional and non-functional requirements and convert them into capabilities. Select architecture patterns that satisfy those principles and capabilities. Choose application, data, platform, and infrastructure components. Produce the target architecture and roadmap. This ensures that technology choices are driven by business needs rather than personal preferences.

1. Application Components

Application Components contain the business logic and business functionality. These are the applications that users directly interact with or that execute business processes. Java Examples Spring Boot User Service Spring Boot Order Service Salesforce CRM SAP ERP Customer Portal Example Capability: Place Order Implemented by: Order Service (Spring Boot) Example Java code:

@RestController
public class OrderController {
@PostMapping("/orders")
public Order createOrder() {
return orderService.placeOrder();
}
}

The Order Service is an Application Component because it performs business work.

2. Data Components

Data Components store and manage information used by applications. They include: Databases Tables Files Metadata Data Models Java Examples Customer table Order table Product catalog PostgreSQL database MongoDB collections Example Capability: Store Customer Information Implemented by: Customer Database Example: Customer

├── id
├── name
├── email
└── address

The data itself is a Data Component.

3. Platform Components

Platform Components provide the environment where applications and data run. Applications cannot execute without a platform. Java Examples Linux Red Hat Enterprise Linux Java JDK Tomcat Docker Kubernetes Example Order Service requires: Java 21 Linux Docker Without these platform technologies, the application cannot run. Think: Application runs on Platform

4. Infrastructure Components

Infrastructure Components provide the physical or cloud foundation. They support the platform. Examples AWS EC2 Server Virtual Machines Network Firewall Load Balancer Storage Devices Physical Servers Example Linux needs somewhere to run: Linux runs on AWS Server The AWS Server is Infrastructure. Think: Platform runs on Infrastructure

Capabilities in Software Architecture

Capabilities describe what a system is able to do. They represent the behaviors and functionalities required for the system to operate and support its lifecycle. The ADA Technology Cube divides capabilities into three categories: Think: Functional = "What business users do" Technical = "What the system needs" Development = "What developers need" Operations = "What support teams need"

Quick Memory Trick Capabilities

│
├── Runtime    → Used by Users
│   ├── Functional → Business Features
│   └── Technical  → Support Features
│
├── Development → Used by Developers
│
└── Operations  → Used by Operations/Support Teams

Think: Functional = "What business users do" Technical = "What the system needs" Development = "What developers need" Operations = "What support teams need"

1. Runtime Capabilities

Runtime Capabilities are the functions and behaviors available while the system is running and serving users. Functional Runtime Capabilities These provide direct business value to users and support business processes. Java E-commerce Examples: User Registration Product Search Place Order Payment Processing Invoice Generation Example:

public class InvoiceService {
public Invoice generateInvoice(Order order) {
// Business functionality
return new Invoice(order);
}
}

Generating an invoice is a Functional Runtime Capability because it directly supports a business process. Technical Runtime Capabilities These support the functional capabilities but are not directly visible as business features. Java Examples: Authentication Authorization Logging Caching Messaging Monitoring Example:

@Service
public class AuthenticationService {
public boolean authenticate(String username, String password) {
// Security support functionality
return true;
}
}

Authentication is a Technical Runtime Capability because it enables users to securely access business functions.

2. Development Capabilities

Development Capabilities support the creation, maintenance, and evolution of the system. Examples: Source Code Management Software Versioning Automated Testing Continuous Integration (CI) Code Quality Analysis Java Examples: Git repositories Maven or Gradle builds JUnit testing Jenkins pipelines SonarQube analysis Example:

git commit -m "Add payment feature"
git tag v1.0.0

Software Versioning is a Development Capability because it helps developers manage application changes.

3. Operations Capabilities

Operations Capabilities support deployment, monitoring, maintenance, and day-to-day running of the system. Examples: Application Monitoring Backup and Recovery Log Management Auto Scaling Incident Management Java Examples: Prometheus monitoring Grafana dashboards Kubernetes deployments Centralized logging Example: logger.info("Order created successfully"); Logging supports Operations because it helps administrators monitor and troubleshoot the system.
