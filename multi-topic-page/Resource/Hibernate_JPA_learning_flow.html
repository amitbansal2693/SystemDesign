01Foundation: ORM → JPA → Hibernate

Start with the big picture

The document's central relationship is: ORM is the concept, JPA is the specification/rulebook, and Hibernate is the implementation/engine. This relationship should be understood before learning EntityManager, Persistence Context, fetching, caching or transactions.

ORM (Concept / Technique)
        ↓
JPA (Specification / Rules)
        ↓
Hibernate (Implementation / ORM Engine)
        ↓
SQL
        ↓
Database

ORM — Object Relational Mapping

ORM maps Java objects to relational database structures. The source describes the mapping as:

Java / Object WorldRelational World
ClassTable
ObjectRow
FieldColumn

The problem ORM solves is the object-relational impedance mismatch: Java works with objects, relationships and inheritance, while relational databases work with tables, rows and columns.

Why ORM is needed

Without ORM, JDBC requires boilerplate connection handling, prepared statements and manual SQL. The source identifies productivity, maintainability and data-conversion problems as key motivations for ORM.

How ORM works

Java Object
   ↓
ORM
   ↓
SQL
   ↓
Database

Database
   ↓
ORM
   ↓
Java Object

Hibernate — the implementation

Hibernate implements JPA and performs the actual ORM work: it reads entity metadata, generates SQL, executes it and converts database results back into Java objects. The source explicitly summarizes the relationship as JPA = WHAT to do; Hibernate = HOW it is done.

When ORM is not the best choice

The source recommends considering JDBC/native SQL for complex reporting queries, very large bulk operations, highly performance-critical systems and stored-procedure-heavy systems.

02JPA: The Standard API and Specification

What is JPA?

JPA (Jakarta Persistence API) is a specification that standardizes annotations, interfaces and contracts for persistence. It defines APIs such as EntityManager and annotations such as @Entity and @Id.

Why JPA exists

Before a common specification, ORM providers exposed different APIs. JPA reduces vendor lock-in by giving application code a standard API while an implementation such as Hibernate performs the work.

Application Code
       ↓
JPA API / Contracts
       ↓
Hibernate
       ↓
SQL
       ↓
Database

JPA does not do the work itself

The source repeatedly emphasizes that JPA defines what/how the persistence API should behave; it does not itself generate SQL or execute database operations. Hibernate implements the JPA contracts.

Core JPA API examples

EntityManager em;

em.persist(entity);             // CREATE
em.find(Employee.class, 1);     // READ
em.merge(entity);               // UPDATE / reattach state
em.remove(entity);              // DELETE
em.createQuery(...);            // JPQL

Interview mental model

ORM = Concept
JPA = Standard rules + API
Hibernate = Actual implementation / engine
03Entity and EntityManager: The Core Building Blocks

Entity — WHAT is mapped?

An entity is a Java class mapped to a database table using JPA annotations.

@Entity
@Table(name = "employee")
public class Employee {
    @Id
    private int id;
    private String name;
    private double salary;
}
Employee class → EMPLOYEE table
id             → id column
name           → name column
salary         → salary column

What happens when Hibernate sees an Entity?

  1. Hibernate scans the entity classes.
  2. It reads annotations such as @Entity, @Table and @Id.
  3. It builds metadata.
  4. It can create/validate database structures depending on configuration.

EntityManager — WHO manages the entity?

EntityManager is the JPA API responsible for entity lifecycle operations and CRUD interaction with the persistence context.

Developer
   ↓
EntityManager
   ↓
Persistence Context
   ↓
Hibernate
   ↓
SQL
   ↓
Database

The four essential operations

OperationEntityManager callCore idea
Createpersist()Add entity to persistence context
Readfind()Check context, otherwise query DB
UpdateModify managed entityDirty checking detects change
Deleteremove()Mark entity for deletion

EntityManagerFactory vs EntityManager

The source introduces the distinction here. Keep the mental model simple: EntityManagerFactory creates/manages EntityManager instances; EntityManager performs persistence operations for a persistence context.

04Persistence Context: The Internal Engine

The most important internal concept

The source describes the persistence context as memory + cache + change tracker. It stores entity objects and tracks their changes.

Persistence Context
= Map<ID, Entity> + Change Tracker

Why it matters

  • It checks whether an entity is already loaded before hitting the database.
  • It keeps managed entities in memory.
  • It tracks modifications.
  • It enables dirty checking.
  • It coordinates changes that are eventually synchronized with the database.

05Entity Lifecycle: Transient → Managed → Detached → Removed

Why lifecycle comes after Persistence Context

Entity lifecycle describes the states an object moves through while interacting with JPA. The source emphasizes that dirty checking, persist and remove depend on the entity's state.

TRANSIENT
   │ persist()
   ▼
MANAGED
   │ detach() / context ends
   ▼
DETACHED

MANAGED
   │ remove()
   ▼
REMOVED

1. Transient

A newly created Java object exists only in memory. It is not in the database and is not tracked.

Employee emp = new Employee();
emp.setName("Raj");

2. Managed / Persistent

The entity is inside the persistence context and tracked by EntityManager. Dirty checking works in this state.

em.persist(emp);
Employee emp = em.find(Employee.class, 1);

3. Detached

The object still exists, but it is no longer tracked by the persistence context. Changes made to it are not automatically synchronized.

em.detach(emp);
// or the persistence context ends

4. Removed

The managed entity is marked for deletion. The delete is synchronized with the database when the context is flushed/transaction commits.

em.remove(emp);
06Transactions and Flush: When Memory Becomes SQL

Transaction — the unit of work

The source defines a transaction as a unit of work where changes are committed together or rolled back together so data remains consistent.

Transaction
   ├── all operations succeed → COMMIT
   └── error → ROLLBACK

Connect transactions with the persistence context

This is the key learning flow: the persistence context holds changes in memory; the transaction provides the boundary in which those changes are synchronized with the database.

EntityManager
      ↓
Persistence Context
      ↓
Transaction COMMIT
      ↓
FLUSH
      ↓
SQL Execution
      ↓
Database

Example

@Transactional
public void createEmployee() {
    Employee emp = new Employee();
    emp.setName("Raj");
    em.persist(emp);
    emp.setName("Rahul");
}

The source's flow: transaction starts → persist adds the object to the context → the name change is tracked → SQL is not necessarily executed immediately → commit flushes the context → SQL is executed.

What is flush?

Flush = synchronize the persistence context with the database. Hibernate generates and executes the SQL needed to make the database reflect the current managed state.

Rollback

If an error causes rollback, the transaction's database changes are discarded. The source's example shows a persisted entity followed by a runtime exception resulting in no committed INSERT.

Spring's @Transactional

The source describes Spring as opening the transaction, executing the method, and then committing or rolling back depending on the outcome.

Interview line: “A transaction in JPA defines a unit of work where changes made in the persistence context are flushed to the database on commit. If an error occurs, the transaction is rolled back to maintain data consistency.”
07Dirty Checking: Automatic Update Detection

What is dirty checking?

Dirty checking means JPA automatically detects changes made to a managed entity and synchronizes those changes with the database without an explicit update query.

Load Entity
    ↓
Persistence Context
    ↓
Modify Object
    ↓
Dirty Checking
    ↓
Generate UPDATE
    ↓
Flush / Commit
    ↓
Database

Example

Employee emp = em.find(Employee.class, 1);
emp.setName("Rahul");

// No em.update(emp) is required.

What happens internally?

  1. Entity is loaded into the persistence context.
  2. JPA/Hibernate keeps track of its managed state.
  3. The application modifies the object.
  4. Hibernate detects the difference.
  5. At flush/commit, it generates the required UPDATE SQL.

When does it work?

Only for managed entities. A transient or detached object is not automatically dirty-checked.

Memory anchor: Persistence Context stores the object → Dirty Checking watches the managed object → Flush/Commit turns the detected change into SQL.
08Fetching: LAZY vs EAGER

What is fetching?

Fetching defines when related entities are loaded from the database.

EAGER

EAGER means related data is loaded immediately when the entity is loaded.

Load Employee
    ↓
Employee + related Address
    ↓
Available immediately

Advantage: simple access to required related data. Risk: data may be loaded even when it is not needed, increasing memory use and database work.

LAZY

LAZY means related data is loaded when it is actually accessed.

Load Employee
    ↓
Employee only
    ↓
getAddresses()
    ↓
DB query / proxy initialization

This can reduce unnecessary data loading, especially for large collections, but it introduces the possibility of additional database queries.

Default relationship behavior in the source

RelationshipSource-listed default
@OneToManyLAZY
@ManyToOneEAGER

Senior-level insight

LAZY is not automatically “better”. It avoids unnecessary loading but must be designed carefully to avoid N+1 queries. EAGER can be convenient but can load too much data.

09N+1 Query Problem: The Performance Trap

Problem statement

The N+1 problem occurs when one query fetches the main entities and then an additional query is executed for each entity to load related data.

1 query → Employees
N queries → Addresses
──────────────────────
N + 1 queries ❌

Concrete example from the source

List<Employee> employees = em.findAll();

for (Employee e : employees) {
    e.getAddresses();
}

For 3 employees, the source shows:

1 × SELECT employees
3 × SELECT address WHERE emp_id = ?
────────────────────────────
4 queries total

For 100 employees, this becomes 101 queries.

Why it hurts

  • Too many database calls.
  • Network overhead.
  • Higher latency.
  • Potentially severe production performance problems.

Connection with LAZY fetching

The source connects N+1 mainly with lazy loading: each related collection is loaded separately when accessed.

Interview answer: “The N+1 problem occurs when one query fetches a list of entities and additional queries are executed for each entity to fetch related data, causing unnecessary database calls and performance degradation.”
10Caching: First-Level vs Second-Level

Why caching?

The source's core idea is simple: database access is relatively expensive, while memory access is fast. Caching keeps frequently accessed data in memory to reduce repeated database calls.

EntityManager
     ↓
First-Level Cache
(Persistence Context)
     ↓
Second-Level Cache
(optional / shared)
     ↓
Database

First-Level Cache

The first-level cache is the persistence context itself and is associated with an EntityManager.

Employee e1 = em.find(Employee.class, 1);
Employee e2 = em.find(Employee.class, 1);

The first call may hit the database. The second lookup can return the entity already present in the persistence context.

Second-Level Cache

The second-level cache is shared across persistence contexts/EntityManagers and can allow subsequent requests to avoid a database hit.

Request 1 → DB → Second-Level Cache
Request 2 → Cache → no DB hit

The source says second-level caching is optional and requires configuration. It lists Ehcache, Redis and Hazelcast as examples of technologies associated with caching.

Key difference

First LevelSecond Level
Persistence ContextShared cache
Scoped to EntityManager / persistence contextAcross persistence contexts
AutomaticOptional/configured
11Concurrency: Optimistic vs Pessimistic Locking

Why locking?

Locking is used to prevent data inconsistency when multiple users access or modify the same data simultaneously.

Optimistic LockingPessimistic Locking
No database row lock during normal editingLocks the database row
Uses @VersionUses database locking such as FOR UPDATE
Detects conflict while savingPrevents conflict before another update proceeds
Higher concurrencyLower concurrency
Good when conflicts are rareGood when conflicts are common

Optimistic Locking

The source describes optimistic locking as assuming conflicts are rare. Hibernate uses a version field and checks whether the row changed before applying the update.

@Entity
public class Recipe {
    @Id
    private Long id;

    @Version
    private Integer version;
}

If another transaction changes the same row first, the later update can fail and the application/user may need to retry.

Pessimistic Locking

Pessimistic locking assumes conflicts are likely. The row is locked when the update starts, so another transaction attempting to modify it waits until the first transaction commits or rolls back.

@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Recipe> findById(Long id);
User A
  ↓
Acquire DB row lock
  ↓
Update
  ↓
Commit / Rollback
  ↓
Release lock
  ↓
User B continues

Decision rule

Optimistic: conflicts are uncommon; prefer concurrency and detect conflicts at save time. Pessimistic: conflicts are common or immediate exclusivity is important; lock the row.

12JPQL and Querying: Where It Fits

JPQL

The source's overall roadmap places JPQL under querying data and describes it as object-based queries.

Application
   ↓
JPQL
   ↓
JPA / EntityManager
   ↓
Hibernate
   ↓
SQL
   ↓
Database

The important mental model is that JPQL works with entity types and their fields rather than directly treating the database as the primary abstraction.

When to step outside ORM abstractions

The source's senior-level guidance is to consider native SQL/JDBC when queries are highly complex, operations are massive/bulk-oriented, performance is critical, or the system relies heavily on stored procedures.
