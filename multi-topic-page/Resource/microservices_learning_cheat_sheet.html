Re-structured as a learning flow — related concepts grouped together, hierarchy charts preserved, detailed source material retained.

How to learn this document

This version is intentionally not organized by PDF page order. The material is regrouped so that each concept is learned in the order it becomes useful in a real microservices design.

1. Understand why microservices exist and what trade-offs they introduce.
2. Learn how to split the system into services.
3. Learn how services and clients communicate.
4. Understand service discovery and traffic routing.
5. Learn how to manage data and distributed transactions.
6. Add resilience so failures do not cascade.
7. Understand deployment and service-to-service infrastructure.
8. Add observability, security and scalability.
9. Finish with pattern selection and interview revision.
01Microservices: Why, What and Trade-offs

Why move from a monolith?

The source describes the motivation as the limitations of a monolithic architecture: a small change can require a full production deployment; the whole application may need to be scaled even when only one component needs more capacity; and many developers working on the same codebase create dependency and coordination problems.

The microservices model addresses this by making application components independently developed, deployed, versioned and scaled. Different services can use different databases and technologies, and different components can be on different versions.

Monolith
  • Small change can require full deployment.
  • Components are more dependent on each other.
  • Scaling one component may mean scaling the full application.
  • Many developers work on the same codebase.
Microservices
  • Independent component development.
  • Independent deployment.
  • Independent scaling.
  • Independent versioning.
  • Different databases and technologies can be used.
  • Different organizations/teams can develop components independently.

Microservices trade-offs

The source also explicitly notes the costs: microservices are more complex to develop and manage, require separate teams and infrastructure, and have higher infrastructure cost.

What problem do microservices patterns solve?

Once an application is split, new system-level questions appear: how do we split services, how do they communicate, how is data managed, how are failures handled, how are services deployed, secured and scaled?

Design patterns vs architecture patterns

The source distinguishes code-level design patterns from architecture-level patterns. Design patterns solve programming problems such as object/class interaction (for example Adapter, Decorator and Factory). Architecture patterns solve system-level problems involving multiple applications or services, such as Microservices, Monolith and Event-Driven Architecture.

03Decomposition: How to Split the Monolith

The question

How do we break a large monolithic application into independent microservices?

The source identifies maintainability, independent deployment, team ownership and scalability as the goals.

Decompose by Business Capability

Split services based on business domains such as User, Product, Order and Payment. The source recommends this when business domains are clearly separated and when following Domain-Driven Design (DDD).

User Service
Product Service
Order Service
Payment Service

Decompose by Subdomain

This is a more fine-grained decomposition of a larger domain.

Product
├── Catalog
├── Inventory
└── Pricing

The source associates this with very large domains, better scalability and smaller codebases.

Strangler Fig Pattern

The pattern hierarchy includes Strangler Fig as a decomposition pattern. The source places it alongside business-capability and subdomain decomposition as a way of breaking down or migrating a larger system.

04Communication: Client-to-Service and Service-to-Service

First decide: synchronous or asynchronous?

SynchronousAsynchronous
REST, gRPCKafka, RabbitMQ, Event Bus
Direct request/responseEvent/message based
Use when an immediate response is requiredUse when the caller does not need an immediate response
Real-time communicationLoose coupling, high throughput and event-driven workflows
Caller waits for responseConsumers process independently

REST — synchronous communication

Example from the source: Order Service needs Payment confirmation before placing an order. The calling service waits for the response.

  • Advantages: simple, easy to debug, widely adopted, immediate response.
  • Disadvantages: tight coupling, higher latency, and cascading failures if the downstream service is unavailable.

Spring technologies: RestTemplate (legacy), WebClient, OpenFeign.

gRPC — synchronous communication

The source describes gRPC as a high-performance RPC framework using Protocol Buffers and HTTP/2. It enables efficient service-to-service communication where clients call remote methods as if they were local.

The notes emphasize: gRPC is still backend network communication and still needs host/port/security; it abstracts the network call as a method call.

Kafka — asynchronous communication

Use asynchronous messaging for work such as sending email after an order, updating analytics or generating reports where synchronous REST would unnecessarily block the caller.

Order Created
      │
      ▼
 Kafka Topic
 ┌────┼─────┐
 ▼    ▼     ▼
Inventory Email Analytics
  • Advantages: loose coupling, high throughput, event replay, multiple consumers, fault tolerance.
  • Disadvantages: eventual consistency, more complex debugging, additional infrastructure and message-ordering considerations.
  • Spring technology: Spring Kafka.

RabbitMQ and Event Bus

The source groups RabbitMQ with Kafka and Event Bus under asynchronous communication. The core idea is that producers publish messages/events and consumers process them independently.

Interview comparison

REST vs gRPC: both are synchronous request/response mechanisms; gRPC focuses on efficient RPC semantics with Protocol Buffers/HTTP/2.

Kafka vs RabbitMQ: the source explicitly lists this as an interview question; the notes emphasize Kafka's event-driven, high-throughput and replay characteristics.

05API Gateway and Backend for Frontend (BFF)

API Gateway — the single entry point

Without a gateway, a client has to know the IP, port and endpoint of every service, update itself when services move, make too many network calls, and potentially duplicate authentication, rate limiting and logging logic.

Client
   │
   ▼
API Gateway
   ├── Authentication
   ├── Rate Limiting
   ├── Routing
   ├── Logging
   ├── Load Balancing
   ├── Service Discovery
   └── Aggregation
        │
        ├── User Service
        ├── Payment Service
        ├── Hotel Service
        └── Rating Service

Gateway responsibilities

  • Authentication: validate JWT/API key; the source notes that stateless APIs require authentication validation for incoming requests.
  • Rate limiting: control how many requests a client can make in a time window. The source distinguishes this from server capacity: rate limiting protects the system from excessive client traffic.
  • Routing: map paths such as /user or /payment to the appropriate service.
  • Logging: capture request/response details for monitoring, debugging and auditing.
  • Load balancing: distribute calls across multiple instances.
  • Service discovery: ask the registry where a service is and select an instance.
  • Aggregation: combine responses from several services into one response.
  • Protocol translation: the source includes HTTP→gRPC/WebSockets and REST→SOAP/legacy-system examples.

Gateway request flow

  1. Client sends a request to the gateway.
  2. Gateway authenticates and applies cross-cutting policies.
  3. Gateway routes the request to the correct microservice.
  4. If required, it calls multiple services and aggregates their responses.
  5. Gateway returns the response to the client.

Advantages

  • Single entry point.
  • Centralized authentication/authorization.
  • Rate limiting and routing in one place.
  • Response aggregation.
  • Hides internal service topology.
  • Easier API versioning.
  • Simplifies client code.

Disadvantages

  • Potential single point of failure unless highly available.
  • Can become a bottleneck or a “mini-monolith”.
  • Additional infrastructure.
  • Slight latency from extra processing/hops.

Technologies listed in the source

Spring Cloud Gateway, Netflix Zuul (legacy), Kong, NGINX.

API Gateway vs BFF

BFF (Backend for Frontend) is useful when different clients need materially different data. The source example: Web needs complete product details, Mobile needs basic information, and a Smartwatch may need only notifications.

             ┌── Web BFF ──┐
Client ──────┼── Mobile BFF ├── Microservices
             └── Admin BFF ─┘

Each BFF communicates with the required microservices and returns only the data needed by its client.

  • Advantages: optimized responses, better performance, independent frontend evolution, frontend-specific logic.
  • Disadvantages: additional services, some code duplication, increased deployment complexity.

The source lists as interview questions: Why BFF? API Gateway vs BFF? Can they coexist?

06Service Discovery and Load Balancing

Why service discovery?

Microservice instances are deployed dynamically. IP addresses and ports can change, instances can scale up/down, and failed services should stop receiving traffic. Hardcoded endpoints therefore become a problem.

Service Registry

A Service Registry is a centralized database/server where microservices register their network locations. It acts as a directory of available services.

Dynamic discovery and self-healing

  • Services register on startup.
  • Services deregister on shutdown.
  • A crashed service can be removed from the registry.
  • Consumers do not need to know the service's current IP/port.
  • Services can move or scale without changing callers.
Service Registry
├── User Service → 10.0.1.2:8080
├── Payment Service → 10.0.1.5:8080
└── Inventory Service → available instances

Client-side discovery

The client queries the Service Registry and selects an appropriate service instance. The client therefore contains discovery/load-balancing logic.

Server-side discovery

The client sends the request to an intermediary such as an API Gateway, Reverse Proxy or Load Balancer. The intermediary queries the Service Registry, selects a healthy instance and forwards the request.

Client → Gateway / Load Balancer → Service Registry
                                      │
                                      ▼
                              Healthy Service Instance

Trade-offs

Client-side discovery gives the client more control but adds discovery logic to every client. Server-side discovery simplifies clients but adds infrastructure and an extra hop; the gateway/load balancer must be highly available and scaled.

Technologies

Eureka (Spring Cloud Netflix), Consul, Zookeeper, Spring Cloud Gateway, NGINX, HAProxy, Kubernetes Service and Kubernetes Ingress.

Use cases

  • Dynamic scaling.
  • Cloud/container environments such as Kubernetes and Docker.
  • Resilience and automatic removal of unavailable instances.

Load balancing

The source explains load balancing as choosing among multiple service instances to distribute load, improve performance and avoid overload. Example: U1, U2, U3, U4, U5 receive requests in distribution rather than every request hitting one instance.

07Data Management: Ownership, Consistency and Distributed Transactions

Why data management patterns are needed

In a monolith, modules commonly share one database and ACID transactions are straightforward. In microservices, each service ideally owns its database, but one business operation can span several services. This creates questions about data ownership, consistency, distributed transactions and synchronization.

Database per Service

User Service   → User DB
Order Service  → Order DB
Payment Service → Payment DB
Inventory Service → Inventory DB

Only the owning service directly reads/modifies its data. Other services use APIs or events.

  • Advantages: loose coupling, independent deployment, independent scaling, better security, technology flexibility, clear data ownership.
  • Disadvantages: cross-service joins are unavailable, distributed transactions are harder, data duplication may be required, reporting becomes more complex.

Technologies: Spring Data JPA, Spring Data MongoDB, Spring Data Redis, Hibernate, Flyway/Liquibase.

Shared Database — anti-pattern

Multiple services directly access one database. It initially provides easy joins, native ACID transactions, no data duplication and less initial development effort, but creates tight coupling, unclear ownership, schema dependencies, difficult independent deployment/scaling and the possibility that one faulty service affects others.

The source says it may be acceptable temporarily during monolith migration, but is not recommended for a true microservices architecture.

Saga Pattern — distributed transactions

A Saga breaks a business transaction into a sequence of local transactions. If a later step fails, compensating transactions undo the completed business actions.

Create Order
    │
    ▼
Reserve Inventory
    │
    ▼
Process Payment
    │
    ▼
Arrange Shipping

Failure example:
Payment fails
   → Release Inventory
   → Cancel Order

Choreography

Services coordinate by publishing and consuming events. There is no central controller.

  • Advantages: decentralized, suitable for smaller workflows, no central coordinator.
  • Disadvantages: event chains become difficult to understand and debug as the system grows.

Orchestration

A central Saga Orchestrator controls the workflow and tells each service what to do next.

  • Advantages: easier to understand, centralized control, easier monitoring/debugging.
  • Disadvantages: another component to maintain; can become a bottleneck if poorly designed.

Technologies: Spring Boot, Spring Kafka, RabbitMQ, Camunda, Temporal, Orkes/Netflix Conductor.

CQRS

CQRS separates write operations (Commands) from read operations (Queries), allowing each side to be optimized and scaled independently.

Source example: a product page may be viewed 100,000 times/day but updated only 50 times/day.

  • Advantages: better read performance, independent scaling, simpler read models, flexible database design.
  • Disadvantages: increased complexity, eventual consistency, more infrastructure.

Technologies: Spring Boot, Spring Data JPA, Kafka/RabbitMQ, Redis, Elasticsearch.

Event Sourcing

Instead of storing only current state, every state-changing business event is stored as an immutable event. Current state is rebuilt by replaying the events.

Account Created
Deposit $500
Deposit $700
Withdraw $300
        │
        ▼
Replay events → Current state
  • Advantages: complete audit history, event replay, debugging, temporal queries.
  • Disadvantages: implementation complexity, event-schema evolution, slower rebuilds without snapshots.

Technologies: Spring Kafka, EventStoreDB, Axon Framework, PostgreSQL, MongoDB.

Transactional Outbox

Problem: a service saves an order successfully but Kafka is temporarily unavailable. The order exists but the event is lost, leaving other services unaware.

DB Transaction
├── Save Order
└── Save OrderCreated in Outbox Table
             │
             ▼
      Background Publisher
             │
             ▼
       Kafka / RabbitMQ

The business data and outgoing event are saved in the same database transaction. A separate process later publishes the outbox event and marks it processed/removes it.

  • Advantages: reliable event publishing, prevents lost messages, supports event-driven architecture, keeps DB and broker state consistent.
  • Disadvantages: extra outbox table, background publisher, possible duplicate events; consumers should therefore be idempotent.

Technologies: Spring Boot, Spring Data JPA, Spring Kafka/RabbitMQ, Debezium (CDC), Kafka Connect.

08Resilience: Designing for Failure

What is resilience?

Resiliency patterns help a microservices system continue functioning when services are slow, unavailable or fail unexpectedly. The source's goal is to prevent a single service failure from bringing down the whole system.

Fault Tolerance
│
├── Detect Failure
│   ├── Health Check
│   └── Timeout
│
├── Prevent Failure
│   ├── Circuit Breaker
│   ├── Bulkhead
│   └── Rate Limiting
│
├── Recover
│   ├── Retry
│   ├── Fallback
│   └── Idempotency
│
└── Scale
    ├── Load Balancer
    └── Kubernetes

Why failures happen

  • Network failures
  • Service crashes
  • Database failures
  • High latency
  • Third-party API failures
  • Hardware/cloud failures

1. Circuit Breaker

Stops sending requests to a failing service for a period, preventing repeated failures and giving the downstream service time to recover.

Order Service → Payment Service (DOWN)
                     │
                     ▼
                Circuit OPEN
                     │
               No more calls
                     │
                 wait period
                     │
               test request
                     │
          success → CLOSED
          failure → OPEN

Advantages: prevents cascading failures, faster failure response, fewer unnecessary network calls, recovery time for the failing service.

Disadvantages: configuration complexity, bad thresholds can block healthy services, operational complexity.

Spring: Resilience4j, Spring Cloud Circuit Breaker.

2. Retry

Retry temporary failures such as a temporary network issue, service startup or short database lock.

Attempt 1 → Failed
Attempt 2 → Failed
Attempt 3 → Success

Advantages: handles transient failures, improves success rate, easy to implement. Disadvantages: increases latency, may overload a failing service, unsuitable for permanent failures.

The source also discusses fixed delay, exponential backoff and maximum attempts. Technologies: Resilience4j Retry and Spring Retry.

3. Timeout

Limits how long a service waits for a response. Example: wait only 3 seconds; if no response arrives, cancel the request and return an error or fallback.

  • Advantages: prevents thread exhaustion, faster failure detection, better responsiveness.
  • Disadvantages: requires careful tuning; too short rejects valid requests, too long reduces performance.

Technologies: WebClient, RestTemplate, OpenFeign, Resilience4j TimeLimiter.

4. Bulkhead

Isolates resources such as thread pools, connection pools or service instances into compartments so one failure does not consume resources needed by other functions.

Order Thread Pool      Payment Thread Pool      Notification Thread Pool
      50 threads              20 threads                 10 threads

Source example: if Notification becomes slow and exhausts its 10 threads, Order and Payment continue using their own pools.

The name comes from ships: watertight compartments stop flooding in one section from sinking the whole ship.

Types

  • Thread Pool Bulkhead: separate thread pools.
  • Semaphore Bulkhead: limit concurrent requests; for example, allow 10 payment requests and reject an 11th.
@Bulkhead(name = "paymentService", type = Bulkhead.Type.THREADPOOL)
@Bulkhead(name = "paymentService")

Spring: Resilience4j Bulkhead.

  • Advantages: prevents cascading failures, improves reliability, protects critical services, better fault isolation.
  • Disadvantages: extra configuration, possible underutilization, pool-size tuning required.

5. Fallback

When the primary service is unavailable, return an alternative response: cached data, a default value, friendly message or alternative service.

It improves user experience, availability and graceful degradation, but may return stale/incomplete data and adds fallback complexity.

6. Rate Limiter

Controls the number of requests a client can make in a specified period. Example: 100 requests per minute. It protects against overload, denial of service and impact on other users.

The source also lists Token Bucket, Leaky Bucket and API Gateway as related concepts.

7. Idempotency

Ensures retries do not create duplicate operations. The source's solution is an Idempotency Key: when the same request arrives again, return the original result rather than executing the operation again.

How the patterns work together

09Timeout, Pooling and Resource Protection

Pooling

The source explains pooling as distributing/reusing a finite set of expensive resources, especially database connections. Instead of creating a new connection for every request, requests take a connection from a pool and return it after use.

Pool = [C1, C2]

getConnection() → remove C1
Pool = [C2]

releaseConnection(C1)
Pool = [C2, C1]

Spring Boot normally uses HikariCP as the default database connection pool.

spring.datasource.hikari.maximum-pool-size=10

Pooling + rate limiting

Client
  ↓
Rate Limiter 🚫
  ↓
Service
  ↓
Connection Pool 🔄
  ↓
Database

Source mental test: if 10 requests arrive and pool size is 5, the first 5 get connections; the next 5 wait or fail depending on configuration.

One-line summary: Pooling = reuse expensive resources instead of recreating them.

10Deployment Patterns and Service-to-Service Infrastructure

Deployment pattern goals

The source groups deployment around zero downtime, easy rollback, independent deployment and safe releases.

Service per Container

Each microservice runs in its own container, such as Docker. The source associates this with isolation and portability.

Sidecar Pattern

A sidecar attaches infrastructure capabilities to a service without embedding them directly into application code.

┌───────────────────────┐
│ Main Service          │
│       +               │
│ Envoy / Sidecar Proxy │
└───────────────────────┘

Typical responsibilities in the source: logging, monitoring, security, traffic management, TLS, routing, load balancing, retries and metrics.

Technologies: Envoy Proxy, Fluent Bit, OpenTelemetry Collector, Istio Sidecar.

  • Advantages: separation of concerns, reusable infrastructure, easier maintenance, no application-code changes.
  • Disadvantages: additional container/process, resource consumption, deployment complexity.

Ambassador Pattern

An Ambassador is a proxy acting as a local representative for communication with external services. The application talks only to the Ambassador.

It can handle routing, TLS, retries, timeouts and authentication. It simplifies application code and centralizes communication logic, but adds infrastructure and network overhead.

Technologies: Envoy, NGINX, HAProxy.

Adapter Pattern

The Adapter converts one interface/protocol to another so incompatible systems can communicate. Source example: an application expects JSON but an external system exposes XML/SOAP.

It helps integrate legacy systems and reduces changes to business logic, at the cost of another component and small performance overhead.

Technologies: Spring Integration, Spring Web Services, Apache Camel.

Service Mesh

A Service Mesh is an infrastructure layer that abstracts service-to-service communication using sidecar proxies. It manages traffic management, security, observability and resiliency without changing application code.

Control Plane
     │     │     │
     ▼     ▼     ▼
┌────────┐ ┌────────┐ ┌────────┐
│Sidecar │ │Sidecar │ │Sidecar │
│  +     │ │  +     │ │  +     │
│Service A││Service B││Service C│
└────────┘ └────────┘ └────────┘

Sidecar proxy responsibilities

  • Traffic routing
  • Load balancing
  • Retry
  • Circuit breaker
  • Timeout
  • mTLS encryption
  • Metrics and distributed tracing

Examples: Envoy and Linkerd Proxy.

Control Plane responsibilities

  • Traffic policies
  • Security policies
  • Certificate management
  • Service discovery
  • Configuration updates

Examples: Istio Control Plane and Linkerd Control Plane.

Service Mesh features

  • Traffic: intelligent routing, load balancing, canary, blue-green, traffic splitting.
  • Security: mTLS, authentication, authorization, certificate management.
  • Observability: distributed tracing, metrics, logging, monitoring.
  • Resilience: retry, circuit breaker, timeout, fault injection.

How the sidecar actually works

The source explains that sidecars intercept inbound and outbound traffic. In Kubernetes this can be achieved by redirecting traffic through the sidecar using Linux iptables. Routing rules are supplied by the control plane. The proxy can discover services through the control plane, establish mTLS between proxies and send metrics/logs to tools such as Prometheus and Grafana.

Service A
   │
   ▼
Sidecar A
   │  mTLS / routing / retry / timeout
   ▼
Sidecar B
   │
   ▼
Service B

The source gives a canary routing example of 90% stable traffic and 10% new-version traffic.

When to use a Service Mesh

  • Large/complex microservice architectures.
  • Security and compliance requirements.
  • Advanced traffic management.
  • Need for retries, timeouts, circuit breakers and traffic splitting without changing application code.

Service Mesh trade-offs

  • No application code changes.
  • Centralized communication policies.
  • Automatic mTLS and observability.
  • Additional infrastructure and resource use.
  • More operational complexity and learning curve.
  • Slight latency from the proxy hop.
11Safe Deployment: Blue-Green, Canary and Rolling

Blue-Green Deployment

Maintain two production environments. Blue serves current production; Green contains the new version.

Blue  → Current Production
Green → New Version

Validate Green
   │
   ├── success → switch all traffic to Green
   └── failure → switch traffic back to Blue

Advantages: near-zero downtime, fast rollback, safe deployment and easy testing.

Disadvantages: roughly double infrastructure, higher cost, and database migrations can be challenging.

Technologies: Kubernetes, NGINX, AWS Load Balancer, Azure Traffic Manager.

Canary Deployment

Release a new version to a small percentage of users and gradually increase traffic.

5% → 20% → 50% → 100%

Monitor metrics at every stage; stop rollout if issues appear.

Advantages: reduced deployment risk, early issue detection, real-user feedback, controlled rollout.

Disadvantages: more complex routing, monitoring requirements and operational effort.

Technologies: Kubernetes, Istio, Argo Rollouts, AWS CodeDeploy.

Rolling Deployment

Replace old instances gradually rather than stopping all servers at once.

Server 1 → Updated
Server 2 → Updated
Server 3 → Updated
Remaining servers continue serving traffic

Advantages: no downtime, lower infrastructure cost, gradual rollout, simple deployment.

Disadvantages: old and new versions run simultaneously, rollback is slower than Blue-Green, and backward compatibility is required.

Technologies: Kubernetes Deployments, Docker Swarm, AWS ECS.

Quick comparison

PatternCore ideaRollbackMain cost/risk
Blue-GreenTwo environments; switch trafficVery fastDouble infrastructure
CanaryGradually increase new-version trafficStop/redirect rolloutRouting + monitoring complexity
RollingReplace instances graduallySlowerVersion compatibility
12Observability: See What the System Is Doing

Observability pattern map

Centralized Logging

Centralize logs so requests and failures across multiple services can be investigated from one place. The source repeatedly associates logging with monitoring, debugging and auditing.

Distributed Tracing

Track a request across multiple microservices so latency and failure points can be located.

Metrics

Collect measures such as request count, latency, error rate and service health. The service-mesh notes specifically describe sidecars collecting latency, request count and errors and sending these to monitoring tools such as Prometheus/Grafana.

Health checks

  • Liveness: whether the service is alive.
  • Readiness: whether the service is ready to receive traffic.
  • Startup: whether a slow-starting service has completed startup.

The source links health checks with Spring Boot Actuator and Kubernetes probes.

Correlation ID

A correlation identifier allows logs/traces belonging to one end-to-end request to be connected across services.

Load Balancing

Distribute requests across multiple service instances. The source example uses five instances and distributes successive requests across U1, U2, U3 and so on to improve performance, availability and resource utilization.

Auto Scaling

Scale service capacity based on demand. The source includes Auto Scaling in the scalability pattern hierarchy and links dynamic service instances to Service Discovery.

Caching

Caching reduces repeated expensive operations by reusing previously obtained data. It is listed as a scalability pattern in the source.

Sharding

Sharding is listed as a scalability pattern for distributing data across partitions/shards so the system can scale beyond a single data store.

Message Queue

Message queues support asynchronous work and decouple producers from consumers. Kafka and RabbitMQ are the source's primary examples.

Connection pooling

Pooling controls access to expensive resources such as database connections. HikariCP is identified as Spring Boot's default DB connection pool.

15When to Use Which Pattern

The source includes a practical selection guide. Use it as the interview decision layer after learning the individual patterns.

SituationPattern to consider
Clients should not depend on internal service layout; central auth/throttling/routing is neededGateway
Service instances scale/move dynamicallyService Registry / Discovery
Downstream service may become slow/unreliableCircuit Breaker
Temporary failures are likely to recoverRetry + Timeout
One workload can consume all shared resourcesBulkhead
One business transaction spans multiple databases/servicesSaga
Read and write workloads scale differentlyCQRS
Shared infrastructure behavior should be added without changing application codeSidecar
A single view needs data from multiple servicesAPI Composition
Services should react to changes without tight couplingEvent-Driven Architecture
Safe progressive release is requiredCanary / Blue-Green / Rolling

Pattern trade-offs captured by the source

Gateway: centralization versus bottleneck/mini-monolith risk.

Service Registry: location transparency versus registry availability/operational complexity.

Circuit Breaker: graceful degradation versus threshold/fallback complexity.

Saga: distributed consistency without distributed locking versus complex compensating transactions and eventual consistency.

CQRS: independent read/write scaling versus more code and eventual consistency.

Bulkhead: failure isolation versus resource fragmentation and capacity tuning.

Sidecar: consistent infrastructure behavior without app changes versus extra resources/latency.

API Composition: simple read aggregation versus latency/reliability determined by the slowest participating service.

Event-Driven: loose coupling and scalability versus harder tracing/debugging and event-ordering/eventual-consistency concerns.

One-line memory anchors

  • Gateway: one entry point for clients.
  • BFF: backend tailored to a specific frontend.
  • Service Discovery: find service instances dynamically.
  • Database per Service: service owns its data.
  • Saga: distributed transaction as local transactions + compensation.
  • CQRS: separate reads and writes.
  • Event Sourcing: state is reconstructed from immutable events.
  • Outbox: persist business change and outgoing event atomically.
  • Timeout: don't wait forever.
  • Retry: try temporary failures again.
  • Circuit Breaker: stop calling a failing dependency.
  • Bulkhead: isolate resources so one failure does not spread.
  • Fallback: return an alternative response.
  • Rate Limiter: control request volume.
  • Idempotency: repeated requests do not repeat the business effect.
  • Sidecar: infrastructure helper beside the service.
  • Service Mesh: infrastructure layer controlling service-to-service communication.
  • Blue-Green: two environments, switch traffic.
  • Canary: gradually increase new-version traffic.
  • Rolling: replace instances gradually.
