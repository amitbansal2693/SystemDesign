1. Spring Events
Problem
Suppose a new user registers.

After registration, you need to:
Send a welcome email
Create a profile
Give bonus points
Write an audit log

Without events, your service would look like:
registerUser();
sendEmail();
createProfile();
giveBonus();
writeLog();

The registration service now has many responsibilities and is tightly coupled to other services.

Solution
Spring provides an Event mechanism.
Instead of calling every service directly, you publish an event.
Page 15 
Other components listen for that event and perform their own work.

Example
After saving the user:
applicationEventPublisher.publishEvent(new UserRegisteredEvent(user));
Now listeners automatically receive the event.
@EventListener
public void sendWelcomeEmail(UserRegisteredEvent event) {
    // Send email
}
@EventListener
public void createProfile(UserRegisteredEvent event) {
    // Create profile
}
@EventListener
public void writeAuditLog(UserRegisteredEvent event) {
    // Save log
}
The registration service doesn't know who is listening.

Advantages
Loose coupling
Easy to add new listeners
Better maintainability

Real-life Example
Think of a fire alarm.
When the alarm rings:
Fire department responds.
Security opens emergency exits.
Elevators stop.
Sprinklers activate.
The alarm doesn't call each one individually—it simply broadcasts an event.

3. Scheduling
Problem
Some tasks should run automatically.

Examples:
Send daily reports
Clean temporary files
Generate invoices every month
Sync data every hour
Backup the database every night
Without scheduling, someone would have to run these tasks manually.

Solution
Spring provides scheduling using the @Scheduled annotation.
You enable scheduling:
@EnableScheduling
Then create scheduled methods.

Example
Run every minute:
@Scheduled(fixedRate = 60000)
public void syncData() {
    System.out.println("Syncing...");
}
Page 18 
Run every day at midnight:
@Scheduled(cron = "0 0 0 * * ?")
public void generateReport() {
    System.out.println("Generating report...");
}
Spring automatically executes these methods based on the configured schedule.

Common Scheduling Options
Fixed Rate
Runs every fixed interval.
@Scheduled(fixedRate = 5000)
Runs every 5 seconds, measured from the start of the previous execution.

Fixed Delay
Runs after the previous execution completes.
@Scheduled(fixedDelay = 5000)
Waits 5 seconds after the previous execution finishes.

Cron Expression
Runs at specific times.
@Scheduled(cron = "0 0 9 * * MON-FRI")
Runs every weekday at 9:00 AM.

Advantages
Automates repetitive tasks
No manual intervention
Built-in support in Spring
Supports intervals and cron-based scheduling

Real-life Example
Think of an alarm clock.
You set it for 7:00 AM every day.
You don't manually check the time—it automatically rings at the scheduled time.
Similarly, Spring automatically executes scheduled methods at the configured times.

What is @Retryable?
@Retryable is a Spring Retry annotation that automatically retries a method when specific
exceptions occur.
Instead of writing manual retry loops:
Page 22 
try {
    return restTemplate.getForObject(...);
} catch (HttpServerErrorException e) {
    // retry logic
}

you can simply write:
@Retryable(
    retryFor = HttpServerErrorException.ServiceUnavailable.class,
    maxAttempts = 3
)
public Response callApi() {
    return restTemplate.getForObject(...);
}

Spring handles the retries automatically.

Prerequisites
Dependency
<dependency>
    <groupId>org.springframework.retry</groupId>
    <artifactId>spring-retry</artifactId>
</dependency>

<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-aspects</artifactId>
</dependency>

Enable Retry
@Configuration
@EnableRetry
public class RetryConfig {
}

Without @EnableRetry, @Retryable will not work.

Q5. Why does self-invocation break retries?
Because Spring AOP works through proxies. Internal method calls bypass the proxy.

Q6. Should I retry HTTP 400?
No.
400 indicates a client/request problem, not a temporary failure.

Q7. Should I retry HTTP 503?
Usually yes.
503 often indicates:
Server restart
Temporary overload
Maintenance
Load balancer transition

Q8. Which is better: Manual retry or @Retryable?
Generally:
Use @Retryable for standard retry scenarios.
Use manual retry only when custom logic is required.
@Retryable is cleaner, easier to maintain, and consistent across the application.

In Spring, both annotations are quite different.

@Component (Marked with class) used to auto-detect and auto-configure beans using

1.3. @Service annotation
The @Service annotation is also a specialization of the component annotation. It doesn’t
currently provide any additional behavior over the @Component annotation, but it’s a good idea
to use @Service over @Component in service-layer classes because it specifies intent better.
Additionally, tool support and additional behavior might rely on it in the future.

1.4. @Controller annotation
@Controller annotation marks a class as a Spring Web MVC controller. It too is a @Component
specialization, so beans marked with it are automatically imported into the DI container. When
