01Design Patterns: The Big Picture

What is a Design Pattern?

A design pattern is a reusable solution to a recurring object-oriented software design problem. It gives you a proven way to structure classes and objects instead of inventing a new design every time.

The three questions

Design Patterns
│
├── How do I create objects?
│       ↓
│   Creational
│
├── How do I organize / connect objects?
│       ↓
│   Structural
│
└── How should objects communicate?
        ↓
    Behavioral
        ↓
Application Architecture

Why use patterns?

  • Reduce coupling between code and concrete classes.
  • Manage complex object-creation logic.
  • Allow implementations to be switched more easily.
  • Improve readability, reuse and testability.
  • Provide a common vocabulary for discussing design.

02Gang of Four (GoF) and the 23 Patterns

What is GoF?

Gang of Four (GoF) refers to Erich Gamma, Richard Helm, Ralph Johnson and John Vlissides, authors of Design Patterns: Elements of Reusable Object-Oriented Software, published in 1994.

The book introduced the 23 classic design patterns and grouped them into three families.

03Creational Patterns: Object Creation

Purpose

Creational patterns control how objects are created. They reduce direct coupling to concrete classes and make object creation easier to change, test and maintain.

CREATIONAL
│
├── Singleton       → one shared instance
├── Factory Method  → choose the implementation
├── Abstract Factory→ create a related family
├── Builder         → construct step-by-step
└── Prototype       → clone an existing object

Three especially useful questions

  • Builder: “How should I build this object?”
  • Factory: “Which object should I create?”
  • Prototype: “I already have one — make me a copy.”
04Factory Method: Encapsulate Object Creation

Problem

Object-creation logic is spread throughout the application. Client code directly knows about concrete classes such as Circle, Square, DomesticPlan or CommercialPlan.

Solution

Centralize object creation inside a factory. The client asks for the required type; the factory decides which concrete implementation to instantiate.

Client
  ↓
Factory
  ↓ chooses implementation
Concrete Object
  ↓
Common Interface
  ↓
Client

Java example

Shape shape = ShapeFactory.getShape("Circle");

Another example

interface ElectricityPlan {
}

class Domestic implements ElectricityPlan {
}

class Commercial implements ElectricityPlan {
}

The factory can select the required implementation based on runtime data such as a string, enum or configuration.

Without Factory

Shape shape = new Circle();

The client is now coupled to Circle. Changing creation logic can require changes in many places.

With Factory

Shape shape = factory.getShape("circle");

The client does not need to know how the object is constructed. The implementation can be changed without changing the client.

Benefits

  • Centralized creation logic.
  • Loose coupling between client and concrete classes.
  • Cleaner client code.
  • Easier extension with new implementations.
  • Supports Open/Closed Principle and Single Responsibility.
  • Allows runtime selection of subclasses.

When to use

  • You have a superclass/interface with multiple implementations.
  • The exact implementation is selected at runtime.
  • Creation logic is complex or varies.
  • You want to hide new from client code.
  • A parent class wants subclasses/factory logic to determine what is created.

Real-world examples

  • UI component factories.
  • Document generators such as PDF/Word.
  • Database driver selection such as MySQL/PostgreSQL.
  • SAP reports/forms such as PDF, SmartForm or Excel.
  • Spring BeanFactory and FactoryBean.

Interview answer

“Factory Method encapsulates object creation so the client works with an interface instead of a concrete class. The factory decides which implementation to create based on runtime input or configuration.”
05Abstract Factory: Create a Compatible Product Family

Problem

You need several related objects to be created together, and those objects must remain compatible.

Example: a UI supports Windows, Mac, Dark and Light themes. Each family provides a Button, Checkbox, Dropdown and TextField. A Windows screen should not accidentally combine Windows and Mac components.

Solution

Use an Abstract Factory to create an entire family of related objects without exposing their concrete classes.

Application
     ↓
GUIFactory
 ┌───┴──────────────┐
 ↓                  ↓
WindowsFactory   MacFactory
 ↓                  ↓
Button             Button
Checkbox           Checkbox
Dropdown           Dropdown

Java example

GUIFactory factory = new WindowsFactory();

Button button = factory.createButton();
Checkbox checkbox = factory.createCheckbox();

Factory vs Abstract Factory

FactoryAbstract Factory
Creates one product at a time.Creates a family of related products.
Simpler.More complex.
Often uses string, enum or configuration as the selection.Uses concrete factory families such as WindowsFactory/MacFactory.
“Give me a Shape.”“Give me the complete Windows UI family.”

When to use

  1. You need families of related objects.
  2. The objects must be compatible with each other.
  3. You need to switch the entire product family at runtime.
  4. You want to add new product families without changing client code.

Real-world examples

  • Cross-platform GUI toolkits.
  • Database driver families.
  • Document generators with coordinated header/footer/body components.
  • SAP theme engines such as Fiori/custom themes.
Memory: Factory = one object. Abstract Factory = a consistent family of objects.
06Builder: Construct Complex Objects Step by Step

Problem

A class has many constructor parameters, especially optional parameters. This creates telescoping constructors such as new Transaction(a, b, c, d, e, f), which are hard to read and maintain.

Solution

Build the object step by step with a fluent Builder API.

Transaction transaction = Transaction.builder()
    .account(account)
    .type(TransactionType.DEPOSIT)
    .amount(amount)
    .createdAt(LocalDateTime.now())
    .note(note != null ? note : "Deposit")
    .build();

How it works

  1. builder() creates the builder.
  2. Each field(value) sets a property and returns the builder.
  3. Methods can therefore be chained.
  4. build() creates the final object.

Lombok example

@Data
@Builder
public class Transaction {
    private Account account;
    private TransactionType type;
    private BigDecimal amount;
    private LocalDateTime createdAt;
    private String note;
}

Lombok generates the builder methods, avoiding manual builder boilerplate.

Benefits

  • Readable construction.
  • Fluent API.
  • Optional fields are easy to select.
  • Avoids constructor parameter confusion.
  • Useful for immutable object construction.

Java/Spring examples

  • Lombok @Builder.
  • Spring UriComponentsBuilder.
Interview answer: “Builder is useful when object construction has many optional or ordered parameters. It separates construction from the final object and gives a readable fluent API.”
07Prototype: Clone an Existing Object

Problem

Creating a new object from scratch is expensive, complex or repetitive. You may need many objects that are mostly identical but have small differences.

Solution

Create a prepared prototype and clone it instead of rebuilding it from scratch.

Prepared Prototype
       ↓ clone()
New Object
       ↓ customize
Final Object

Java mechanism

Cloneable
clone()

Benefits

  • Faster object creation.
  • Avoids repeating expensive initialization.
  • Reduces duplicate construction code.
  • Useful when many similar objects are required.
  • Can reduce the need for additional subclasses.
  • Hides construction complexity from the client.
  • Allows objects to be added or removed at runtime.

Shallow vs Deep Copy

Shallow CopyDeep Copy
The object itself is copied.The object and referenced mutable objects are copied independently.
Reference fields can still point to the same object.Referenced state is separately duplicated.

Typical use cases

  • Game enemies and game objects.
  • Drawing applications.
  • UI objects.
  • Report templates.
  • Configuration templates.
  • Object pools.
  • SAP SmartForm/configuration versions.

Real-world example

A report template is the prototype. Each department receives a cloned report and customizes only the required fields.

Prototype vs Factory

Factory
→ Decide which new object to construct.

Prototype
→ Start with an existing object and clone it.
Memory: “Here is a template object — make a copy and customize it.”
08Singleton: Exactly One Shared Instance

Problem

Only one instance of a class should exist, for example a configuration or logger object.

Solution

Restrict construction with a private constructor and expose controlled access to the single instance.

public final class Singleton {

    private static final Singleton INSTANCE = new Singleton();

    private Singleton() {
    }

    public static Singleton getInstance() {
        return INSTANCE;
    }
}

Important Java point

Thread safety matters when implementing Singleton. The implementation must prevent multiple instances from being created under concurrent access.

Spring

Spring beans use singleton scope by default: one bean instance is normally maintained per Spring application context.

Benefits

  • One shared instance.
  • Controlled/global access.
  • Can avoid repeated creation of shared resources.
Interview answer: “Singleton restricts instantiation so only one instance is available through a controlled access point. In Java, thread safety and lifecycle management are important considerations.”
09Structural Patterns: Object Composition and Connection

Purpose

Structural patterns define how classes and objects are organized and connected into larger structures while keeping the design flexible and maintainable.

STRUCTURAL
│
├── Adapter   → compatibility
├── Bridge    → separate abstraction / implementation
├── Composite → tree structures
├── Decorator → add behavior dynamically
├── Facade    → simplify complex subsystem
├── Flyweight → share repeated state / reduce memory
└── Proxy     → control access

Why use structural patterns?

  • Improve flexibility and reusability.
  • Reduce coupling between components.
  • Make changes easier when components are swapped or extended.
  • Simplify complex interfaces.
  • Support composition of reusable parts.
  • Connect components that were not originally designed to work together.
  • Reduce memory consumption where many similar objects exist.

Typical problem → pattern

ProblemPattern
Two classes have incompatible interfaces.Adapter
Abstraction and implementation should evolve independently.Bridge
Individual and group objects should be treated the same.Composite
Add functionality without modifying the original class.Decorator
A complex API needs one simple entry point.Facade
Many similar objects consume too much memory.Flyweight
Access needs security, logging, caching or lazy loading.Proxy
10Adapter: Make Incompatible Interfaces Compatible

Problem

Two classes expose incompatible interfaces but need to work together.

Solution

Wrap the existing class in an Adapter that exposes the interface expected by the client.

Client
  ↓ expects Interface A
Adapter
  ↓ converts
Existing Class / Interface B

Java examples

  • InputStreamReader adapts InputStream to Reader.
  • Arrays.asList() adapts an array to a List view.
  • Enumeration-to-Iterator adaptation.

Spring example

Spring MVC's HandlerAdapter adapts different controller types to a common invocation mechanism.

Key benefit

Reuse existing classes without modifying their source code.

Real-world analogy

A plug adapter allows a device with one plug format to work with a different socket format.

Interview answer: “Adapter converts the interface of an existing class into the interface the client expects, allowing incompatible components to work together.”
11Bridge: Separate Abstraction from Implementation

Problem

An abstraction hierarchy and an implementation hierarchy are tightly coupled. Changing one can force changes in the other.

Solution

Separate the abstraction from the implementation and connect them through a bridge interface.

Abstraction
    ↓
Bridge
    ↓
Implementation

Example:
Shape
  ↓
Renderer
  ├── VectorRenderer
  └── RasterRenderer

Examples

  • JDBC: application code is separated from concrete database drivers.
  • AWT: component abstractions are separated from peer implementations.
  • Spring ViewResolver can bridge controllers with different view technologies.
  • Shape → draw() using a Renderer.

Benefit

Abstraction and implementation can evolve independently.

Real-world analogy

A remote control can work with different TV implementations without changing the remote abstraction.

12Composite: Treat Individual and Group Objects Uniformly

Problem

You need to represent a tree structure where a client should be able to treat an individual object and a group of objects in the same way.

Solution

Compose objects recursively into a tree and expose a common component interface.

Component
├── Leaf
├── Leaf
└── Composite
    ├── Leaf
    └── Composite
        └── Leaf

Examples

  • Files and directories.
  • Organization charts.
  • Menus and menu items.
  • XML DOM trees.
  • java.awt.Component and Container.

Java design idea

The common interface can expose operations such as add() and remove() on composite objects.

Spring connection

Composite-style processing can appear in chains of framework components such as BeanFactoryPostProcessor processing.

Real-world analogy

A file explorer displays both files and folders through one hierarchical model.

13Decorator: Add Behavior Dynamically

Problem

You need to add behavior without modifying the original class and without creating a large inheritance hierarchy.

Solution

Wrap the original object inside a decorator that implements the same interface and adds behavior before/after delegating.

Client
  ↓
Decorator
  ↓
Decorator
  ↓
Original Object

Java examples

  • BufferedReader wraps an InputStreamReader.
  • BufferedInputStream wraps FileInputStream.
  • Collections.synchronizedList() wraps a List with synchronization behavior.

Spring examples

  • Spring Security filters wrapping request processing.
  • BeanPostProcessors adding/decorating bean behavior.

Key benefit

Runtime extension without modifying the original class.

Decorator vs inheritance

Inheritance fixes the extension structure at compile time. Decorator allows behavior to be composed dynamically at runtime.

Interview answer: “Decorator wraps an object and adds behavior while preserving the same interface, so functionality can be composed dynamically.”
14Facade: One Simple Interface for a Complex Subsystem

Problem

A subsystem contains many classes and APIs that are difficult for clients to use directly.

Solution

Create a Facade that provides a simple entry point and delegates to the underlying subsystem.

Client
  ↓
Facade
  ↓
Complex Subsystem
├── Service A
├── Service B
├── Service C
└── Service D

Examples

  • FacesContext as a simplified entry point around JSF components.
  • SLF4J as a facade over different logging implementations.
  • Spring JdbcTemplate.
  • Spring RestTemplate.
  • Spring JmsTemplate.

Benefit

Reduces complexity and hides internal subsystem details from the client.

Real-world analogy

A banking application's “Transfer Money” button can trigger multiple internal services while presenting one simple operation to the user.

15Flyweight: Share Objects to Reduce Memory

Problem

Large numbers of similar objects consume excessive memory.

Solution

Separate intrinsic state that can be shared from extrinsic state that varies per usage. Reuse the shared object instead of creating duplicates.

Many logical objects
       ↓
Shared Flyweight
       +
External / extrinsic state
       ↓
Lower memory usage

Java examples

  • String pool: repeated string values can be shared.
  • Integer.valueOf() can reuse cached Integer objects for supported values.

Spring connection

Shared singleton-scoped beans illustrate the general idea of reusing one object rather than creating a separate instance for every use.

Real-world example

In a map application, thousands of trees can share the same graphical tree definition while position and other varying properties remain external.

Benefit

Significant memory optimization when a very large number of similar objects exist.

16Proxy: Control Access to the Real Object

Problem

Access to an object needs additional control or behavior such as security, logging, caching, lazy loading or remote access.

Solution

A Proxy acts as an intermediary. The client talks to the proxy, and the proxy controls or enhances access to the real object.

Client
  ↓
Proxy
├── Security
├── Logging
├── Caching
├── Lazy Loading
└── Access Control
  ↓
Real Object

Proxy types

TypePurpose
Virtual ProxyLazy loading / defer expensive object creation.
Remote ProxyRepresent a remote object or service, such as RPC/RMI.
Protection ProxyControl access based on authorization.

Java examples

  • java.lang.reflect.Proxy for dynamic proxies.
  • RMI stub proxies.

Spring examples

  • AOP proxies.
  • JDK Dynamic Proxy.
  • CGLIB proxies.
  • @Transactional uses proxy-based interception in common Spring configurations.
  • @Async uses proxy-based interception.

Hibernate connection

Hibernate can use proxies for lazy loading: the associated object is represented by a proxy and initialized only when required.

Key benefit

Cross-cutting behavior can be added transparently without changing the real object.

Interview answer: “Proxy controls access to another object. In Spring, proxies are heavily used for AOP, transactions and asynchronous execution.”
17Behavioral Patterns: Communication and Responsibility

Purpose

Behavioral patterns define how objects communicate, share responsibilities and change behavior.

BEHAVIORAL
│
├── Chain of Responsibility → pass request through handlers
├── Command               → encapsulate request
├── Interpreter            → interpret a language/expression
├── Iterator               → traverse a collection
├── Mediator                → centralize object communication
├── Memento                → capture and restore state
├── Observer               → notify dependents
├── State                  → behavior changes with state
├── Strategy               → interchangeable algorithms
├── Template Method         → common algorithm skeleton
└── Visitor                → add operations without changing object structure
18Observer: One-to-Many Notifications

Problem

Many dependent objects need to react when one object's state changes.

Solution

Create a one-to-many dependency: the Subject maintains observers and notifies them when an event/change occurs.

Subject
  ↓ event
  ├── Observer A
  ├── Observer B
  └── Observer C

Java note

Observable and Observer are historical Java examples and are deprecated in recent Java versions.

Backend interpretation

The same design idea appears whenever one event needs to notify multiple independent consumers.

19Chain of Responsibility: Pass a Request Through Handlers

Problem

Multiple handlers may be able to process a request, and the sender should not need to know which handler will handle it.

Solution

Build a chain of handlers. Each handler either processes the request or passes it to the next handler.

Request
  ↓
Handler A
  ├── handled → finish
  └── not handled
          ↓
      Handler B
          ↓
      Handler C

Examples

  • Servlet filters.
  • Logging chains.
Interview answer: “Chain of Responsibility decouples the sender from the receiver by passing a request through a sequence of possible handlers until one handles it.”
20Strategy: Interchangeable Algorithms

Problem

Multiple algorithms are required for the same operation and the application needs to select the algorithm at runtime.

Solution

Define a Strategy interface and implement each algorithm separately. The context uses the selected strategy.

Context
  ↓
Strategy interface
├── Strategy A
├── Strategy B
└── Strategy C

Examples

  • Different sorting strategies.
  • Different payment modes.
  • Different backend processing algorithms.

Why it is important in backend development

Strategy is especially useful when a large if/else or switch contains several interchangeable business algorithms.

Interview answer: “Strategy encapsulates interchangeable algorithms behind a common interface so the algorithm can be selected or changed without changing the client.”
21Command: Encapsulate a Request as an Object

Problem

An action/request needs to be represented as an object so it can be queued, logged, stored or undone.

Solution

Encapsulate the request in a Command object.

Invoker
  ↓
Command
  ↓
Receiver

Capabilities

  • Undo/redo.
  • Queue actions.
  • Log requests.
  • Delay execution.

Example

A GUI button can hold a Command object representing the action to execute when clicked.

Memory: Command turns “do this action” into an object.
22State: Behavior Depends on Current State

Problem

An object's behavior changes when its internal state changes. Large conditional blocks can become difficult to maintain.

Solution

Represent states as objects and delegate behavior to the current state.

Context
  ↓
Current State
├── State A → behavior A
├── State B → behavior B
└── State C → behavior C

Key idea

The object does not need a huge if/else block for every state. The active state object controls the behavior.

Interview answer: “State encapsulates state-specific behavior so an object's behavior changes by changing its current state object.”
23The Remaining GoF Behavioral Patterns

Interpreter

Defines a representation for a language or grammar and an interpreter for evaluating expressions in that language.

Iterator

Provides a standard way to traverse elements of a collection without exposing the collection's internal representation.

Mediator

Centralizes communication between multiple objects so they do not need direct references to each other.

Memento

Captures an object's state so it can later be restored without exposing the object's internal representation.

Visitor

Separates operations from the object structure, allowing new operations to be added without changing the classes that make up the structure.

Interpreter → interpret expressions
Iterator    → traverse collection
Mediator    → centralize communication
Memento     → save / restore state
Visitor     → add operations to object structures
Important: These five patterns belong to the complete GoF behavioral family and should not be forgotten when discussing the 23 GoF patterns.
24Pattern Comparisons: Choose the Right Pattern

Factory vs Abstract Factory

Factory
→ One product
→ Choose one implementation

Abstract Factory
→ Multiple related products
→ Keep the product family compatible

Factory vs Prototype

Factory
→ Create a fresh object
→ Select implementation / hide construction

Prototype
→ Clone an existing object
→ Avoid repeating expensive construction

Builder vs Factory vs Prototype

PatternPrimary question
BuilderHow should I build this object?
FactoryWhich object should I create?
PrototypeCan I copy an existing object?

Adapter vs Decorator vs Proxy

PatternThink
AdapterChange the interface so incompatible code can work together.
DecoratorAdd behavior while keeping the same interface.
ProxyControl access to the real object.

Facade vs Adapter

Facade simplifies a complex subsystem for the client. Adapter changes an incompatible interface so two existing components can work together.

Decorator vs Proxy

Decorator focuses on adding behavior. Proxy focuses on controlling access. The implementations can look similar because both wrap another object.

Strategy vs State

Strategy: choose an algorithm. State: behavior changes because the object's state changes.

“Creational patterns control object creation. Structural patterns control how objects are composed and connected. Behavioral patterns control communication and responsibility. In backend development, Factory is useful for selecting implementations, Singleton for shared framework-managed instances, Strategy for interchangeable business algorithms, Adapter for integrating incompatible APIs, Proxy for cross-cutting behavior such as transactions and security, and Observer/Chain for event and request processing.”
