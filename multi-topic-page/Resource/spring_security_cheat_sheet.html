2. CORS — Cross-Origin Resource Sharing Pages 2–5

What is CORS?

CORS (Cross-Origin Resource Sharing) controls access when a website tries to access a different site/API from the current site. Browsers do not allow cross-origin JavaScript requests by default; the target server must explicitly allow the origin through CORS headers.

Key idea: CORS allows selected origins to access your API. It prevents malicious websites from reading data from another origin unless that server explicitly permits the origin.

How it works

  1. Browser makes a request from the current site to a target website.
  2. If the target website allows traffic from the source website, the browser allows the request/response to be used by the current site.
  3. The server communicates its policy through CORS response headers.

Example configuration from the notes

registry.addMapping("/**")
         .allowedOrigins("http://localhost:3000")
         .allowedMethods("*");

Frontend vs backend example

ComponentOrigin
Frontendhttp://localhost:3000
Backendhttp://localhost:8080

These are different origins because the ports are different.

fetch("http://localhost:8080/api/recipes")

The browser may block it with:

Access to fetch has been blocked by CORS policy

Why is this restriction needed?

Suppose you are logged into https://bank.com. Your browser stores your session cookie. You then visit https://evil.com. The malicious site could attempt:

fetch("https://bank.com/account")

Without browser cross-origin protections, the malicious website could potentially read sensitive information such as a bank balance. Therefore, the browser requires the target site to explicitly allow the requesting origin before the response can be read.

CORS flow shown in the notes

Browser → OPTIONS Request → Server → Access-Control-Allow-Origin → Browser allows request

Spring Boot example

@CrossOrigin(origins = "http://localhost:3000")
Interview memory: CORS is primarily a browser-side cross-origin access control mechanism. The server declares which origins may access its resources; the browser enforces whether frontend JavaScript can read the response.
3. CSRF — Cross-Site Request Forgery Pages 6–7

What is CSRF?

CSRF (Cross-Site Request Forgery) is an attack where a malicious website tricks a user's browser into sending an authenticated request to another site.

The notes emphasize that this is especially relevant to session/cookie-based authentication, because browsers automatically include session cookies with requests.

Attack idea

Bank User Logged In
↓
Visits Malicious Website
↓
Hidden Transfer Request
↓
Bank receives request
↓
Money transferred

Why cookies need CSRF protection

  • Cookie = automatic passport
  • Browser sends the cookie automatically
  • Therefore, an attacker may cause the browser to send an authenticated request
  • CSRF protection adds a value the attacker cannot normally read or reproduce

Spring Security protection

Spring Security generates a unique CSRF token. The client must send the token with every state-changing request. Attackers cannot normally read this token because of the browser's Same-Origin Policy, so forged requests are rejected.

JWT REST APIs

For REST APIs using JWT in the Authorization header, CSRF protection is typically disabled because authentication is stateless and browsers do not automatically attach the JWT in the same way they automatically attach cookies.

Cookie/session
Automatic passport → browser sends it automatically → needs CSRF protection.
JWT Authorization header
Manual ID card → application explicitly attaches it → generally not vulnerable to CSRF in the same way.

Protection flow

  1. Spring Security generates a CSRF token.
  2. Client must send the token with every state-changing request.
  3. Server validates the token.
  4. A forged request without the correct token is rejected.

7. JWT — JSON Web Token Pages 11–17

JWT in one sentence

JWT (JSON Web Token) is a compact, URL-safe, JSON-based token used for stateless authentication. It carries claims such as identity and roles and is digitally signed to prevent tampering.

JWT format

xxxxx.yyyyy.zzzzz
Header.Payload.Signature

Core idea

Instead of storing sessions on the server, the client sends the token with every request.

Basic JWT flow

Login
↓
Username + Password
↓
Server verifies
↓
Generate JWT
↓
Client stores token
↓
Every subsequent request: Authorization: Bearer Token
↓
Server validates
↓
Access Granted

Advantages

  • Stateless
  • Scalable
  • Good for Microservices
  • No server session
  • Better scalability
  • Faster request processing
  • No session storage required

Disadvantages

  • Difficult logout
  • Token expiration is required

How JWT is created

  1. User sends username and password to the /login endpoint.
  2. Spring Security authenticates credentials using AuthenticationManager, UserDetailsService, and PasswordEncoder.
  3. After successful authentication, the server collects required claims.
  4. A header is created with the algorithm and token type.
  5. A payload is created containing claims.
  6. Header and payload are Base64URL encoded.
  7. JJWT creates a digital signature using the encoded header, encoded payload and secret/private key.
  8. The signature is appended to the encoded header and payload.
  9. The final token is returned to the client.
  10. The client sends it with future requests.

Claims listed in the notes

  • sub — SUBJECT — who the token is for
  • role — role such as ADMIN
  • iat — ISSUED_AT — when token was created
  • exp — EXPIRATION — when token expires
  • iss — ISSUER — who created the token, generally the application name
  • aud — AUDIENCE
  • nbf — NOT_BEFORE — token is not valid before this time
  • jti — ID
  • type — access / refresh
  • User ID — optional

Example payload

{
  "sub": "amit",
  "role": "ADMIN",
  "iat": 1722144000,
  "exp": 1722147600
}

Is JWT encrypted?

No. JWT is Base64URL encoded, not encrypted. Anyone who has the token can decode the header and payload. The signature protects against modification.

Important wording: JWTs are not decrypted — they are decoded and verified. The server decodes the payload and checks the signature using the appropriate secret/public key.

JWT signature creation

The notes show the conceptual process:

  1. Define a secret key.
  2. Encode the header and payload separately using Base64URL.
  3. Build the data to sign:
dataToSign = base64UrlEncode(header) + "." + base64UrlEncode(payload)

Then sign the data:

signature = HMAC_SHA256(dataToSign, secretKey)

Example key setup from the notes

static String secret = "superSecretKeyForJWTsuperSecretKeyForJWT";
private static Key key = Keys.hmacShaKeyFor(secret.getBytes());

JJWT builder example from the notes

String token = Jwts.builder()
    .subject(username)
    .claim("role", role)
    .issuedAt(new Date())
    .expiration(expiryDate)
    .signWith(secretKey)
    .compact();

What happens in a JWT-based system?

  1. User logs in with username/password.
  2. Server generates a JWT containing information such as userId, role, issuedAt and expiry.
  3. Server signs the JWT using a secret key or private key.
  4. Server sends the JWT back to the client as a string.
  5. Client sends the token in each future request:
Authorization: Bearer <JWT>
  1. Server verifies the signature using the same secret key or corresponding public key.
  2. If valid, the server reads the payload and grants access.

JWT verification

  • JWT is verified inside the Spring Security Filter Chain.
  • The server checks expiration while validating the token.
  • Libraries such as JJWT automatically validate the exp claim when parsing the JWT.
  • Invalid or expired JWT → 401 Unauthorized.

Why doesn't the server trust the client?

The client can modify or forge a token. Therefore, every incoming JWT must be verified for:

  • Signature
  • Expiration
  • Issuer — optional
  • Audience — optional

JWT best practices from the notes

  • Use HTTPS.
  • Keep access tokens short-lived, e.g. 15 minutes.
  • Use refresh tokens.
  • Store refresh tokens securely, preferably HttpOnly cookies.
  • Never store passwords or sensitive data in JWT claims.
  • Validate signature and expiration on every request.
  • Rotate signing keys periodically.
  • Consider RS256 for distributed systems where services only need the public key to verify tokens.

8. OAuth2 — Open Authorization Pages 17–21

What is OAuth2?

OAuth2 is an authorization framework/protocol. It allows users to give one application limited access to another application without sharing their password.

Key idea: Instead of giving away your password, you give a token that lets another app act on your behalf — in a limited, secure way.

OAuth2 roles

User
↓
Client Application
↓
Authorization Server
↓
Resource Server

Simple flow from the notes

User → Google Login → Google verifies → Access Token → Application → API Access

Real-life example: Login to LinkedIn with Google

  1. User clicks Sign in with Google on LinkedIn.
  2. Google asks for consent to share basic profile information.
  3. User approves.
  4. Google gives LinkedIn an access token.
  5. LinkedIn uses the token to get the user's name and email.
  6. Login completes without the user giving LinkedIn the Google password.

OAuth flow — 4 main steps

  1. Authorization Request: The app sends the user to the provider's login page, such as Google.
  2. User Grants Access: User logs in and clicks Allow.
  3. Authorization Code: Provider redirects back to the app with a short-lived code.
  4. Token Exchange: App sends the code plus credentials and gets an access token.

Behind the scenes — detailed example

Step 1 — LinkedIn requests Google authorization

LinkedIn redirects the user to Google's authorization page, for example:

https://accounts.google.com/o/oauth2/auth?client_id=...&scope=...

LinkedIn includes:

  • Client ID — identifies LinkedIn
  • Scope — what information LinkedIn wants, such as email and name
  • Redirect URI — where Google should send the user afterward

Step 2 — User logs in / gives consent

Google asks whether LinkedIn may see information such as email address and basic profile information. The user clicks Allow.

Step 3 — Google redirects back with an authorization code

Google sends LinkedIn a temporary authorization code, not the actual token yet.

GET https://linkedin.com/callback?code=XYZ123

The code is short-lived and intended to be used only once.

Step 4 — LinkedIn exchanges the code for a token

LinkedIn communicates server-to-server with Google:

POST https://oauth2.googleapis.com/token

{
  code: "XYZ123",
  client_id: "linkedin-client-id",
  client_secret: "linkedin-secret",
  grant_type: "authorization_code"
}

Google responds with an access token:

{
  "access_token": "ya29.a0AVvZV...",
  "expires_in": 3600
}

Step 5 — LinkedIn uses the access token

GET https://www.googleapis.com/oauth2/v2/userinfo
Authorization: Bearer ya29.a0AVvZV...

Google can return information such as:

{
  "email": "alex@gmail.com",
  "name": "Alex Kumar",
  "picture": "https://..."
}

Why this is safe — as described in the notes

  • You never gave LinkedIn your Google password.
  • You chose exactly what information to share.
  • You can revoke access from Google settings.
  • The token has a time limit and cannot be used indefinitely.

UserYou — granting access to your Google account

9. SSH Keys vs OAuth Tokens vs SSL Certificates vs Credentials Pages 22–25

1. SSH Keys

SSH (Secure Shell) is a protocol used to securely connect to remote systems such as servers.

What is SSH key-based authentication?

It uses a pair of cryptographic keys:

  • Public key: shared with the server
  • Private key: kept safe by the user

It replaces the need for a password.

Why use SSH keys?

  • More secure than passwords; the notes describe them as almost impossible to brute-force.
  • Useful for automated scripts or remote server management.
  • Avoids sharing plain-text passwords.

When to use SSH keys?

  • Managing cloud servers such as AWS EC2 or DigitalOcean
  • Git over SSH, such as GitHub or GitLab
  • DevOps pipelines requiring secure access

Real-life use case

A developer connects from a laptop to a Linux server on AWS. They generate SSH keys, upload the public key to AWS, and connect securely using the private key.

Step-by-step

  1. Generate keys on your machine:
ssh-keygen -t rsa -b 4096 -C "your_email@example.com"
  1. Upload the public key to the server's ~/.ssh/authorized_keys.
  2. When connecting, the server sends a challenge encrypted with the public key.
  3. Your SSH client/laptop decrypts it using the private key.
  4. If successful → access is granted.

2. OAuth Tokens

OAuth (Open Authorization) is described in the notes as a protocol/token-based authorization approach that lets one app access data from another without sharing user credentials.

Why use OAuth?

  • Delegate secure access to APIs without exposing passwords.
  • Tokens can expire and be revoked.
  • Helps prevent unauthorized access if a token is leaked.

When to use OAuth?

  • Applications accessing user accounts from other services
  • Protecting API endpoints

Real-life use case

A travel app wants access to a user's Google Calendar to book trips. Instead of asking for the Google password, it uses OAuth to request permission and gets a token.

Step-by-step

  1. Client sends request with client ID + secret to the Authorization Server.
  2. Server validates credentials and sends back an access token.
  3. Client uses the token to access protected APIs.
  4. Server checks token validity before allowing the request.

3. SSL Certificates

SSL (Secure Sockets Layer) certificates are digital files that secure communication over the internet, especially websites using HTTPS.

They ensure data sent between browser and server is encrypted and safe. The notes use “SSL” terminology while also explaining HTTPS/TLS.

Why use SSL?

  • Protects against man-in-the-middle attacks.
  • Encrypts sensitive data such as passwords and credit card numbers.
  • Builds trust with users and shows the browser padlock.

When to use SSL?

  • Always use SSL/HTTPS on public-facing websites.
  • Especially important for e-commerce, login pages and APIs.

Real-life use case

An e-commerce site uses SSL to protect user passwords and credit card details during checkout.

Step-by-step

  1. Browser contacts the website, e.g. https://example.com.
  2. Server sends its SSL certificate.
  3. Browser checks certificate expiry.
  4. Browser checks issuer / trusted Certificate Authority.
  5. Browser checks domain-name match.
  6. If checks pass, browser trusts the connection.
  7. A secure connection is established using encryption.
  8. Data sent and received is now secure.

4. Credentials — Username & Password

This is the most basic form of authentication: the user provides a username and password and the system checks them against stored records.

Why use it?

  • Simple and widely understood.
  • Easy to implement in web and mobile applications.

When to use?

  • Basic login systems such as user portals and admin dashboards.
  • Internal applications that do not need OAuth or tokens.

Real-life example

You log in to Netflix using email and password. Behind the scenes, credentials are sent securely over HTTPS and verified.

Step-by-step

  1. User sends username + password over a secure HTTPS connection.
  2. Server decrypts the request.
  3. Server checks whether the user exists in the database.
  4. Server checks whether the password hash matches.
  5. If yes → Login success.
10. Static URLs & Method-Level Security Page 25

Restrict static URLs

The notes include this Spring Security configuration example for excluding static resources from security:

<http pattern="/static/**" security="none" />

Spring Security at method level

  • Spring Security supports method-level security.
  • The notes state that Spring Security uses AOP for security at the method level.
  • Security can be applied using annotations based on Spring annotations or JSR-250 annotations.
  • Java configuration is used to activate detection of annotations.
  • It typically secures your services.

Important note from the source

Do not access repositories directly when the intention is to enforce service-layer security, because direct repository access can bypass the security applied at the service/method level.

Annotations mentioned

  • @Secured
  • @RolesAllowed

Example from earlier in the notes

@PreAuthorize("hasRole('ADMIN')")
