02Creational Patterns: How Objects Are Created

Core mental model

CREATIONAL ↓
How should I create objects? ├── Need only one object? → Singleton ├── Need different object types? → Factory ├── Need complex object creation? → Builder ├── Need to clone objects? → Prototype └── Need related object families? → Abstract Factory

lists Factory, Singleton, Abstract Factory, Builder and Prototype as the main creational patterns. fileciteturn5file0L6-L12

What they optimize

  • Reduce coupling between client code and concrete classes.
  • Centralize or simplify object creation logic.
  • Allow object types to change without spreading new throughout the code.
  • Improve readability, reuse and testability.
03Factory Pattern: Choose Which Object to Create

Problem

Object creation logic is spread throughout the code, or the client should not know the exact concrete class being instantiated.

Solution

Encapsulate creation logic inside a factory. The client asks for an object and the factory decides which implementation to return.

Shape shape = factory.getShape("circle");

Core flow

Client ↓
Factory ↓ decides using input / type
Concrete implementation ↓
Common interface returned to client

Benefits

  • Encapsulation — creation logic is centralized.
  • Loose coupling — client depends on an interface rather than concrete classes.
  • Easier extension — add implementations through the factory.
  • Cleaner client code — fewer scattered new statements.

When to use

says to use Factory when you have a superclass/interface with multiple implementations, need runtime selection, want to hide creation logic, or want to support SOLID goals such as OCP and SRP. fileciteturn5file0L617-L621

Java / Spring examples

  • ShapeFactory
  • UI component factories
  • Document generators
  • Database driver selection
  • SAP report/form generation
  • Spring BeanFactory / FactoryBean

Factory Method note

Factory Method means creating objects based on runtime input such as a string or enum, hiding object creation logic. fileciteturn5file0L566-L570

04Factory vs Abstract Factory: One Object vs Object Family

The most important distinction

Factory → Create ONE object → Choose among implementations Abstract Factory → Create a FAMILY of related objects → Keep the family compatible
AspectFactoryAbstract Factory
PurposeCreate one object from multiple optionsCreate families of related objects
ReturnsOne objectMultiple related objects
Typical triggerString / enum / configFactory object / factory subclass
FocusObject creationFamily/group creation
ComplexitySimplerMore structured

Factory example

Shape s = shapeFactory.getShape("circle");

Abstract Factory example

GUIFactory factory = new WindowsFactory();
Button b = factory.createButton();
Checkbox c = factory.createCheckbox();

Use-case test

Ask yourself: “Do I need one product, or a compatible set of products?”

  • One product → Factory.
  • Compatible product family → Abstract Factory.

The key distinction is: Factory creates a single object from multiple options, while Abstract Factory creates a related product family. fileciteturn5file0L467-L476

05Builder Pattern: How Should I Build This Object?

Problem

A class has many optional parameters, leading to telescoping constructors or confusing constructor calls.

Solution

Build the object step by step through a fluent API.

Transaction.builder() .account(account) .type(TransactionType.DEPOSIT) .amount(amount) .createdAt(LocalDateTime.now()) .note(note != null ? note : "Deposit") .build();

What happens

  1. builder() creates a builder.
  2. Each fluent method sets one property and returns the builder.
  3. build() creates the final object.

Benefits

  • Readable object construction.
  • Fluent API.
  • Optional fields can be selected naturally.
  • Avoids constructor parameter chaos.
  • Useful for immutable object creation.

Lombok example from 

@Data
@Builder
public class Transaction { private Account account; private TransactionType type; private BigDecimal amount; private LocalDateTime createdAt; private String note;
}

Builder vs Factory vs Prototype

PatternQuestion it answers
Builder“How should I build this object?”
Factory“Which object should I create?”
Prototype“I already have one — make me a copy.”
06Prototype Pattern: Clone an Existing Object

Problem

Creating a new object from scratch is expensive, complicated or repetitive.

Solution

Clone an existing prepared object and customize the copy.

Prepared Prototype ↓ clone()
New Object ↓ customize
Final Object

Cloneable
clone()

Typical use cases

  • Game objects / enemies.
  • UI builders.
  • Document templates.
  • Object templates.
  • Configuration copies.
  • SAP SmartForms / configuration versions.

Shallow vs Deep Copy

Shallow copyDeep copy
Copies the object itself.Copies referenced objects as well, when implemented.
Reference fields may still point to the same referenced object.Referenced state is independently copied.

Prototype vs Factory

Factory: decide what new object to construct. Prototype: start from an existing prepared object and copy it.

The key distinction is: hiding creation logic versus cloning an existing object. fileciteturn5file0L514-L515

09Adapter Pattern: Make Incompatible Interfaces Work Together

Problem

Two incompatible interfaces need to work together.

Solution

Create an adapter/wrapper that converts one interface into the interface expected by the client.

Client ↓ expects Interface A
Adapter ↓ converts
Existing class / Interface B

Examples from

  • InputStreamReader: InputStream → Reader.
  • Arrays.asList(): array → List.
  • Spring MVC HandlerAdapter.
  • Real-world analogy: a plug adapter between incompatible sockets.

Key benefit

Reuse existing classes without modifying them.

10Decorator Pattern: Add Behavior Dynamically

Problem

Add behavior dynamically without changing the existing class.

Solution

Wrap the original object inside another object that adds behavior.

Original Object ↓ wrapped by
Decorator ↓
Additional behavior

Java examples

  • BufferedReader wrapping InputStreamReader.
  • Collections.synchronizedList() wrapping a List.

Spring examples

  • Spring Security filters wrapping HttpServletRequest.
  • BeanPostProcessors decorating bean logic.

Decorator vs inheritance

emphasizes runtime extension rather than static inheritance. fileciteturn5file0L378-L388

11Facade Pattern: Simplify a Complex Subsystem

Problem

A subsystem exposes APIs that are too complex for the client to use directly.

Solution

Provide a simpler interface that delegates to the complex subsystem.

Client ↓
Facade ↓
Complex subsystem
├── Service A
├── Service B
└── Service C

Examples from

  • SLF4J as a facade for logging frameworks.
  • Spring JdbcTemplate.
  • Spring RestTemplate.
  • Spring JmsTemplate.

Interview phrase

Facade hides subsystem complexity behind a simple entry point.

12Proxy Pattern: Control Access to Another Object

Problem

Access to another object needs to be controlled—for example security, logging, caching or lazy loading.

Solution

A proxy acts as an intermediary between the client and the real object.

Client ↓
Proxy ├── security ├── logging ├── caching ├── lazy loading └── access control ↓ Real Object

Proxy types

  • Virtual proxy — lazy loading.
  • Remote proxy — RPC.
  • Protection proxy — authorization.

Spring examples

In Spring, AOP proxies, JDK Dynamic Proxy, CGLIB, @Transactional and @Async with Proxy. fileciteturn5file0L153-L163

Hibernate connection

15Observer Pattern: Notify Many Dependents

Problem

Many dependent objects must react when one object changes.

Solution

Create a one-to-many dependency: the subject publishes a change and observers react.

Subject ↓ change ├── Observer A ├── Observer B └── Observer C

mentions Java's Observable/Observer as a historical example and notes that they are deprecated in recent versions. fileciteturn5file0L193-L196

16Chain of Responsibility: Pass a Request Through Handlers

Problem

Multiple handlers may be able to process a request.

Solution

Pass the request through a chain until a handler processes it.

Request ↓
Handler A ↓
Handler B ↓
Handler C ↓
Handled

Source examples

  • Servlet filters.
  • Logging chains.

defines the pattern as passing a request through a chain until one handler handles it. fileciteturn5file0L197-L200

17Strategy Pattern: Switch Algorithms at Runtime

Problem

Multiple algorithms are needed and the application should be able to choose among them.

Solution

Define a strategy interface and provide multiple implementations that can be selected at runtime.

Context ↓
Strategy interface ├── Strategy A ├── Strategy B └── Strategy C

Source examples

  • Sorting strategies.
  • Payment modes.

Interview framing

Strategy is especially useful when you have multiple interchangeable business algorithms and want to avoid a large conditional block.

Strategy is as one of the patterns commonly used in backend microservices. fileciteturn5file0L213-L217

18Command and State: Request vs State-Driven Behavior

Command Pattern

Problem: Encapsulate a request as an object.

Solution: Represent an action as an object so it can support concepts such as undo/redo and queuing.

Invoker ↓
Command ↓
Receiver

Example: GUI button actions. fileciteturn5file0L206-L209

State Pattern

Problem: An object's behavior changes when its internal state changes.

Solution: Model state transitions as state objects.

Context ↓
Current State ├── State A ├── State B └── State C

fileciteturn5file0L210-L212

Quick distinction

Command: “What action/request should I encapsulate?”

State: “How should this object behave in its current state?”

Study order

  1. Understand the three families.
  2. Master Factory, Builder, Prototype and Abstract Factory.
  3. Master Adapter, Decorator, Facade and Proxy.
  4. Learn Composite, Bridge and Flyweight.
  5. Master Strategy, Observer and Chain of Responsibility.
  6. Then learn Command, State and Template Method.
  7. Finally, connect every pattern to a real Java/Spring example and an interview problem statement.
Best interview habit: Don't start with “Factory is a creational pattern.” Start with the problem: “We had multiple implementations and the client shouldn't know which concrete class to instantiate, so I centralized that decision in a Factory.”
